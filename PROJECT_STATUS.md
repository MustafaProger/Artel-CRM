- Ветка: `main`.
- Текущий commit: `f5cae902681e638b8e12fac48a1803d3c02293a5` (`Redesign sign-in screen and refine sidebar controls and transitions`).
- До обновления этого документа рабочее дерево было чистым, `HEAD`, `origin/main` и `origin/HEAD` указывали на один commit.
- Production отдаёт те же JS/CSS-файлы, что свежая локальная сборка. Неавторизованный API возвращает `401`, а `/.env` и исходные JSON не раздаются (`404`). `/api/auth/session` подтверждает, что первоначальная учётная запись уже создана (`needsSetup: false`) и setup защищён серверным токеном.

Ближайшая цель следующего этапа — выполнить авторизованную приёмку production с реальной учётной записью и закрыть внешние интеграции/незаполненные разделы, не меняя существующую бизнес-логику и рабочие данные без отдельного решения владельца.

## 2. Что завершено

### Доступ и безопасность

- Реализованы серверные сессии, вход/выход, первичная настройка директора, смена пароля и роли `director`, `admin`, `manager`.
- Область данных менеджера ограничивается на сервере; управляющие действия скрыты в интерфейсе и дополнительно запрещены API.
- Мутации защищены проверкой Origin, версиями записей и конфликтами конкурентного изменения.
- Экран входа приведён к стилю FuelLead; сохранены setup, login, loading, error и retry-состояния, клавиатурная навигация и reduced motion.

### Рабочие разделы

- «Работа»: задачи, заметки и работа с компаниями, исполнители, комментарии, приватные файлы, напоминания, архив/возврат одним действием и удаление с проверкой прав и версии.
- «Отгрузки»: бензовозы и отдельный режим АЗС, создание/редактирование/удаление машины с несколькими клиентами, распределение тоннажа и затрат, оплаты, фильтры, сортировка, CSV и виртуализация.
- Формула новых бензовозных отгрузок следует шаблону формы оплаты; исторические исходные значения не перезаписываются. АЗС использует отдельные правила и не принимает F2.
- Ширины столбцов меняются как в Excel на широком десктопе, сохраняются отдельно по виду таблицы и сбрасываются мышью или клавиатурой; мобильные размеры от них не зависят.
- «Справочники»: компании, менеджеры, товары, формы оплаты, водители, автомобили и адреса; удаление учитывает зависимости и tombstone-записи. Архивирование клиентов/поставщиков сохраняет исторические ID и связи.
- «Китай»: несколько заправок за день, независимые платежи и точный баланс за всё время `поступления − заправки`; на узких экранах таблица прокручивается внутри контейнера.
- PWA-иконки, manifest и service worker подключены. Web Push умеет подписывать устройство, отправлять тест, доставлять напоминания и исключать повторы; GitHub Actions настроен на dispatch каждые 5 минут через OIDC.

### Хранение и публикация

- Исходный снимок `data/local-xlsx-final/` считается неизменяемым. Все рабочие изменения хранятся отдельно в envelope `operations.json` с checksum и `revision`.
- Локальная запись атомарна и защищена lock-файлом. Production использует приватный Vercel Blob `artel/operations.json`, сильный ETag и `If-Match`; при конфликте возвращается `409`, повреждённое или отсутствующее хранилище не заменяется пустым.
- Очистка операций и справочников отделена от старта приложения, требует явного запуска, создаёт и перечитывает резервную копию. Флаг `sourceOperationsCleared` не позволяет импортированным операциям появиться снова.
- Автоматическая публикация идёт из GitHub `MustafaProger/Artel-CRM`, ветка `main`, в проект Vercel `artel-crm`.

## 3. Ключевые технические решения

| Область | Решение, которое нужно сохранять |
| --- | --- |
| Архитектура | React/Vite в `web/`; единый Node API создаётся в `server/local-api.ts`; Vercel-адаптер — `server/cloud-handler.ts`. |
| Данные | Не править исходный XLSX/JSON при работе CRM. Изменения, удаления, аккаунты, задачи, Китай и push живут в отдельном operations-store. |
| Конкурентность | На клиентских сущностях используются версии; локально — сериализация и lock, в Blob — сильный ETag/`If-Match`. Не обходить конфликт перезаписью. |
| Авторизация | Проверки ролей и области данных обязательны на сервере; скрытие кнопок не считается защитой. Пароли хешируются, сессии хранятся в HttpOnly cookie. |
| Расчёты | Денежные и китайские суммы обрабатываются точной десятичной арифметикой. Исторические результаты Excel сохраняются, новые правила применяются только там, где это явно предусмотрено. |
| QA | Браузерные CRUD-проверки запускаются на временном `ARTEL_STORE_DIR`; production и рабочий локальный store не должны участвовать в тестовых мутациях. |
| Push | Разрешение запрашивается только действием пользователя. Постоянный секрет GitHub не нужен: планировщик подписывает вызов OIDC-токеном, который проверяется сервером. |

Локальный запуск: `npm run dev`, адрес `http://127.0.0.1:5173`. Закрытые настройки задаются только через локальное/production-окружение; реальные значения не должны попадать в Git, отчёты или логи.

## 6. Известные проблемы и ограничения

- «Операторская» пока только сообщает, что исходный Excel и правила не предоставлены. Реализацию нельзя начинать с предположений о колонках или формулах.
- «Обзор» и «Склад» намеренно пустые после согласованной очистки; в «ЗП» есть только вкладки водителей/менеджеров без расчётов.
- Актуальная Google-таблица не предоставлена и не сверена. Текущий immutable snapshot основан на `БХЧ Артэль 2026 (5).xlsx`; ошибки и неполные формулы самого источника перечислены в `docs/source-audit.md`.
- Живой запрос к Чекко ранее завершался `502`/таймаутом. Тестовый контракт покрыт, ручное заполнение доступно, но реальная интеграция из текущей сети/production требует повторной проверки.
- Реальная push-доставка на физическое устройство и фактическая регулярность GitHub schedule в этом handoff не проверялись. Для iPhone приложение нужно добавить на экран «Домой»; GitHub schedule может задерживаться и отключается в публичном репозитории после длительной неактивности.
- `README.md` и начало `docs/vercel-deployment.md` содержат устаревшие формулировки о публичном API, локально не опубликованных функциях и старом количестве тестов. Ориентироваться на этот файл и текущий код; документацию нужно синхронизировать следующей отдельной правкой.
- `scripts/verify_vercel.mjs` рассчитан на прежний публичный API и полное равенство local/production. После включения авторизации и начала независимой работы облачного store этот сценарий больше не является корректной production-проверкой.

## 7. Опробованные, но не сработавшие подходы

- Чекко не стал доступен после принудительного IPv4/TLS 1.2; по одному сетевому таймауту нельзя делать вывод о неверном ключе или исчерпанном лимите.
- Первый ad-hoc Axe-прогон через `browser.newPage()` завершился ошибкой `Please use browser.newContext()`. Для Axe/Playwright нужен отдельный `browser.newContext()`; исправленный прогон прошёл.
- Desktop headless WebKit зависал при активном service worker. В этом тестовом профиле service worker блокируется; push проверяется отдельным сценарием и на мобильных профилях.
- Сравнение полного рабочего store до/после браузерного QA давало ложное изменение из-за фонового push heartbeat/revision. Актуальные сценарии используют временное хранилище и не смешивают тестовые записи с рабочими.
- Системный `/usr/bin/python3` (3.9.6) не запустил export-тесты из-за отсутствующего `openpyxl`. Одноразовый virtualenv с зависимостями из `requirements.txt` решил проблему; менять код тестов не потребовалось.
