## 3. Ключевые технические решения

### Приложение и API

React 19 + TypeScript + Vite 6. Локальный Node API подключён как Vite middleware и работает как в `dev`, так и в `preview`; отдельного API-процесса сейчас нет. Финансовые значения передаются десятичными строками или `null`; суммы считаются через `decimal.js` с точностью 80. Пропуск не заменяется нулём.

| Маршрут | Контракт |
| --- | --- |
| `GET /api/snapshot?shipments=omit` | Компании, платежи, склад, качество и актуальные агрегаты; `shipments: []`. Интерфейс использует этот вариант. Без параметра сохранён полный снимок для совместимости. |
| `GET /api/shipments` | Параметры `limit`, `offset`, `query`, `period`, `manager`, `settlement`, `companyId`. По умолчанию 50, максимум 100; сортировка по дате убыванию, затем стабильному ID. Ответ: `items`, `total`, `hasMore`, `nextOffset`, `summary`, `topCustomers`. Итоги относятся ко всему фильтру. |
| `GET /api/shipments/:id` | `{ shipment }`, используется для адресного получения операции. |
| `POST /api/shipments` | `{ fields }` → `{ shipment }`, новая операция с версией 1. |
| `PATCH /api/shipments/:id` | `{ fields, version }` → `{ shipment }`; версия увеличивается. |
| `DELETE /api/shipments/:id` | `{ version }` → `{ deleted, id }`; запись исключается из рабочих итогов. |
| `POST /api/companies/from-inn` | `{ inn }` → `{ company, created }`; повторный ИНН возвращает существующую компанию без нового обращения к провайдеру. |

Исходные операции имеют версию 0. UI передаёт версию при изменении/удалении; устаревшая версия даёт 409. Параметр версии на API пока необязателен — это учитывать при добавлении другого клиента.

Первоначальная загрузка интерфейса не получает все отгрузки: обзор запрашивает 5 последних, карточки компаний — порции по 50, проверка данных — связанные строки по запросу. Фильтры отменяют/игнорируют устаревшие ответы. Таблица виртуализирована: высота строки 60 px, запас по 8 строк; не менять высоту CSS без пересмотра расчёта окна.

### Данные и сохранение

- `data/local-xlsx-final/` — неизменяемая выгрузка БХЧ с `manifest.json` и SHA-256. Все восемь файлов повторно сверены при передаче, расхождений нет.
- `data/local-operations/operations.json` — отдельные изменения, новые отгрузки, отметки удаления и реквизиты фирм. Путь можно переопределить через `ARTEL_STORE_DIR`.
- Хранилище связано с SHA-256 исходной книги. Используются проверка структуры и контрольной суммы, очередь записей, эксклюзивная `.lock`, временный файл, `fsync` и атомарное переименование. Повреждённый файл не заменяется пустым.
- Для переноса нужны исходная выгрузка **и** рабочие изменения, если они уже созданы. `data/`, `qa/` и `.env` исключены текущим `.gitignore`: будущий Git-checkout сам по себе не восстановит данные и отчёты. Новый снимок Excel нельзя просто подставить под существующее хранилище: требуется сопоставление ID и миграция изменений.
- Идентичность компании определяется ИНН/ID. Одинаковое название не объединяет разные юридические лица. Редактор передаёт внутренние `customer_id`, `supplier_id`, `carrier_id` отдельно от видимых колонок.
- Варианты регистра подписей менеджеров объединены в исходные 7 групп; `fields.manager_label` сохраняет текст источника. Владелец записи и пользователь из подписи автоматически не создаются.

### Бизнес-значения и происхождение

Формулы Excel не исполняются. Пользователь вводит суммы, прибыль, оплату, долг и срок независимо; сервер пересчитывает агрегаты по сохранённым значениям, а не бизнес-формулы отдельных строк. В исходнике есть разные правила прибыли, включая коэффициент 0.83, условные правила долга/срока и закупочная цена без единой указанной единицы.

`kvp_source` (КВП) и `additional_costs` (дополнительные затраты) — разные поля. Безымянные значения столбца W хранятся в `unlabelled_note`, не используются как дата оплаты. Новые поля `customer_inn`, `supplier_inn`, `loading_address`, `unloading_address`, `additional_costs`, `payment_date` отсутствуют в исходной выгрузке и не заполняются предположениями. Полный порядок колонок — в `web/src/shipment-templates.ts`.

Склад и `quality` остаются аудитом исходного XLSX, даже после изменения отгрузок. Платежи доступны только для просмотра/экспорта. Девять текстовых сумм нормализованы, 70 платежей без корректной даты учитываются в общем итоге, но не в месячных агрегатах. Суммы отгрузок и выписки сами по себе не подтверждают задолженность. Подробности исходника — `docs/source-audit.md`.

### Чекко и локальный доступ

`server/checko.ts` вызывает официальные `/v2/company` и `/v2/entrepreneur` методом POST с таймаутом 12 секунд. Проверяются контрольные цифры ИНН, ИНН в ответе, наименование и статус ответа. Сохраняются название, полное название, ИНН, КПП, ОГРН/ОГРНИП, доступный адрес, статус и дата получения.

`CHECKO_API_KEY` загружается сервером из `.env` через Vite `loadEnv`; значения настроек в документ не включены. Не использовать префикс `VITE_`. Шаблон — `.env.example`. После изменения настроек сервер следует перезапустить. Проверки ключа в клиентских файлах и прав приватного файла отражены в `qa/final-integrity.json`.

API проверяет локальный адрес, Host/Origin, запрещает cross-site запросы и кеширование. JSON-запросы ограничены 128 КБ. Данные, серверные файлы и `.env` не раздаются через Vite. Авторизации и прав пользователей пока нет; `config/roles.json` — спецификация, не механизм защиты.

## 6. Известные ограничения и уже опробованные подходы

- **Чекко:** реальный POST через CRM завершился таймаутом. Независимые HTTPS HEAD к `api.checko.ru` и `checko.ru`, в том числе IPv4/TLS 1.2, тоже дали `SSL connection timeout`. Переключение на IPv4/TLS 1.2 проблему не решило. Причина сетевой недоступности не установлена; считать ключ неверным или лимит исчерпанным оснований нет. При передаче новых запросов к провайдеру не выполнялось.
- **Мобильная таблица:** проверки одного лишь отсутствия горизонтального выхода страницы недостаточно. Закреплённые дата/контрагент/действия перекрывали поздние поля на 320 и 768 px. Отключения только до 760 px оказалось недостаточно из-за боковой панели; итоговое правило ≤1100 px проверено через фактическое попадание указателя в крайнюю ячейку.
- **Даты и менеджеры:** исходный datetime нельзя напрямую подставлять в `input type=date`; теперь он нормализуется до дня. Разделение менеджеров по буквальному регистру давало 9 вместо 7 групп; это исправлено без изменения исходного текста ячеек.
- **Финансовые проверки:** стандартной точности Decimal 20 не хватило для сохранённых длинных дробей. Приложение и тестовые расчёты используют 80. Универсальный пересчёт прибыли/долга не вводился: сначала необходимо согласовать бизнес-правила.
- **Масштабирование:** оптимизированы доставка отгрузок и DOM. Backend по-прежнему собирает рабочий снимок и агрегаты в памяти; компании/платежи загружаются начальным ответом целиком, загруженные отгрузки накапливаются в памяти браузера. Это не постраничное чтение из БД и не доказательство работы на произвольно большом объёме.
- **Хранение:** нет истории всех редакций и интерфейса восстановления удалений. Автоматического восстановления оставшейся после аварии `.lock` в коде нет; при занятом хранилище сначала проверить запущенные процессы и сохранить данные, не удалять файл блокировки вслепую.
- **Следующие функции ещё не реализованы:** пользователи/права, общая база, онлайн-синхронизация, запись обратно в Excel и редактирование платежей. Ф2, КВП и неоднозначные финансовые правила требуют пояснений владельца данных. Ссылка на живую Google-таблицу не предоставлена; онлайн-сверки нет.

## 7. Последовательность продолжения

1. **Восстановить среду и точку отсчёта.** Прочитать этот файл, проверить фактический Git/runtime, сохранить исходную выгрузку и рабочие изменения, если они появились. Запустить сборку/API-тесты и соответствующий браузерный прогон после изменений. Не создавать новый пустой снимок вместо существующих данных.
2. **Закрыть приёмку Чекко.** Проверить доступность HTTPS без передачи ключа; после восстановления соединения выполнить один реальный запрос и проверку сохранения/повторного ИНН в отдельном хранилище. В `qa/verify-checko-live.ts` сохранён сценарий этого этапа без секрета; он читает серверную настройку и использует временную базу. Сначала сверить его контрольные количества с текущим снимком. Не выводить тело запроса с ключом. Обновить отдельный live-отчёт, не подменяя им mock-проверки.
3. **Уточнить бизнес-правила до автоматических расчётов.** Получить определения Ф2, КВП, единиц закупочной цены, правил прибыли, оплаты, долга и срока. Добавлять автоматизацию отдельно от сохранённых результатов исходника, с согласованными примерами и тестами.
4. **При получении живой таблицы подготовить новый снимок отдельно.** Сверить его с текущим через экспортёр/верификатор; определить миграцию существующих ID и локальных изменений. Не менять базовый SHA под уже созданным хранилищем.
5. **Перед общим доступом согласовать следующий архитектурный этап.** Выбрать хранилище для выбранного режима работы (локальный или многопользовательский), миграцию, резервное копирование, историю изменений и пользователей/права. Для роста данных отдельно измерить серверные агрегаты и загрузку компаний/платежей. Роли из `config/roles.json` должны быть реализованы на сервере до предоставления общего доступа.

Пункты 2–5 — незавершённая работа/условные следующие этапы, а не уже выполненные изменения.
