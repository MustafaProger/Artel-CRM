# Отдельный процесс проверки напоминаний

Подготовлены только локальные файлы. Служба нигде не установлена; внешнего адреса и секретов в шаблонах нет. В режиме `npm run dev` CRM уже проверяет напоминания каждые 30 секунд, поэтому отдельный процесс обычно не нужен. Этот runner пригодится для API без встроенного расписания или отдельного планировщика в будущем.

Нужен Node.js 18+ и запущенный API с настроенными Web Push и `PUSH_SCHEDULE_ENABLED=true`. Runner не запускает API. По умолчанию он обращается только к `http://127.0.0.1:5173/api/push/dispatch`. Вызов отправляет реальные ожидающие уведомления подключённым устройствам, если у API настроена отправка.

Передайте процессу тот же `CRON_SECRET`, который использует API, либо укажите путь к файлу с ним в `ARTEL_REMINDERS_SECRET_FILE`. Секрет: 32–512 печатных ASCII-символов без пробелов. Одновременно оба способа задавать нельзя. Runner самостоятельно не загружает `.env`.

```sh
# Одна проверка; код завершения 1 означает ошибку HTTP, JSON или отправки.
node scripts/dispatch-reminders.mjs --once

# Последовательные проверки каждые 60 секунд; остановка Ctrl+C.
node scripts/dispatch-reminders.mjs

# Проверки каждые 30 секунд.
ARTEL_REMINDERS_INTERVAL_SECONDS=30 node scripts/dispatch-reminders.mjs
```

| Переменная | Назначение |
| --- | --- |
| `ARTEL_REMINDERS_URL` | Полный адрес `/api/push/dispatch`; HTTP разрешён только для localhost, `127.0.0.1` и `::1`, другие адреса требуют HTTPS. |
| `ARTEL_REMINDERS_INTERVAL_SECONDS` | `30` или `60`, по умолчанию `60`; влияет только на непрерывный режим. |
| `ARTEL_REMINDERS_TIMEOUT_SECONDS` | Тайм-аут запроса, 1–65 секунд; по умолчанию `65`. |
| `CRON_SECRET` | Секрет из окружения API. В журнал не выводится. |
| `ARTEL_REMINDERS_SECRET_FILE` | Вместо `CRON_SECRET`: файл, содержащий только секрет. |

Запросы одного процесса не пересекаются. Ошибка в непрерывном режиме записывается в журнал, затем выполняется следующая проверка; `--once` сразу завершается с кодом 1. Если запрос длится дольше интервала, следующая проверка начнётся после его окончания. Сервер самостоятельно управляет повторной доставкой и защищает действующие отправки от параллельных вызовов.

Успешная строка журнала содержит время, длительность и `checked/sent/failed/expired`. `sent` означает принятие push-сервисом, а не подтверждение показа на устройстве. `expired` означает удалённые недействующие подписки. Сам `lastRunAt` в CRM подтверждает начало серверной проверки; успешный ответ runner подтверждает её завершение. Каждый проход обновляет heartbeat и сохраняет хранилище API.

## Шаблоны systemd для будущего размещения

Это заготовки, их копирование в репозиторий ничего не включает. Для systemd 247+ подготовьте отдельный `/etc/artel-reminders/runner.env` с явным `ARTEL_REMINDERS_URL=http://127.0.0.1:5173/api/push/dispatch` и `/etc/artel-reminders/cron-secret` с секретом. Каталог и секрет должны принадлежать root, права `0700` и `0600` соответственно. Не записывайте секрет в `runner.env`: служба передаёт его через `LoadCredential`.

При будущем размещении скопируйте runner в `/usr/local/libexec/artel-dispatch-reminders.mjs`, проверьте путь `/usr/bin/node` и конфигурацию API. Затем проверьте шаблоны через `systemd-analyze verify`, установите service/timer и только после отдельного решения включите timer. До создания обязательных файлов конфигурации service не запустится. Таймер вызывает `--once` каждую минуту; настройка интервала runner на него не влияет. Если понадобится 30 секунд, отдельно измените `OnCalendar` таймера.

Для проверки работы используйте `systemctl list-timers artel-reminders.timer` и `journalctl -u artel-reminders.service`. Нужны несколько последовательных автоматических успешных запусков, затем проверка уведомления на устройстве. Изменение адреса в конфигурации само по себе не меняет интервал, показанный в интерфейсе CRM.
