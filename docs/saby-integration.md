# Рейсы → Saby: реализованный этап и подключение

**Обновление 29.09.2026 по новому решению Мустафы:** историческая ЭТрН №7 Олега разрешена как эталон локального воспроизведения. Новый рейс и актуальность старого профиля не блокируют эти тесты; запрет дублирования в рабочем учёте/Saby сохраняется. Локальный первый титул 1110339 и сравнение XML/PDF уже подготовлены: [результат и повторный запуск](saby-etrn-replay-2026-09-29.md). Доступ повторно не запрашивать, Дениса исключить. Ниже сохранён контекст предыдущих этапов; ограничения новой рабочей отправки не переносить на локальный тест.

Дата: 28.09.2026. Серверный адаптер создаёт **формализованный черновик заказа на перевозку** (`TransportOrder`, титул грузоотправителя КНД `1110361`, версия `5.01`) на каждую клиентскую строку рейса. Сохранение черновика в Saby и отправка подписанного документа перевозчику — разные этапы. Текущий код не вызывает подписание, не отправляет документ от имени водителя, не формирует печатные документы CRM и не объявляет завершённым обмен с ГИС ЭПД.

**Доступ для чтения подтверждён 28.09.2026:** после передачи доступа выполнены явный вход в отдельные кабинеты Артэль и НК Артэль, чтение собственных организаций и ЭТрН №7 с компьютера и production-сервера. XML первого титула совпал с сохранённым образцом. Конфигурация на сервере пока подготовлена отдельно от runtime; создание нового черновика и полномочия подписания не проверены. [Отчёт и оставшиеся шаги](saby-access-verification-2026-09-28.md). Автотесты ниже по-прежнему используют синтетический API.


## Рабочий путь ЭТрН — новое поручение 29.09.2026

Добавлен самостоятельный `ConsignmentNote` первого титула 1110339 v5.01: сохранённый рейс → выбранная клиентская доставка → редактируемая подготовка → проверка → запись в Saby → отдельное чтение → ссылка для подписи → повторное чтение статусов и файлов. Старый TransportOrder остаётся отдельным типом; кнопка ЭТрН его не создаёт. Фактический результат выпуска и границы живой приёмки фиксируются в [отчёте нового релиза](../ops/production/etrn-release-2026-09-29.md).

Текущий рабочий сценарий: грузоотправитель Артэль, перевозчик НК Артэль; это явные роли из проверенных кабинетов. В рейсе должна быть выбрана Артэль. Другую организацию нельзя молча заменить ролью из банковского счёта. Получатель берётся из выбранной доставки. До отправки пользователь подтверждает её массу отдельно от расчётной доли рейса, сведения груза, опасность, грузоподъёмность/вместимость, основание владения, роли погрузки, фактические времена и сведения подписанта. Исторические значения №7 не подставляются в новую перевозку.

Дополнения сохраняются отдельно в `operations.etrn`; финансовые строки не изменяются. Снимок подготовки сверяется повторно перед отправкой: изменения рейса/справочника требуют повторного сохранения. До сети сохраняются ID попытки, уникальная метка, снимок, хеш и аренда. ID Saby сохраняется перед чтением результата. `unknown` никогда не разрешает повторную запись: используется поиск существующего документа. Переданная или потенциально переданная ЭТрН блокирует изменение/удаление рейса.

API требует раздела «Рейсы» и доступа ко всем строкам рейса:

- `GET /api/shipment-trips/:id/etrn` — сведения подготовки и состояние доставок.
- `PUT /api/shipment-trips/:id/etrn` с `{shipmentId,profile}` — сохранить и проверить.
- `POST /api/shipment-trips/:id/etrn/submit` с `{shipmentId}` — создать/сверить один документ; повтор подтверждённого создания не пишет заново.
- `POST /api/shipment-trips/:id/etrn/refresh` — получить актуальные сведения; после неизвестного результата сначала искать прежнюю запись.
- `GET /api/shipment-trips/:id/etrn/xml/:shipmentId` — скачать подготовленный неподписанный XML.
- `GET /api/shipment-trips/:id/etrn/files/:shipmentId/:fileId` — скачать возвращённый Saby XML/PDF/подпись/архив через серверную сессию. Байты сохраняются приватно с SHA-256, версией и проверкой прав; токены и временные ссылки файлов браузеру не передаются.

В runtime включаются существующие credentials и текущие реквизиты двух кабинетов. `SABY_TRANSPORT_PROFILE_JSON` для нового пути не нужен: подготовка каждой ЭТрН доступна в интерфейсе. Телефоны, которых нет в ответе организаций Saby, пользователь подтверждает в форме. Отсутствующие идентификаторы ЭДО заполняет Saby при подготовке действия согласно своему API; окончательные байты перед подписанием могут отличаться от предварительного XML CRM.

Реально найденная КЭП Артэль — клиентская. Подписание выполняет её владелец по ссылке документа в Saby с доступным носителем; логин/пароль не заменяют ключ. Первое действие отправителя в TMS API — «Погружен» на этапе отправки, после фактической погрузки. CRM не выполняет его без владельца. После подписи нажать «Обновить из Saby». Сведения о подписи, состоянии Saby и идентификаторе ГИС показаны раздельно. Наличие данных подписи не означает локальной криптографической проверки либо завершения всех этапов. [Официальные источники, проверка сертификатов и ограничения](saby-signing-api-2026-09-29.md).

Действия перевозчика/получателя выполняют их уполномоченные участники в Saby/ЭДО. Список сертификатов текущего пользователя в кабинете НК пуст; сертификаты других сотрудников этим не исключаются. Новая перевозка и следующие титулы никогда не создаются копированием подписей старой №7.

Ниже сохранён контракт предыдущего этапа TransportOrder; его прежние ограничения не отменяют новое поручение и отдельную реализацию ЭТрН.

- [Официальный формат 1110361](https://formats.saby.ru/edo/trucking/130957?version=130957) и его публичная XSD скачаны 28.09.2026. [Схема для проверок](../tests/fixtures/saby/transport-order-1110361-5.01.xsd), [происхождение и SHA-256](../tests/fixtures/saby/README.md). - [Запись документа](https://saby.ru/help/integration/api/all_methods/doc) может сохранить черновик с ошибкой. Поэтому одного `HTTP 200` или полученного ID недостаточно.
- После записи вызывается [чтение документа](https://saby.ru/help/integration/api/all_methods/read_doc): сверяются тип, участники, метка запроса, наличие формализованного вложения и отсутствие замечаний. ID сохраняется до чтения, чтобы ошибка проверки не потеряла связь.
- Неопределённый результат сверяется через [список документов](https://saby.ru/help/integration/api/all_methods/list_doc): фильтр по уникальному номеру заказа, дате и отправителю, затем точное совпадение сохранённой метки. Отсутствие совпадений не разрешает повторно создавать документ.

## Рейс, клиенты, заказ и будущая ЭТрН

Выбрано соответствие **одна клиентская строка → один заказ** с пунктами погрузки и доставки этой строки. Один рейс хранит несколько связанных заказов. Это выбор текущей реализации для независимого результата каждой доставки, а не ограничение Saby: формат допускает повторяемые `АдрПункт`/`ОпГруз`; в предоставленном заказе есть две выгрузки. Чужие клиентские строки не включаются в XML отдельной доставки.

Заказ создаёт настроенная Артэль, получатель заказа — настроенная НК Артэль. Клиент доставки записан в дополнительной информации к заказу; роль перевозчика не подменяется клиентом. Данные водителя и выбранной машины передаются как плановые дополнительные сведения. Формальное подтверждение перевозчиком (титул `1110362`) — отдельный этап. ИНН/ВУ водителя не являются обязательным полем первоначального титула `1110361`, поэтому по ним нельзя блокировать создание этого заказа.

ЭТрН (`ConsignmentNote`) не создаётся этим действием. Будущая связь «заказ — утверждение перевозчика — ЭТрН — этапы участников» остаётся отдельной задачей. Основание текущего состава данных и отличия плановых/фактических событий описаны в [разборе образца Олега](saby-etrn-sample-2026-09-15.md).

## Данные и проверка готовности

XML использует снимок сохранённого рейса и справочников. Адреса площадок берутся из снимка `loading_address` / `unloading_address`; юридический адрес получателя не подставляется вместо площадки. `loading_planned_at` означает плановую подачу машины/погрузку в Москве (`+03:00`), время доставки необязательно. Фактические события не выдумываются и не заменяют плановые. Литры делятся на 1000 для м³, тонны умножаются на 1000 для кг; округление ради соответствия схеме запрещено. Например, объём `8001 л` не представляется точно с двумя знаками м³ и требует уточнения процесса/формата вместо скрытого округления.

Проверяется общая загрузка машины по всем клиентам: объём и масса рейса должны укладываться в подтверждённые вместимость и грузоподъёмность. Значение полной массы машины 442 **27,9 т** не используется как грузоподъёмность.

Обязательные дополнительные данные формата задаются подтверждённым профилем на сервере. Профиль не заполняется автоматически из старой накладной. До его настройки UI показывает конкретные группы недостающих данных: телефон и ID ЭДО каждой организации, сведения составителя/подписанта, транспортное описание продукта, упаковка/места, метод определения массы, габариты, опасный груз, грузоподъёмность и вместимость именно выбранной машины. Нулевые габариты и отсутствие опасности допустимы только как явно подтверждённые значения. Формат требует сведения подписанта внутри XML; это не криптографическая подпись и не подтверждение полномочий.

Поддерживаются функции `Заказ` и `Заявка`. Для заявки обязателен явно подтверждённый профиль `contract` с названием, номером, датой и ИНН составителей договора организации перевозки; они попадают в `Документ/ДогОргПрвз`. Файл договора не прикладывается. Полномочия по МЧД/бумажной доверенности с кодами `3`/`5` сейчас не поддерживаются: не подставлять вместо них другие коды, нужно расширить проверенный сценарий. Два сохранённых договора остаются приватными и не загружаются автоматически.

## Защита от повторов и восстановление

`operations.saby.trips[tripId]` хранит по каждой доставке ID и редакцию Saby, статус, время, неизменный снимок и его SHA-256, уникальную метку и номер попытки. Клиенту возвращается только безопасная сводка; снимки/телефоны/профиль не раскрываются через endpoint статуса.

Перед сетью атомарно сохраняются снимки и аренда обработки на пять минут. Сетевые запросы выполняются вне файловой блокировки, записи результата — короткими транзакциями. Второе нажатие при активной обработке получает `409`. Доступ сотрудника повторно проверяется перед каждым документом и перед возвратом ответа. Уже полученный ID сохраняется даже при отзыве прав.

- `pending`: запрос выполняется; истёкшая аренда отображается как `unknown`.
- `draft`: отдельное чтение подтвердило созданный формализованный черновик; повторного создания нет.
- `unknown`: таймаут, неопределённый ответ записи, несогласованный read-back или потеря подтверждения. Разрешена только сверка; автоматическое создание заново запрещено, даже если список пока пуст.
- `error`: запрос создания точно не выполнялся либо был однозначно отклонён до обработки; можно исправить данные/доступ и повторить.

Рейс с существующей или возможной записью Saby защищён от редактирования/удаления, чтобы не менять уже переданные данные. Старые снимки сохраняются при изменениях справочника. Авторизация и полный профиль текущих полей нужны для нового заказа; для сверки неизвестного результата достаточно действующего серверного доступа, используются исходные участники и снимок.

## Серверная конфигурация

Секреты устанавливаются только в защищённом серверном окружении, без префикса `VITE_`. Авторизация: `SABY_LOGIN`, `SABY_PASSWORD`, `SABY_ACCOUNT_NUMBER` либо готовая `SABY_SESSION_ID`. Вход рабочего адаптера по логину без выбранного кабинета запрещён во избежание случайного использования последнего кабинета пользователя.

При первичной настройке доступные кабинеты можно определить отдельной временной сессией через официальный [СБИС.СписокАккаунтов](https://saby.ru/help/integration/api/all_methods/list_of_acc), после чего явно авторизоваться в нужном кабинете. Такая сессия обнаружения не используется для записи документов.

В локальном исправлении после живой проверки добавлен `SABY_CARRIER_ACCOUNT_NUMBER`: для отдельного кабинета перевозчика проверка его собственных организаций использует отдельную сессию и те же предоставленные логин/пароль. Сессия заказчика туда не переносится; при отсутствии логина/пароля проверка завершается ошибкой конфигурации. Если отдельный кабинет не задан или совпадает с основным, сохраняется прежняя проверка одного кабинета. Запись, чтение и сверка заказов остаются в основном кабинете Артэль. Изменение ещё не опубликовано в образе `20260928-trips-saby-0df0a84`.

Подготовленный `/opt/artel-crm/secrets/saby.pending.env` (`0600`) не входит в Compose `env_file`; его наличие не активирует интеграцию. До активации нужны проверенный профиль нового рейса и совместимый релиз. В текущем коде нет отдельного переключателя режима read-only: диагностические проверки выполняются отдельным процессом с разрешённым списком методов чтения, без обращения к `OperationsStore`.

Для каждой роли нужны `SABY_CUSTOMER_INN`, `SABY_CUSTOMER_KPP`, `SABY_CUSTOMER_NAME`, `SABY_CUSTOMER_ADDRESS`, `SABY_CUSTOMER_PHONE`, `SABY_CUSTOMER_EDO_ID`; аналогичный набор с префиксом `SABY_CARRIER_`. Номера участников из исторического XML не считаются подтверждёнными текущими ID кабинета.

`SABY_TRANSPORT_PROFILE_JSON` содержит:

Для опасного груза нужен объект со строками `unNumber`, `shippingName`, `class`, `classificationCode`, `packingGroup`, `hazardSign`, `tunnelCode` из документов конкретного продукта. Коды полномочий, упаковки, массы и признаки выбираются по подтверждённым фактам и формату.

До первого создания: настроить доступ; выполнить read-only `СБИС.СписокНашихОрганизаций` и `СБИС.ПрочитатьДокумент` существующей накладной №7 с реальным ID; сверить кабинет и роли; заполнить подтверждённый профиль; выбрать новый действительный рейс. Старый комплект №7 не воспроизводится как новая перевозка. Проверка полного обмена с перевозчиком потребует отдельного этапа подписания в Saby.

## Проверки

`npx tsx --test tests/api-saby.test.ts` проверяет XML официальной XSD через `xmllint`, точность единиц, обязательные поля, синтетическую передачу нескольких доставок, блокировки/двойное нажатие, чтение результата, сохранение/перезапуск, таймаут/неопределённый результат, истёкшую сессию, отказ доступа, ошибки внутри HTTP 200, отсутствие секретов и отзыв доступа во время обработки. Все хранилища временные, сведения синтетические, реальный API не вызывается. Системный `xmllint` нужен только тестам, не рабочему серверу.

`npm run test:trips-saby-ui` проверяет браузер → HTTP API → настоящий адаптер → временное хранилище с подменённым внешним транспортом: отдельные кабинеты, двойное нажатие, чтение черновиков, повтор без дублей и восстановление после потерянного ответа. `npm run test:trips-ui` покрывает редактор, конфликты, права и мобильную вёрстку. Оба набора используют синтетический снимок и не читают рабочее хранилище. [Результат проверки 29.09.2026 и границы реального обмена](trips-saby-check-2026-09-29.md).

Оставшиеся водительский интерфейс, QR/уведомления, зарплата, счета/УПД/1С, полный цикл подписания и договорные сценарии сохранены в [backlog handoff](trips-saby-implementation-handoff-2026-09-28.md#сохранить-на-следующий-этап-сейчас-не-реализовывать).
