# Подтверждение водителя и очередь Saby — 08.10.2026

## Задача и причина задержки

Пользователь попросил выделить подтверждение водителем в самостоятельный второй этап перед отправкой АРТЭЛЬ и привести название во всём интерфейсе к «Артэль / АРТЭЛЬ» (написание через «Э» подтверждено явно).

Чтение production для заявки №20, рейса №13, показало: водитель зафиксировал прибытие в 08:14:51 МСК и подтвердил массы/убытие в 08:14:58. Данные были сохранены. Прежний планировщик последовательно обрабатывал все рейсы, пропускал новые минутные проходы, пока предыдущий не закончился, и не получал немедленного сигнала после «Убыл». Заявка №20 дошла до проверки только в 08:20:18; запись массы и обратное чтение были подтверждены к 08:20:48. После этого Saby принял запрос отправителя, но подпись оставалась в ожидании. Таким образом, первоначальная задержка очереди CRM и последующее ожидание подписи Saby — разные причины.

Диагностика не повторяла Write/Prepare/Execute и не создавала документов. Прежняя надпись «ожидаем водителя» также могла отставать от уже сохранённых событий водителя.

## Изменения

Семь видимых этапов: подготовка → подтверждение водителя → отправка АРТЭЛЬ → водитель и машина → подтверждение НК → создание ЭТрН → отправка клиентам. Завершение второго этапа и его московское время берутся только из принятого действия водителя «Убыл», с проверкой текущего состава доставок и назначенного водителя. Факты погрузки старых рейсов сами по себе не становятся подтверждением водителя. Событие водителя не объявляется электронной подписью Saby.

API добавляет читаемое `driverConfirmation`; бизнес-формат завершения обмена `stage6CompletedAt` остаётся прежним. Для уже подтверждённых данных при отставшем workflow интерфейс показывает ожидание обработки, а не ожидание водителя.

Планировщик запускает рейсы независимо; общий FIFO допускает до четырёх полных сетевых запросов Saby одновременно, включая получение тела ответа. Минутный проход больше не ждёт полного завершения всех обменов. Успешно сохранённое «Убыл» немедленно сигнализирует планировщику, используя прежнее поручение сотрудника. Повторные сигналы объединяются. Новые права и поручения от имени водителя не создаются; старые рейсы без включённой автоматизации не подключаются автоматически.

Параллельные рейсы и ручные запросы используют общий кеш авторизации с раздельными сессиями отправителя и перевозчика. Одновременная авторизация одного аккаунта объединяется; запоздалый HTTP 401 старой сессии не сбрасывает уже обновлённую сессию. Это необходимо с учётом [лимита пяти активных сессий Saby](https://saby.ru/help/integration/api/sequence/auth) и [лимита пяти параллельных потоков](https://saby.ru/help/integration/api/techreq_edo).

Проверки прав, lease и отметка отправки выполняются после получения сетевого слота. Начатые workflow дожидаются завершения при остановке сервера; очередь уже начатых запросов не отменяется. Новый внутренний предел завершения — 600 секунд. При данном выпуске Compose вызывается с `--timeout 600`; для будущих выпусков необходимо сохранять такой же срок ожидания. Серверный `compose.yaml` этим выпуском не меняется.

Для ручных маршрутов старого Saby/ЭТрН также добавлена свежая проверка полномочий и точной действующей lease после очереди. Подготовленная ЭТрН проверяет собственную дочернюю lease; скачивание — права, прежний документ, редакцию и вложение. Все эти guards наследуют общий кеш сессий и сетевой лимит.

Текст мониторинга объясняет, что CRM проверяет данные водителя и Saby в фоне. Минутный интервал — период запуска проверки; ответ Saby может занимать больше времени. Отображаемая дата названа «Последняя успешная проверка Saby».

Название исправлено в интерфейсе, формах, карточках банков, проверках формы и системных уведомлениях. Названия собственных организаций из ответа выбора подписей приводятся к нужному написанию только при отображении. Идентификаторы, юридическое содержимое XML, исходные банковские назначения платежа и хранимые деловые данные не переименовываются.
