# Рейсы №52/54: маршрут исправления этапа 6 — 01.11.2026

Это анализ кода и предложение исправления для нового чата Ultra. Production-код, данные CRM/Saby и ключи этим анализом не менялись. Тесты исправления ещё не выполнялись: исправления пока нет.

## Подтверждённая причина

Диагностический агент прочитал coherent core в 13:26:11 МСК и Saby в 13:27:39 МСК. Оба проблемных рейса уже используют новый протокол `orderConsignmentCreationVersion=2`; это **не** прежняя проблема старых записей №47–49 без v2.

| Рейс CRM | Заявка Saby | Существующая нативная ЭТрН | Зафиксированная дата перевозки | Дата документа Saby |
|---|---|---|---|---|
| №52 | №50, `f7e9fe7a-2914-4bed-8dd0-471bff8f472b` | №51, `47e686d6-2db0-452e-9093-4453b09daa93` | 30.10.2026 | 01.11.2026 |
| №54 | №51, `fe1ae7cd-1d2b-4b45-9554-1fc06667623f` | №52, `68b2ff15-0962-41ca-af97-2f4b5cf41bf3` | 31.10.2026 | 01.11.2026 |

По provider-чтению каждая заявка имеет ровно одну взаимную точную связь с указанной ЭТрН (ID, тип, номер и дата ссылки). Обе ЭТрН — неподписанные черновики: состояние `0`, один T1, подписи отсутствуют, не удалены, не частичны. У CRM-попыток `id=null`, `linkedDraft` отсутствует, `reservationAttempted=false`, `uploadAttempted=false`: ошибка возникла **до** привязки или записи нативной ЭТрН. У №52 две доставки, вторая ещё не обрабатывалась; у №54 одна.

Код в `etrn-linked-draft.ts:116–119` ошибочно требует равенства даты существующего документа Saby и `doc.snapshot.fields.date` (дата перевозки). Остальные условия этого guard проверяют реальную идентичность. Общий текст ошибки скрывает точный неуспешный предикат: «Не подтверждена однозначная связь существующей ЭТрН с этой заявкой.»

После этого `etrn-service.ts:883` сохраняет `status=error`, поскольку ещё нет ID/намерения создания; `trip-saby-workflow.ts:589` переносит ошибку в workflow. `trip-saby-scheduler.ts:42–56` не выбирает `phase=error`. Поэтому исправленный код сам по себе не гарантирует возобновления этих двух уже остановленных рейсов.

Успешный контроль №51: `phase=completed`, CRM создала ЭТрН №50 по ветке `nativeDraftEnabled=false`, дата совпала с датой перевозки. Он не проверяет проблемный путь более позднего нативного документа. №45/47–49 уже завершены по свежей проекции; №55 ждёт водителя без этой ошибки.

Приватные доказательства: `.local/stage6-handoff-20261101/diagnosis/projection.private.json`, `provider-read.jsonl` и proof-файлы рядом. Полный frozen snapshot содержит персональные данные; в Git или handoff-текст его не копировать. Подробный диагноз — `docs/stage6-diagnosis-2026-11-01.md`.

## Предпочтительное исправление

1. Ввести явное различие **даты перевозки** из неизменяемого snapshot и **даты конкретной ЭТрН**, подтверждённой по нативному документу. Не менять `snapshot.fields.date`, даты/байты подписанной заявки, факты погрузки/убытия, массы, литры, адреса или клиентов ради прохождения проверки.
2. Для нативного документа закреплять дату ЭТрН только вместе с доказанной идентичностью: точная взаимная связь с принятой заявкой, единственный кандидат, неподписанный текущий T1, точные стороны, исходная редакция и полный XML. `metadata.Дата`, дата в ссылке и `T1.ДатаТрН` должны быть согласованы. Зафиксировать эти доказательства до записи и повторно проверить перед ней. При конфликте metadata/XML или неподтверждённой связи блокировать запись с конкретной причиной.
3. Согласованно использовать эту закреплённую дату в начальной проверке, распределении нативного черновика, построении/проверке ожидаемого T1, проверке metadata при sender/carrier signing и последующем refresh. Возможно расширить существующий `LinkedDraftState.documentDate` и добавить единый helper/явную опцию сериализатора; точный дизайн выбирает новый чат после чтения XML. Не клонировать snapshot с подменённой датой в разных местах без явной модели и проверки происхождения этой даты.
4. Ограничить новую ветку доказанным нативным ordinary-документом. Старые/direct/CRM-created документы сохраняют прежние правила, если отдельный тест не выявит необходимость иного изменения. Не использовать текущую дату сервера вместо фактической даты документа и не вводить произвольное разрешение расхождения на N дней.
5. Разбить общий guard на причины, например `native_document_date_mismatch`, `native_xml_date_mismatch`, `reciprocal_link_mismatch`, `multiple_linked_notes`. В UI показывать короткое понятное сообщение, а в приватном доказательстве — конкретный предикат и идентификаторы. Не выводить полные XML, сертификаты, download URL или персональные данные в обычный лог.
6. После исправления и свежей сверки адресно продолжить **сохранённые** попытки №52/54 на текущих ЭТрН №51/52, через штатную проверяемую цепочку и действующее разрешение. Не сбрасывать attempt/grant/prepared, не создавать замену этим существующим документам. Для второй доставки №52 отдельная ЭТрН допустима только после успешного распределения первой и свежего доказательства отсутствия своей прежней попытки/документа. Переход старого `phase=error` должен быть адресным, идемпотентным и защищённым CAS; не включать все ошибки в бесконечные автоматические повторы.

Если XML или реквизиты native не соответствуют frozen перевозке помимо отдельно подтверждённой даты документа, автоматическая привязка запрещена. Тогда задача распадается на конкретную коррекцию бизнес-сведений/операторского документа; не ослаблять остальные проверки ради завершения.

Отдельная связанная неточность UI остаётся в `trip-saby-workflow.ts:307`: наличие `autoAuthorization` даёт текст «CRM продолжит обмен в фоне», хотя `phase=error` выключает мониторинг на строке 287. Исправить сообщение согласованно с фактическим состоянием; не маскировать блокер зелёным этапом.

## Воспроизведение и приёмка нового рейса

Нужны проверяемые before/after сценарии **именно этого дефекта**, а не только рост общего числа тестов. Fixtures должны воспроизводить форму реальных ответов, но содержать синтетические ИНН/персональные данные/байты.

1. Native T1 появляется позже даты перевозки: два кейса формы №52 (две доставки, дата 30.10 → документ 01.11) и №54 (одна, 31.10 → 01.11). На исходном production source они должны давать наблюдаемую ошибку. После исправления пройти от новой заявки с водительскими фактами через появление native note до обеих подтверждённых подписей и передачи соответствующему клиенту, без вмешательства helper в середине сценария.
2. Новый рейс с датой перевозки сегодня и нативным документом завтра, включая переход месяца/года и полночь МСК. Закреплённая дата документа остаётся прежней при дальнейшем перезапуске/другой дате системных часов.
3. Native отсутствует → safe v2 creation по нынешнему протоколу; native появляется между двумя чтениями → нет конкурентного дубля. Native появляется на позднем проходе → корректная привязка того же ID. Для №52 первая native ЭТрН сохраняет свой ID, вторая delivery получает не более одного собственного ID после полной проверки.
4. Несовпадение metadata/XML даты, неверная дата ссылки, посторонняя заявка, два candidates, неполные links, чужие стороны/получатель, изменённые масса/литры/адрес/водитель/машина, signed/non-draft T1 или другая редакция: 0 provider writes и 0 новых документов. Новый date policy не превращает эти ошибки в успех.
5. Сохранённые before/filled bytes, номер, дата документа, source-order ID и allocation остаются точными после restart. Потеря ответа записи, ошибка durable intent, остановка процесса и повторная сверка не повторяют write/Prepare/Execute; не теряется журнал исходных попыток. Изменение даты или редакции после подготовки подписи останавливает цепочку.
6. Pause/revoke прав до следующего запроса и на очереди network budget запрещают этот запрос. Старые completion/identity/signature доказательства сохраняются. Concurrent manual refresh/scheduler не создают второй workflow/lease/document.
7. UI отображает реальный этап 6/7, конкретную ошибку и состояние автопроверки без противоречия. Обычный этап 6 — «Создание ЭТрН»; историческое поле `stage6CompletedAt` обозначает завершение нынешнего этапа 7. Direct этап 6 означает другое — передачу клиентам.

Опорные тесты текущей базы: `tests/etrn-linked-draft.test.ts` (86, 169, 178, 198, 213, 406, 429, 443), `tests/etrn-linked-draft-addressing.test.ts`, `tests/saby-consignment-draft.test.ts`, `tests/etrn-order-creation.test.ts` (166, 184, 195, 206), `tests/etrn-order-discovery.test.ts`, `tests/saby-consignment-dispatch.test.ts`, `tests/trip-saby-scheduler.test.ts`, `tests/api-trip-controls.test.ts`. Сохранить отрицательные проверки; нынешний тест `etrn-linked-draft.test.ts:188` меняет дату только в metadata при старой дате ссылки, это **не** тот же положительный сценарий согласованного более позднего native документа.

## Завершение в новом чате

Пользователь поручил исправление локально/на сервере, commit и push, затем полный аудит. Для выпуска сохранить чужие изменения, получить fresh server source/manifest, проверить пакет и Git exact, выполнить lint/TS/build, применимые API/unit/security/regression/UI проверки, оба Linux-образа, копию актуального store с запретом внешних запросов, backup, HTTPS и авторизованный read-only production UI. Коммит/push сверенного кода должны предшествовать server build/switch согласно актуальному порядку проекта.

После восстановления каждого affected рейса проверить отдельно: те же существовавшие order/ETRN ID, точные frozen business facts, обе выбранные подписи, точные подписанные T1/T2, назначение следующего этапа именно своему клиенту. Передача клиенту не означает его подпись T3. Полный preservation audit должен включать все 15 fact-коллекций, `tripExchangeControls`, accounts/права, documentArchive, business records банков, существующие Saby документы/гранты/подготовленные байты и историю, ключи, worker и соседние сервисы. Непонятные дельты не списывать автоматически на фон; сохранить raw и прежние `globalReviewed=false`/`preservationReviewRequired=true`.

Создание нового реального тестового рейса для проверки не требуется: пользователь попросил доказать отсутствие повторения при создании нового рейса, это сначала полный синтетический сценарий нового рейса и изолированный runtime. Не создавать фиктивный реальный перевозочный документ. Финал честно отделяет воспроизведённые/устранённые ошибки, реальный результат №52/54, синтетическую проверку нового рейса и ещё не проверенное поведение провайдера.

На момент подготовки этого предложения XML T1 №51/52 диагностический агент ещё не скачал. Metadata mismatch и место остановки доказаны; согласованность XML даты и всех бизнес-якорей, возможность пройти последующие guards и реальное завершение пока неизвестны. Это обязательная первая read-only проверка в новом чате или дополнение диагностики до передачи.
