# Яндекс: метод остатка; ЛУКОЙЛ: самостоятельное подключение доступа

Проверено 12.10.2026, 12:43 МСК. Продолжение [отчёта по natcar и доступам](natcar-three-accounts-and-provider-access-2026-10-12.md). В этом продолжении код приложения и production не менялись, обращения не отправлялись, VPN/прокси/DNS не менялись.

## Яндекс — точный результат дополнительного поиска

Кнопка «Документация» в авторизованном профиле компании открыла https://taxi__business-api.docs-viewer.yandex.ru/ru/. Проверены полный опубликованный справочник, SDK-разделы Client/BudgetManager/TankerManager и исходники официального Python SDK `yandex-b2b-go` версии 1.0.4 — текущей версии PyPI на момент проверки. Wheel прочитан как ZIP без установки/исполнения; SHA-256 `e512f7b21e98ee86557e706e086ec351ab1c012e6635bb6465442d3c20b1efc7` совпал с PyPI. В Python-файлах нет `balance`; TankerManager предоставляет список операций `orders/tanker`, BudgetManager — лимиты. Поддерживаемый OAuth-метод текущего остатка договора в этих источниках не найден. Это не доказательство отсутствия отдельно подключаемого API.

В публичном JavaScript действующего веб-кабинета найден конкретный запрос:

```http
GET https://b2b-api-lk.go.yandex.ru/corp-cabinet/3.0/contracts/list
X-YaTaxi-Selected-Corp-Client-Id: <id компании>
```

Модуль договоров вызывает `contracts/list` версии `3.0`. Преобразователь групп лицевых счетов читает `balances.balance`, `receipt_sum`, `available_funds`, `overdraft_limit`, `overdraft_balance`, `reduced_balance`. Транспорт использует auth-proxy и `credentials: include`: это браузерная сессия. Доступность этого запроса с интеграционным OAuth не установлена; предыдущая серверная проверка с сохранённым OAuth вернула 401, тогда как `/integration/2.0/auth/list` вернул 200 и нужную компанию. Повторный выпуск токена не требуется. Cookies браузера не переносились.

Основание: публичные файлы `yandex-app-3740.js` и `yandex-app-8462.js`, сохранённые на сервере в `/opt/artel-crm/private/cabinet-adapters-20261012/`. Это анализ клиентского кода, не успешное серверное чтение остатков. Отдельный серверный вход ранее не завершился получением сессии после подтверждения пользователя — нельзя считать браузерную авторизацию серверной.

Свежий авторизованный Chrome показывает:

- Договор «Заправки» 43207794/25: 10 488,94 ₽.
- Договор 43207806/25: Яндекс Go 0 ₽, отсрочка 2 000 ₽.
- «Всего средств»: 12 488,94 ₽. Эта сумма включает отсрочку и не должна автоматически записываться как собственный остаток «Заправок».

На странице есть предупреждение о технических работах; причинная связь с API-ошибкой 401 не установлена. Раздел «Заправки» открывает каталог цен АЗС, дополнительного API-доступа в нём не обнаружено.

Следующий необходимый результат — поддерживаемая серверная авторизация к методу остатков либо OAuth-аналог от Яндекса. Подключение баланса в CRM остаётся незавершённым.

### Точный текст вопроса поддержке Яндекса — не отправлен

> Настраиваем чтение текущего остатка договора «Заправки» 43207794/25 ООО НК АРТЭЛЬ в собственной серверной CRM. OAuth из «Профиль компании → Интеграция по API» работает: GET /integration/2.0/auth/list возвращает 200 и нашу компанию. Веб-кабинет использует GET https://b2b-api-lk.go.yandex.ru/corp-cabinet/3.0/contracts/list, однако этот метод возвращает 401 с интеграционным Bearer-токеном. Какой поддерживаемый метод и тип авторизации доступны для серверного чтения balance/available_funds по договору? Есть ли OAuth-аналог или отдельный доступ API Заправок? Нужны собственные средства отдельно от отсрочки, без зависимости от браузера сотрудника. Просим передать вопрос специалистам API.

## ЛУКОЙЛ — действия пользователя

1. После окончания текущей работы открыть https://lk.licard.com/ с теми сетевыми настройками, при которых кабинет работает. VPN пользователь переключает самостоятельно. Если доступ с компьютера остаётся закрыт, можно обратиться к своему менеджеру с телефона — вход в кабинет не обязателен для запроса API.
2. Указать ООО «НК АРТЭЛЬ», договор RU260007461. Через раздел «Поддержка», если он доступен, либо своего менеджера ЛИКАРД отправить текст ниже.
3. Получить документацию и подтверждение доступа к текущему остатку именно этого договора. Не путать выгрузку операций с методом остатка.
4. Передать в этот чат ответ менеджера, документацию или скриншот параметров без секретов. Если выдан сертификат/ключ — сообщить только факт выдачи; его установку выполнить отдельным защищённым способом, не прикладывать `.p12` и пароль к сообщению.

### Запрос менеджеру ЛИКАРД — не отправлен

> Просим подключить API для чтения текущего денежного остатка договора RU260007461 ООО «НК АРТЭЛЬ» из нашей серверной Artel-CRM. Нужны актуальная документация, адрес сервиса, метод остатка и схема авторизации. Уточните, выдаётся ли клиентский сертификат .p12 с паролем либо используется другой способ, и требуется ли разрешить исходящий IP нашего сервера 130.49.151.239. Просим доступ только на чтение, без платежей и управления картами/лимитами. Веб-сайт с сервера возвращает 403 до входа; нужен поддерживаемый API, доступный с сервера.

Публичная инструкция действующего интегратора Fort Monitor для ЛИКАРД прямо описывает получение через менеджера номера контракта, адреса API, сертификата `.p12` и пароля. Это конкретный ориентир для обращения, но не подтверждение схемы/условий по договору Artel и не документация метода остатка. Пункт «API на чтение» с ClientID/ClientSecret на той же странице относится к ППР, а не к ЛИКАРД.
