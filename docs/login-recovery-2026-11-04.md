# Восстановление входа — 04.11.2026

По поручению «исправь» со скриншотом ошибки входа восстановлена доступность production CRM. `502` с пустым телом воспроизведён по HTTPS; разбор этого ответа формой давал `Unexpected end of JSON input`.

## Причина и изменение

Контейнер `artel-crm-crm-1` многократно завершался с кодом 134. В журнале — `Reached heap limit / JavaScript heap out of memory`, в том числе при JSON.parse/создании строк. На диагностике наблюдалось 30 перезапусков, на сохранённом baseline — 32. Действовал V8 old-space 640 MiB при лимите контейнера 1 GiB. Свободного диска достаточно; на хосте 4 GiB RAM и 2 GiB swap.

В `/opt/artel-crm/compose.yaml` изменены только три ресурсных параметра: `mem_limit` и `memswap_limit` 1g → 2g, `--max-old-space-size` 640 → 1536. Тариф провайдера не менялся. CRM пересоздана один раз с тем же точным image ID и тегом `artel-crm:20261102-operator-service-label-a2936566`; старт 16:23:52 МСК. Исходники приложения и схема данных не менялись. Увеличение лимита устраняет наблюдавшийся дефицит памяти; отсутствие утечки на длительном интервале этим не доказано.

Те же три изменения внесены в `ops/production/compose.yaml`. Этот локальный шаблон имеет прежние отличия от production (mount ключа bridge и stop grace); его целиком на сервер не копировали и для следующих выпусков нельзя использовать без свежей сверки.

## Сохранность

До изменения конфигурации CRM остановлена штатным `docker stop`; скопированы все 1043 постоянных файла operations, SHA-256 каждого файла совпал. Резервная копия и исходный compose: `/opt/artel-crm/backups/login-recovery-20261104/`. После восстановления также успешно выполнен штатный `artel-crm-backup.service`.

Image ID, mounts, env кроме NODE_OPTIONS и HostConfig кроме двух лимитов памяти точны; порядок bind mounts проверен без зависимости от порядка элементов. ID соседних контейнеров сохранены. Ключи/права/пароли не редактировались, отката backend/store и ручных запросов отправки/подписания документов не было.

Сверка core до остановки и после старта: shipments, companies, directories, paymentAllocations, accounts, china, sber, sberArtel, tripCreateRequests, driverTripProgress, tripNumbers, tripRequests, tripRequestCreates, cabinets, operator, tripExecutions и tripExchangeControls точны. Изменились banking (8 путей), documentArchive (2), etrn (74), push (1), revision (1), tripSaby (62). Полная атрибуция этих runtime-изменений не выполнялась; полная неизменность данных и закрытие прежних аудитов не заявляются. Raw пути сохранены в приватном `preservation-after.json`.

## Проверка

- HTTPS `/api/auth/session`: HTTP 200, корректный JSON, `needsSetup=false`.
- POST `/api/auth/login` с пустым объектом, без реальных реквизитов: HTTP 401 и штатный JSON «Неверный логин или пароль.»; не пустой 502.
- Chrome, существующая вкладка: форма входа видна без прежней ошибки. Поля пустые; успешный вход под Egor не проверялся.
- Контроль до 16:29:01 МСК, более 5 минут после старта: healthy, перезапусков 0. Все 7 последовательных HTTPS-проверок session прошли; 1,2–2,6 с на ответ. В серии память колебалась между 1,208 и 1,517 GiB при лимите 2 GiB; CPU оставался высоким (139–177% при двух ядрах). Новых OOM в журнале нет. Это короткая проверка восстановления, не доказательство долгосрочной стабильности или устранения высокой нагрузки. Наблюдения сохранены в `.local/login-recovery-20261104/stability.json`.
- Штатная резервная копия после восстановления: Result=success, ExecMainStatus=0.

Серверные доказательства: `before-inspect.json`, `before-logs.txt`, `data-before-manifest.json`, `recovery-result.json`, `preservation-after.json`, `final-summary.json` в каталоге резервной копии. Первое сравнение mounts остановило только завершающую проверку после успешного старта из-за порядка элементов; нормализованная проверка прошла, повторного пересоздания не было. Первое сравнение соседних ID смешивало короткие и полные ID; исходная отрицательная сводка сохранена отдельно, сравнение одинаковых префиксов подтвердило точность.

Commit/push не выполнялись. Перед следующими серверными изменениями сверять актуальные image, compose и состояние данных; не возвращать лимиты 640 MiB/1 GiB вместе со старым шаблоном.
