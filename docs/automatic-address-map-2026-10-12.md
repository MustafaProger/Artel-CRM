# Автоматическая точка по адресу — 12.10.2026

## Требование

Пользователь уточнил: адрес, уже указанный в заявке, должен автоматически появляться точкой на карте. Ручной выбор — возможность уточнения, а не обязательный первый шаг. Предыдущий выпуск `artel-crm:20261012-osm-leaflet-16fe82eb` обеспечивал карту и ручные точки, но не выполнял это требование.

## Проверенный адрес и источник

В существующей заявке указан адрес «улица Бианки, 2к1, Московский, Филимонковский район, Новомосковский административный округ, Москва». Прямой поиск полной строки в Nominatim не дал результата. После удаления районов/округов запрос «улица Бианки, 2к1, Московский, Москва» нашёл дом: `55.6032093, 37.3583189`. Чтение подтверждено HTTP 200 с рабочего сервера. Второй результат — терминал в том же доме, а не отдельное место доставки. Исходный адрес заявки не менялся.

Используется Nominatim по данным OpenStreetMap. [Официальный API поиска](https://nominatim.org/release-docs/develop/api/Search/) и [ограничения публичного сервиса](https://operations.osmfoundation.org/policies/nominatim/): не более одного запроса в секунду для всего приложения, идентификация приложения, атрибуция и кеш результатов. Поиск не запускается на каждую букву, по таймеру или массовым обходом справочника. Сервис получает только адрес; компания, литры и комментарий не передаются. Доступность публичного сервиса не гарантируется; endpoint должен заменяться настройкой без изменения кода.

## Реализация и проверка

- При открытии карты активные заявки без сохранённой точки автоматически обращаются к защищённому `POST /api/trip-requests/geocode`. В форме новой заявки то же происходит после выбора площадки. Сервер принимает только ID заявки либо компании/площадки, а адрес читает из своего хранилища.
- Поиск использует снимок адреса заявки. Ручные координаты и явная точка навигационной ссылки имеют приоритет; актуальный справочник может дополнить точку только при неизменном адресе. Права и актуальность данных повторно проверяются после ответа поставщика.
- Координаты автопоиска — отдельный результат для карты, без скрытого PATCH, смены версии заявки или переписывания старых рейсов. Найденная точка появляется также в редакторе и сама не создаёт несохранённых изменений. Ручное уточнение сохраняется обычной формой.
- Ответы разделены на поиск, найденный дом/улицу, неточное совпадение, отсутствие адреса и временную ошибку. Дом не подменяется центром города. Проверяется совпадение улицы, номера дома и населённого пункта; дом `2/1` не равен `21`, а `12-14` не равен `1214`.
- Кеш `trip-request-geocoding-cache.json` находится рядом с `operations.json`, записывается атомарно с правами `0600`, ограничен 1000 адресами. Найденные точки хранятся 30 дней, отрицательные результаты — сутки; временные ошибки имеют короткую задержку повторения. Это отдельный технический файл, не деловые данные.
- Настройки: `ARTEL_GEOCODER_URL` — HTTPS endpoint с Nominatim-совместимым ответом; `ARTEL_GEOCODER_USER_AGENT` — идентификация приложения; `ARTEL_GEOCODER_ENABLED=false` — отключение автопоиска. Значения по умолчанию позволяют работать без API-ключа; рабочие секреты не меняются.
- Реальный resolver отдельно проверен в изолированном Node-контейнере на рабочем сервере без доступа к производственному хранилищу: полный адрес + упрощённый запрос нашли дом Бианки, 2к1; повтор не вызвал внешних запросов. Локальный Node-запрос оказался недоступен по своему сетевому маршруту; настройки сети не менялись, эта неуспешная проверка сохранена отдельно.

Браузерная проверка: **52 группы / 42 снимка** — заявки 16, карта 10, восстановление 12, автопоиск 6, выбор точки 8; Chromium и WebKit, включая мобильные размеры. ## Сохранность данных и границы проверки

Первичный deployment-helper завершился отказом проверки сохранности после успешного запуска здорового нового контейнера: `preservation-proof.json` содержит `allPassed=false` и `dataPreservationPassed=false`. Эти исходные результаты не изменялись. Автоматический возврат старого backend и восстановление данных не выполнялись.

Отдельный `preservation-release-classified.json` подтвердил `reviewedPreservationPassed=true`: обе активные заявки, их координаты/версии, остальные защищённые коллекции, конфигурация и другие сервисы сохранены. Рейс №17 остался единственным; №15/16 не возвращались. Полные защищённые хеши Saby/ЭТрН первоначального after-снимка точно совпали с единственным сохранённым after-UI снимком. Для него есть проверенные сырые байты, поэтому изменённые защищённые поля установлены по сохранённым доказательствам без повторного чтения рабочего хранилища.

Штатный обмен Saby изменил `carrier_confirmation_pending → carrier_confirmed`, кеш `carrierEvidence: null → object`, диагностический статус отправителя ЭТрН `unknown → blocked` и сообщения диагностики. Кеш подтверждения и статусы явно считаются изменёнными. ID, редакции, содержимое основных документов, подготовленные сведения и попытки подписания сохранились. Новых ручных Write/Prepare/Execute не выполнялось. Исключённые из защищённой проекции промежуточные отметки времени/lease первичного after-снимка не реконструируются и не объявляются неизменными.

После пользовательской проверки выполнен ровно один дополнительный снимок. Создан отдельный технический кеш геокодера (714 байт); хранилище заявок автопоиском не записывалось. Исходный after-UI strict-отказ сохранён отдельно от подробной классификации.

Банковский `preservation-after-ui-bank-detail.json` сравнивает строки по постоянным ID: прежние 399 операций `banking`, 343 `sber`, 391 `sberArtel` сохранены; новых, удалённых и изменённых деловых строк — 0. В `sberArtel` изменился порядок массива, что и породило тысячи позиционных различий первоначального диагностического отчёта. Исключены только отметки `updatedAt`; счета и зашифрованные токены прежние, денежные изменения дней обоих Сберов равны нулю. Фоновые отметки опроса, job/lease не объявляются неизменными. Это классификация уже сохранённой пары снимков, а не новая попытка получить удобный результат проверки.
