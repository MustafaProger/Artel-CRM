# Отгрузки: бензовозы и АЗС

## Реализованная модель

Операции по-прежнему хранятся в `OperationsData.shipments` через существующий файловый/Blob store. Поле `fields.shipment_type` разделяет `tanker` и `azs`. У исторических записей метка отсутствует: они считаются бензовозными. Исходные данные не переписаны и не переклассифицированы по названию компании, форме оплаты или товару. Изменение типа уже созданной операции запрещено сервером; для другого типа создаётся отдельная операция. SQL-миграции не нужны.

`GET /api/shipments?type=tanker` и `?type=azs` фильтруют до вычисления итогов, фасетов и пагинации. Общий API без параметра сохраняет прежний объединённый результат для карточки компании. Интерфейс отправляет тип при каждом запросе списка, фильтров и CSV. Бензовозный редактор общей машины и распределение по клиентам сохранены.

В АЗС вводятся литры, сумма покупателя и сумма поставщика; УПД вводится вручную необязательно; суммы сохраняются как decimal-строки. «Сумма поставщика» использует существующий `purchase_amount` — в модели нет другого самостоятельного supplier total, а `Shipment.cost` уже ссылается на него. Это изменение подписи в отдельном представлении АЗС, без нового дублирующего показателя.

Формулы АЗС:

- Безнал: `customer_amount - purchase_amount`.
- Наличные: `customer_amount - purchase_amount * 0.83`.

При 100 000 и 80 000 результаты: 20 000 и 33 600. Перевозка, дополнительные расходы и КВП не вычитаются из этой утверждённой формулы. Используется общий `decimal.js` с точностью 80 значащих цифр; денежные значения в хранении сохраняют точность, как в текущем приложении. Интерфейс показывает суммы с двумя знаками. Нулевая/отрицательная величина литров, отрицательные суммы, пустые обязательные поля и некорректные числа отклоняются сервером; нулевые денежные суммы допустимы. Ф2 и неизвестные формы оплаты отклоняются и при создании, и при редактировании АЗС.

Сервер запрещает ввод в АЗС бензовозных полей: тонны, цены за тонну, цены закупки, единицы закупки, транспорт, водитель/автомобиль, адреса, дополнительные затраты, дата из файла. Клиент не может вручную подменить прибыль, оплату или долг. Поле «долг затраты» соответствует существующему `additional_costs` с заголовком «Доп Затраты»; `debt_overpayment_source` («Долг/переплата») сохранено.

## Существующие расчёты, применённые к АЗС

Общий код платежей выделен из расчётов бензовозов без смены правил:

- «Оплата» — сумма существующих привязок `paymentAllocations`; банковские строки без связи не учитываются. Для исторических данных сохраняется начальная оплаченная сумма.
- «Долг/переплата» — оплата минус сумма покупателя: отрицательное значение означает долг.
- «Дней с отгрузки» — календарные дни с даты отгрузки до текущей даты в `Europe/Moscow`; после полной оплаты поле пустое, как в действующем приложении.
- `payment_date` и сохранённые значения остались в схеме. Дата доступна в редакторе; в таблице АЗС её пока нет согласно перечню полей. Изменять её вручную API не позволяет; существующая привязка платежей обновляет её.

## Что требует согласования

1. Формула цены продажи за литр для АЗС отсутствует в текущем проекте. Возможное деление суммы на литры не реализовано. Для новых операций поле пустое и отмечено в редакторе как ожидающее согласования; сохранённое значение, если оно появится из прежних данных, не удаляется.
2. Правило КВП для АЗС отсутствует. Для новых операций поле пустое; прежнее значение не удаляется и не влияет на утверждённую формулу прибыли.
3. Нужно подтвердить, показывать ли дату оплаты отдельным столбцом АЗС. Данные не удалены.
4. В АЗС УПД вводится вручную, автоматическая нумерация не придумана. Для бензовозов сохранена существующая заготовка `allocateShipmentNumber`, возвращающая `null`: формат, период и стартовая последовательность не заданы.

## Проверки

`npx tsx --test tests/api-shipment-azs.test.ts` проверяет обе формулы, десятичную точность, пустые значения, нулевые литры, Ф2, точный состав таблицы, серверный запрет посторонних полей, неизменность исторических данных, разделение итогов и HTTP-сохранение/редактирование/удаление с повторным чтением файла и конфликтом версий. Остальные `api-shipment*.test.ts` проверяют сохранность бензовозных формул и рейсов. Все тесты используют временные хранилища и не меняют рабочие данные.
