## Что сделано

- Данные Work (задачи, записи компаний, заметки, их комментарии/вложения и события назначения задач) вынесены в `work-storage/work.json`. Изменение задачи не переписывает файл остальных данных CRM.
- Справочники, сотрудники, права, рейсы и остальные данные сохраняют общий источник `work-storage/core/operations.json`. Ссылки по ID прежние; копий справочников для отдельных страниц нет.
- Небольшой `operations.json` становится указателем формата. Старый backend отклоняет такой файл, а не начинает с пустыми задачами. До явной миграции новый код продолжает работать со старым общим файлом. Blob/serverless-хранилище не мигрируется.
- Work получает отдельную очередь допуска: оно может пройти раньше ожидающих общих транзакций. Общая блокировка на чтение/фиксацию остаётся, чтобы проверять актуальные права и согласованно изменять связанные данные. Уже выполняющуюся транзакцию Work не прерывает.
- Запись атомарна через временный файл, fsync и rename. Для транзакции, меняющей оба файла, используется checksummed redo-журнал `commit.json`; следующий читатель завершает запись под той же блокировкой. Утрата ответа после фиксации не трактуется как доказательство отсутствия изменения.
- В production уведомление о назначении запускается после HTTP-ответа; событие сохраняется вместе с задачей и повторно обрабатывается существующим планировщиком. При отсутствии production wakeup сохранён прежний серверный механизм отправки, включая serverless. Гарантия отсутствия повторной внешней доставки при обрыве после принятия push провайдером не заявляется.
- Редактор Work применяет ответ сохранения без обязательного дополнительного GET. Во время сохранения приостанавливает обновление списка и отменяет старый GET. Фильтр исполнителя сохраняется. Мгновенная галочка и откат при ошибке сохранены.
- Подготовлены CLI split/merge/export, согласованный экспорт для backup, обновлённый backup.py и recovery блокировок в entrypoint после получения lifetime lock. Добавлены инструменты в сборку и Dockerfile. Журнал фиксации при старте не удаляется. Сумма размеров разделов с запасом 4 КиБ ограничена прежними 64 МиБ: запись отвергается до изменения файлов, чтобы сохранить возможность полного flat backup/merge. Это не снятие предельного размера базы.

Это изоляция записей Work, а не полная независимость страниц: общий адаптер хранения изменён, основная часть CRM всё ещё читается и разбирается для прав/связей, процесс и CPU общие. Разделять все страницы по файлам автоматически не следует: сущности и их связи важнее экранов. Ревизия составного снимка монотонна; смешанная запись может увеличить её на 2, версии задач сохраняют прежнюю семантику.

## Замеры

Изолированный повторный ABBA-прогон завершён успешно (`benchmark-final.json`), внешних вызовов 0. Методика: HTTP на loopback, одна и та же локальная кандидатная API-реализация, старый и разделённый адаптер; legacy → partitioned → partitioned → legacy. 3500 синтетических банковских операций, общий JSON около 6,04 МБ, Work около 2,25 КБ; реальные локальные файловые записи. По 30 образцов на действие/режим (600 HTTP-записей суммарно): создание, выполнение, возврат в todo, редактирование, удаление. Два режима: без фоновых записей и с шестью общими транзакциями перед каждым действием. Отдельно измеряется завершение всей пачки, чтобы учитывать воздействие на фоновые записи.

Полная пачка «6 фоновых записей + действие Work»: медиана 387,38 → 387,13 мс; p95 402,90 → 404,13 мс, по 150 образцов. Существенного ухудшения завершения пачки в этом локальном сценарии не видно. Это не измерение задержки каждой другой страницы отдельно.

Промежуточный прогон до исправления общего пути выявил замедление фоновой пачки примерно 386 → 558 мс. Удалены два лишних JSON-сравнения core из обычных транзакций; после уже проверенной записи запоминаются её точные байты, но каждое чтение всё равно сверяет реальный файл. Промежуточные данные сохранены отдельно как `benchmark-before-core-fix.*` и не используются как результат финального алгоритма.

ABBA измеряет исправленный алгоритм до последнего добавления защитной проверки суммарного размера файлов. Эта проверка не добавляет чтения/записи файла; финальная сборка с ней проверена функционально и через built UI. Отдельный ABBA после этого защитного уточнения не повторялся.

Это macOS/локальный Node, без сетевого пути пользователя, production cgroup, внешних API и минутного прогрева после перехода. Предварительный прогон пересекался с частью QA; выводы следует делать по `benchmark-final.json`, выполненному отдельно. Сохранность остальных 3499 банковских строк проверяется в каждом прогоне.

## Подготовленный порядок серверного переноса (здесь не выполнялся)

1. Сверить текущий live image, исходники и runtime drift; перенести только согласованный патч на актуальный baseline. Не заменять live основной локальной копией.
2. Собрать новый Linux-образ. На отдельной копии данных выполнить проверки сохранности бизнес-фактов, прав, защищённых Saby и фоновых сервисов, API/UI, backup и восстановление. Запустить `tests/production-entrypoint.sh` с entrypoint override в этом образе.
3. Проверить, что будущие release/audit-инструменты получают согласованный полный снимок через `server-render/export-operations.mjs`, а не копируют только корневой `operations.json`. Старые `release-state`/preservation helpers и `deploy-invoices.py`, читающие файл напрямую, нельзя использовать для разделённого layout без адаптации. В этом локальном пакете они не запускаются и не объявляются совместимыми. Существующие QA-скрипты, ожидающие flat fixture, запускаются на экспортированной изолированной копии.
4. Подготовить приватную резервную копию, новый backup.py на хосте и остановить **всех** писателей именно CRM: runtime, обслуживающие cron/maintenance-процессы. Не менять соседние сервисы, входы, ключи или worker. Получить тот же lifetime lock через новый entrypoint. Обозначить окно обслуживания.
5. В новом maintenance-контейнере с правильными mounted store/snapshot выполнить команду ниже. `SOURCE_SHA` берётся из текущего `snapshot/manifest.json`, не из имени образа или этой инструкции:

   ```sh
   node server-render/work-storage.mjs split "$ARTEL_STORE_DIR" "$SOURCE_SHA" --writers-stopped
   ```

   Split сохраняет private backup, пишет оба файла, сверяет логический снимок и только последним атомарно меняет указатель. При ошибке до указателя старый файл остаётся источником; оставшийся `work-storage/` не перезаписывается автоматически. Повтор успешного split проверяет файлы и не переносит данные заново. `--writers-stopped` — подтверждение оператора, а не самостоятельная остановка процессов.

6. Сверить полный экспорт до/после и неизменность всех деловых фактов; запустить новый runtime и новый backup. Проверить HTTPS, права и чтение страниц. Контролируемые записи для замера выполнять на тестовых задачах с согласованным пользователем; фиксировать ответ сервера, время интерфейса, очередь и CPU throttling сразу после перехода и спустя минуту. Тариф и лимиты не менять одновременно с этим экспериментом.
7. Если нужен возврат к единому файлу, остановить писателей/получить lifetime lock и **новым инструментом** собрать текущие данные:

   ```sh
   node server-render/work-storage.mjs merge "$ARTEL_STORE_DIR" "$SOURCE_SHA" --writers-stopped
   ```

   Сначала проверить полученный flat snapshot, затем запускать совместимый код на актуальной функциональной базе. Merge использует текущие задачи и текущие остальные данные; старую предмиграционную копию поверх новых операций не восстанавливать. Оставшийся каталог разделения сохранить как закрытый архив доказательств, а перед новым split перенести его в отдельное приватное место при остановленных писателях. При неизвестном исходе записи сначала сверить текущее состояние/журнал, затем повторять.

Backup после разделения представляет собой полноценный проверенный flat snapshot. Восстанавливать его следует в пустой изолированный store; оставшийся указатель или старые разделённые файлы не смешивать с восстановленным снимком. Формат нового кода поддерживает оба layout.
