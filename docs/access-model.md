# Модель доступа Artel CRM

Статус: описание ролей на подтверждённом этапе локальной выгрузки JSON. `config/roles.json` описывает предполагаемые права будущей CRM; он не реализует вход, серверную авторизацию или защиту JSON-файлов. Учётные записи, пароли и действующие назначения ролей на этом этапе не создаются.

## Требования и допущения

Из запроса: администратор раздаёт роли; директор имеет полный доступ; менеджер работает только со своими компаниями и отгрузками. Из Excel нельзя достоверно установить, какой будущей учётной записи принадлежит запись. Поэтому импортированные записи получают `owner_user_id: null`, пока директор или администратор не назначит владельца.

Рабочее допущение: администратор также видит все бизнес-данные для импорта, проверки и распределения записей. Директор вправе управлять пользователями и ролями, поскольку для него запрошен полный доступ. Бухгалтер и сотрудник склада — предложенные базовые роли: их названия и права не являются подтверждённым требованием и пока не доступны для назначения (`enabled_for_assignment: false`).

## Матрица прав

«Свои» определяется на сервере правилами ниже. «Назначенные» у предложенных базовых ролей означает отдельное явное разрешение директора/администратора для конкретной записи; таких разрешений сейчас нет.

| Действие | Директор | Администратор | Менеджер | Бухгалтер, предложение | Склад, предложение |
| --- | --- | --- | --- | --- | --- |
| Просмотр компаний | Все | Все | Свои | Назначенные, финансовые поля | Только реквизиты доставки компаний из назначенных отгрузок |
| Создание/изменение компаний | Все | Все | Свои; владелец задаётся сервером | Нет | Нет |
| Просмотр отгрузок | Все | Все | Свои отгрузки своих компаний | Финансовые поля отгрузок назначенных компаний | Назначенные отгрузки, логистические поля |
| Создание/изменение отгрузок | Все | Все | Свои отгрузки своих компаний | Только поля оплаты в своей области доступа | Только статус, фактическая дата и примечание склада в своей области доступа |
| Удаление компаний/отгрузок | Все, с аудитом | Все, с аудитом | Нет | Нет | Нет |
| Отчёты и экспорт | Все | Все | Только своя область доступа | Нет по умолчанию | Нет по умолчанию |
| Финансовая выписка (`payments`), общие финансовые сводки | Все | Все | Нет | Нет по умолчанию; нужен отдельный перечень прав | Нет |
| Просмотр записей без владельца | Да | Да | Нет | Нет | Нет |
| Назначение/смена владельца | Да | Да | Нет | Нет | Нет |
| Импорт исходных данных | Да | Да | Нет | Нет | Нет |
| Пользователи, роли, дополнительные разрешения | Полный доступ | Полный доступ | Нет | Нет | Нет |
| Журнал изменений | Все события | Все события | Нет по умолчанию | Нет | Нет |

Список финансовых и логистических полей нужно зафиксировать перед реализацией соответствующей базовой роли. До появления явного списка действует запрет. Предложенные базовые роли не расширяют доступ менеджера: на начальном этапе у пользователя одна активная роль.

## Владение компанией и отгрузкой

У компании хранится `company.owner_user_id`. У отгрузки независимо хранятся `shipment.owner_user_id`, ссылка на покупателя `shipment.customer_id`, поставщика `shipment.supplier_id` и перевозчика `shipment.carrier_id`. Для контроля доступа компания отгрузки — именно покупатель по `customer_id`. Поля `company_id` в текущей выгрузке отгрузок нет. Владельца отгрузки нельзя подменять владельцем покупателя при чтении.

Для менеджера выбрана строгая политика:

```text
company.read/update/export:
  company.owner_user_id == authenticated_user.id

shipment.read/update/export:
  shipment.owner_user_id == authenticated_user.id
  AND shipment.customer_id ссылается на существующую компанию-покупателя
  AND customer.owner_user_id == authenticated_user.id
```

Владение компанией не открывает менеджеру чужие отгрузки. Владение отгрузкой не открывает чужую компанию. Отгрузка без подтверждённого покупателя или без любого из двух владельцев доступна только директору и администратору. Названия фирм, ФИО в ячейках и авторство Excel не считаются назначением владельца.

Связи `supplier_id` и `carrier_id` не дают менеджеру доступ к полной карточке поставщика/перевозчика, их другим отгрузкам или платежам. В доступной отгрузке можно показывать названия поставщика и перевозчика из этой отгрузки. Если связанная компания сама принадлежит менеджеру, её карточка открывается по самостоятельному правилу `own_company`; одна ссылка из отгрузки такого права не создаёт.

Владение компанией не открывает финансовую выписку `payments`, её строки по `counterparty_id`, финансовые сводки `company_summaries` или исходный `raw_workbook`. Эти ресурсы для менеджера запрещены. В карточке/экспорте компании не возвращаются `payment_ids` и сырые `occurrences`; `shipment_ids` фильтруются по доступу к каждой отгрузке. Отчёты менеджера используют только разрешённые данные компаний и отгрузок и не включают скрытые платежи через суммы, ссылки или вложенные объекты.

Менеджер создаёт компанию от своего имени: сервер устанавливает `owner_user_id` по проверенной сессии. Отгрузку он создаёт только для своей компании-покупателя; владельцем новой отгрузки сервер устанавливает того же текущего пользователя. Поля `owner_user_id`, роли, дополнительных разрешений и системных идентификаторов исключаются из разрешённых полей менеджерского запроса; попытка их передачи отклоняется. При смене `customer_id` у отгрузки повторно проверяется доступ к новому покупателю. Смена `supplier_id` или `carrier_id` не меняет область доступа и не открывает связанные карточки.

Смена владельца компании не меняет владельцев её отгрузок автоматически. Прежний менеджер немедленно теряет доступ к компании и отгрузкам, где она указана покупателем. Новый менеджер получает компанию, но не чужие отгрузки. Директор/администратор может отдельно передать выбранные отгрузки тому же новому владельцу. Пока владельцы отгрузки и покупателя различаются, отгрузка доступна только директору/администратору. Массовую передачу компании и выбранных отгрузок необходимо выполнять атомарно, с записью старого и нового владельца в аудит.

## Правила будущей серверной реализации

1. Аутентифицировать запрос; получать идентификатор пользователя и роль из доверенного серверного состояния. Значения из query/body, `localStorage` и скрытые кнопки не подтверждают полномочия. Неизвестная роль или отключённый пользователь получают отказ.
2. Применять ограничение `owner_user_id` на сервере до чтения и возврата данных. Оно действует для списков, отдельных записей по ID, поиска, подсказок, отчётов, вложений, экспорта, количества строк и сумм. JSON целиком не передаётся браузеру менеджера с последующей фильтрацией.
3. Повторять проверку области доступа и разрешённых полей для `create`, `update`, `delete`, пакетных операций и смены связанных записей. Проверка и запись выполняются атомарно, чтобы параллельная передача компании не обошла ограничение.
4. Отклонять изменение роли или владельца менеджером, в том числе через вложенные объекты и массовые запросы. Назначать владельцев можно только существующим активным пользователям. Любое право, отсутствующее в спецификации, запрещено.
5. Для предложенных базовых ролей отдельно проверять явное разрешение на запись и список видимых/изменяемых полей. Запись с `owner_user_id: null` закрыта даже при наличии такого разрешения. Для отгрузки также обязательны подтверждённый покупатель по `customer_id` и его ненулевой владелец.
6. Отзывать доступ при блокировке пользователя, смене роли и передаче записей. Для чужого ID возвращать одинаковый ответ об отсутствии доступной записи, без её названия и других реквизитов. Журналировать изменения ролей, владельцев, импорт и изменения данных без паролей и токенов.
7. Хранить локальную полную выгрузку вне публичной папки сайта. Доступ к файлу на диске означает доступ ко всем его данным; роли из конфигурации этот файл не защищают.

## Проверки при реализации

Эти сценарии задают критерии будущей приёмки; сейчас авторизации для их запуска нет.

- Менеджер A видит свои компании и свои отгрузки своих компаний; данные менеджера B отсутствуют в списках, поиске, карточках, отчётах и экспорте.
- Прямой запрос по чужому ID, смена `customer_id`, подстановка `owner_user_id`, изменение роли и пакетная запись не обходят ограничения.
- `supplier_id` и `carrier_id` доступной отгрузки дают только названия из этой отгрузки; чужие карточки, другие отгрузки и платежи остаются закрытыми.
- Владение компанией не открывает `payments` по `counterparty_id`, `company_summaries`, `raw_workbook`, `payment_ids` или финансовые суммы из запрещённых ресурсов через отчёт/экспорт.
- Своя компания с чужой отгрузкой и своя отгрузка с чужой компанией не дают менеджеру доступ к отгрузке.
- Записи без владельца/компании доступны директору и администратору и не раскрываются другим ролям.
- Передача компании немедленно закрывает прежнему менеджеру доступ; история отгрузок открывается новому только после явной передачи этих отгрузок.
- Директор видит все записи и управляет ролями; администратор распределяет роли и владельцев; отключённый пользователь не получает доступ.
- Неактивная базовая роль и неизвестное разрешение не дают доступа. Предложенные роли не получают скрытые финансовые/логистические поля вне своего перечня.
