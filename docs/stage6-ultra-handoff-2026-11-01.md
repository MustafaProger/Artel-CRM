## Требования к реализации и приёмке

Новый чат должен исправить корень, безопасно восстановить затронутые существующие рейсы в пределах подтверждённых фактов и разрешений, опубликовать проверенное изменение и завершить аудит. Локальное изменение сообщения об ошибке или ручной перевод `phase` в completed не являются решением.

Обязательная матрица нового рейса на изолированной синтетической среде:

1. Полный связный путь от создания рейса/сохранённых фактов водителя и разрешения до создания правильных ЭТрН, выбранных T1/T2-подписей и handoff правильному frozen клиенту; одна и несколько доставок.
2. Ordinary и direct режимы; существующая ЭТрН обнаружена/связь подтверждена, отсутствие документа после полного ограниченного поиска, ложный/чужой/неоднозначный кандидат.
3. Повторный scheduler/manual retry, reload, restart, concurrent workers/CAS; partial failure между резервированием/номером/загрузкой/подготовкой/Execute/фиксацией результата. Никаких дублей или дополнительных изменяющих provider calls.
4. Unknown result и принятый pending Execute не приводят к слепому повтору. Подпись/редакция/точные байты/клиент проверяются до следующего действия. Корректный success восстанавливается по evidence; неподтверждённый успех не рисуется.
5. Pause/restart/resume, старый callback после pause, действующие ограничения прав и guarded delete; ожидание водителя или клиента не объявляется ошибкой CRM.
6. Проверка этапа/сообщения UI и причины остановки: созданная ЭТрН не выглядит как отсутствующая; при error нельзя обещать фоновое продолжение, если scheduler её исключает.

Ключевой regression: обезличенные реальные формы native envelope/XML именно №52/54 должны воспроизводить тот же error на старой версии и проходить согласованное исправление без дублей. Обязателен переход через сутки/месяц: рейс30/31.10, созданная ЭТрН01.11; дополнительно нормальный same-day. Снять общий guard недопустимо. Проверить всю модель: `etrn-linked-draft.validateNote`, XML `ДатаТрН` в `server/saby-consignment-draft.ts:96`, сохранение native `documentDate` в `updateRequest` около строки178, дальнейшую сверку/подпись. Исправление одной проверки без остальных может лишь перенести остановку. До adoption требуется доказательство точных XML business-полей и сохранения frozen shipping date/facts; не переписывать историю перевозки под сегодняшнюю дату ради прохождения guard.

До релиза: осмысленные unit/API/target regression, lint, TypeScript, build; source и built UI Chromium/WebKit (мобильный/desktop) и axe для изменённого UI; оба Linux-образа с одинаковым новым backend, restart/CAS, проверка точного пакета и Git-кода. Существующие smoke/check helpers брать из свежей базы и проверять их область действия. Обязательна совместимость на копии актуального store без внешних записей, резервная копия и восстановимость, HTTPS/static/routes/security headers.

Копия store должна подтвердить `fullDataExact=true`, external requests 0; резервная копия проверяется в остановленном состоянии. `tripExchangeControls` включается во все задействованные preservation classifiers, не только один путь проверки.

После релиза: контейнер health/restarts, read-only production UI с сохранённой сессией, актуальное состояние №52/54 и успешных контрольных рейсов, точные документы/связи/подписи/отсутствие дублей.
