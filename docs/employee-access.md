# Сотрудники, права и сверка заказчиков

Реализовано 16.09.2026 в текущем репозитории. Эти изменения ещё не опубликованы.

## Как создать учётную запись

1. Войдите как директор или администратор. Откройте **Сотрудники и доступ → Добавить пользователя**.
2. Выберите сотрудника справочника. Если его ещё нет, заполните **Новый сотрудник** и нажмите **Добавить сотрудника**. При точном совпадении выбирается существующая запись; второй сотрудник не создаётся. Для разных людей с одинаковыми именами используйте различимые полные имена.
3. Задайте имя для отображения, уникальный логин и пароль от 12 до 256 символов. Имя сотрудника, логин и полномочия — отдельные поля.
4. Выберите **Сотрудник / менеджер** и отметьте нужные разделы: Обзор, Работа, Отгрузки, Китай, Склад, Платежи, Операторская, ЗП, Справочники.
5. Оставьте **Активен** включённым и нажмите **Сохранить пользователя**. В списке видны связанный сотрудник, доступные разделы и область отгрузок.

Один сотрудник может иметь только одну активную учётную запись. Пустой список разделов означает отсутствие доступа. Новые аккаунты требуют связи с сотрудником, включая новые аккаунты администраторов. Существующие директорские/административные аккаунты без связи продолжают работать; их можно привязать через редактирование. Первичная настройка первого директора сохранена.

Для изменения нажмите **Изменить**. Пустое поле нового пароля сохраняет прежний пароль. Заполненное поле меняет пароль через существующий scrypt с новой солью. Снятие **Активен** запрещает вход. Любое сохранение существующего аккаунта удаляет все его сеансы и подписки уведомлений; сервер сразу отклоняет прежние cookie. Последнего активного директора нельзя отключить или понизить.

Полномочия **Директор** и **Администратор** дают полный доступ ко всем разделам и отгрузкам, включая управление аккаунтами. Обычный сотрудник не может создавать аккаунты, изменять собственные права или назначать себе административные полномочия.

## Что означают разделы и принадлежность отгрузок

Отключённый раздел отсутствует в меню и не открывается по прямому адресу. API проверяет разрешение самостоятельно, в том числе внутри транзакции записи. Общий снимок, компании, суммы, поиск, фильтры, подсказки фильтров и CSV содержат только разрешённые записи.

У сотрудника **Отгрузки** всегда означают **только отгрузки связанного сотрудника**. Настроек «все отгрузки» и выбора коллег нет. Назначение менеджера компании не даёт доступа ко всем её отгрузкам. В общем рейсе сотрудник видит свои строки без общих сумм машины; менять такой рейс может только администратор. Рейс, состоящий исключительно из собственных строк, можно создавать и редактировать. Удаление отгрузок по-прежнему доступно только директору/администратору.

Сотрудник без действующей связи со справочником не получает отгрузок. Явный `manager_id` имеет приоритет. Если старый импорт содержит только подпись менеджера, допускается лишь однозначное точное соответствие с учётом нормализации регистра/пробелов и сохранённого стабильного ID. Неизвестные ID, отсутствующие подписи и неоднозначные совпадения не открывают запись сотрудникам. Сам импорт и его исходные поля не перезаписываются. Аудит:

```sh
npx tsx scripts/audit-shipment-ownership.ts /absolute/path/to/store
```

Доступ к Работе сохраняет прежние ограничения исполнителя и автора для задач, заметок и вложений. Снятие права на Работу закрывает также скачивание файлов и уведомления. Минимальные списки названий компаний и вариантов выбора для доступной формы остаются рабочими зависимостями формы; они не содержат чужих отгрузок или закрытых реквизитов справочника.

Разрешение раздела не повышает административные полномочия: банковские платежи и учёт Китая сохраняют прежнее ограничение директором/администратором, справочники для сотрудников доступны только для чтения. Обзор, Склад, Операторская и ЗП не получили новых расчётов или выдуманных данных.

## Совместимость хранения

Общая модель: `web/src/auth-model.ts`; проверка API: `server/permissions.ts`; область данных: `server/auth-scope.ts`; исторические назначения: `server/shipment-ownership.ts`.

Старые аккаунты без поля `sections` читаются без принудительного изменения файла. Старые менеджеры сохраняют прежние доступные разделы, кроме ранее недоступных им данных Китая и банковских платежей. При следующем сохранении аккаунта сохраняется явный список. Директор и администраторы сохраняют полный доступ. При понижении администратора без явного списка разрешений используется пустой список, чтобы не расширять доступ неявно.

Права находятся в существующем защищённом envelope аккаунтов. Используются прежние локальное хранилище с блокировкой/атомарной заменой и приватный Vercel Blob с сильным ETag/If-Match. Новая база данных не вводится.

## Адресная сверка заказчиков

Сверка рассматривает **существующие импортированные отгрузки выбранного хранилища**, а не произвольные последние 100 строк. Последние 100 использованы только в отдельной диагностической тестовой копии, поскольку рабочий локальный и production-наборы различаются.

Сначала создайте план с явным указанием целевого хранилища:

```sh
npx tsx scripts/reconcile-customers.ts plan /absolute/path/to/store /absolute/path/to/plan.json
npx tsx scripts/reconcile-customers.ts apply /absolute/path/to/store /absolute/path/to/plan.json
```

Для Blob вместо пути каталога укажите `blob:artel/operations.json`; штатные credentials должны быть уже доступны серверному процессу. Скрипт не загружает `.env` и не подменяет production локальным файлом. Не публикуйте файл плана, backup или credentials в Git.

После публикации кода доступны административные маршруты: `GET /api/directories/reconcile-customers` возвращает план; `POST` того же адреса принимает только `revision` и `fingerprint` этого плана. Доступ сотрудникам запрещён. CLI и API используют одну и ту же функцию и оба хранилища.

Перед изменением создаётся и перечитывается полная резервная копия через storage abstraction. Проверяются revision и отпечаток данных; конкурентная запись приводит к конфликту, а не к перезаписи чужих изменений. После записи выполняется контрольное чтение и проверка точного ожидаемого состояния. При конфликте во время контрольного чтения нужно повторно прочитать данные и план, а не откатывать всю базу поверх новых записей.

Сверка восстанавливает только архивные карточки по точным связанным ID. Новую карточку можно создать лишь при наличии стабильного source ID и единственного согласованного имени в источнике; указанные ИНН дополнительно проверяются по контрольным цифрам и на конфликт с другими ID. Похожие названия не объединяются. Удалённые карточки, неизвестные исходные отгрузки и противоречивые реквизиты попадают в отчёт. Отсутствующий customer ID нельзя придумать по названию. Суммы, даты, поставщики, платежи, назначения сотрудников и сами отгрузки не меняются.

Второй запуск сначала требует новый план. Если изменений нет, он не создаёт backup, не увеличивает revision и не добавляет карточки.
