# Сравнение авторизации GloPro и Artel-CRM — 09.11.2026

По просьбе пользователя исследован https://lk.glopro.ru/ через изолированный Chromium с предоставленным доступом. Изучались обычный вход/выход и штатная загрузка страницы; бизнес-формы не сохранялись. Credentials, cookie values и содержимое кабинета не включены в этот отчёт или raw timings.

## Наблюдаемый подход GloPro

- Обычная HTML form: POST /login → HTTP302 → /clients (первый вход дополнительно прошёл через /). Загружается HTML кабинета; jQuery/Bootstrap, без необходимости предполагать SPA.
- После страницы отдельные AJAX POST /clients/clients-list загружают список фирм; POST /messages/load-messages загружают сообщения. В опубликованном clients.js виден вызов paginationAjax. Список появляется после оболочки, некоторые сообщения в исследовательском проходе загружались несколько секунд и не блокировали оболочку.
- Выход: GET /logout → HTTP302 → GET / → форма входа. После собственных выходов token_access отсутствовала в browser cookies. Инвалидация прежнего bearer на сервере отдельно НЕ проверялась.
- Наблюдаются Secure/HttpOnly cookies token_access и token_refresh. Названия не доказывают JWT, stateless-сессии, Redis или конкретный backend. Серверные исходники, БД, блокировки и физическое хранение неизвестны; утверждать, что GloPro использует auth.json, нельзя.

## Короткие реальные замеры

Три сопоставимые пары в одном изолированном Chromium-контексте без throttling, с обычным HTTP cache. Начало — DOM click timestamp; оболочка — видимый элемент меню профиля, первый ответ списка отдельно. Выход активирован DOM click штатной ссылки /logout; открытие выпадающего меню исключено. Эти критерии не совпадают полностью с CRM benchmark (cache disabled и готовый Обзор), поэтому прямой процент преимущества между продуктами некорректен.

| Метрика | Пара1 | Пара2 | Пара3 | Медиана |
|---|---:|---:|---:|---:|
| Вход → оболочка, с | 1.070 | 1.696 | 1.052 | 1.070 |
| Вход → первый ответ списка, с | 2.052 | 2.960 | 2.156 | 2.156 |
| Выход → форма, с | 0.565 | 0.321 | 0.647 | 0.565 |
| HTTP POST /login, с | 0.626 | 1.283 | 0.662 | 0.662 |
| HTTP GET /logout, с | 0.160 | 0.152 | 0.142 | 0.152 |

HTTP включает сеть и сервер. Получение первого ответа списка не равно завершению всей пагинации/всех фоновых сообщений. После каждого из трёх выходов token_access отсутствует. p95 по n3 не вычисляется.

Предварительные исследовательские проходы исключены из сопоставимой серии: ошибочные ожидания exact accessible name/неверного h3 и нестабильного dropdown. Первые два ожидания кнопки не отправили login; последующие три исследовательских успешных входа завершены собственным logout, включая восстановление после ошибки меню. Эти ошибки инструмента не выдаются за сбои сервиса. Финальный браузер закрыт после подтверждённой формы выхода. Значения старого bearer не сохранялись и серверная ревокация не доказана.

## Что применять к CRM

1. Короткий серверный путь авторизации, независимый от чтения и записи большого бизнес-архива. Уже опубликованный auth partition CRM соответствует этой цели, но фактические причины скорости backend GloPro неизвестны.
2. Показ доступной рабочей оболочки сразу после подтверждённого входа, независимые загрузки содержимого и необязательных уведомлений. CRM уже частично делает это; нужен профиль текущего пути, а не повторное добавление существующей логики.
3. Сохранять отдельные показатели: auth HTTP, видимая оболочка, готовый первый рабочий экран. Не ускорять метрику только переносом незавершённой работы за её конец.
4. Следующий вероятный участок CRM — ожидание общей блокировки/занятого event loop при фоновых бизнес-записях. Это гипотеза из собственного кода CRM и остаточной задержки, не наблюдение внутренностей GloPro. Нужны phase timings latch wait/read/KDF/commit/serialization и settlements перед следующим архитектурным решением.
5. Не копировать автоматически GET logout, имена/формат tokens или иной механизм сессий: это не доказанная причина быстродействия. Сохранить нынешние POST/origin checks, durable logout, worker revocation и изоляцию прав CRM.

## Дополнение по фактическому пути опубликованной CRM

Повторно разобраны **парные** длительности десяти after-наблюдений из независимого аудита, без новых login/logout или изменения production. Разница между временем «клик→оболочка» и длительностью HTTPlogin: median **24,128мс**, диапазон22,546–37,397мс. Для «клик→форма выхода» минус HTTPlogout: median **48,304мс**, диапазон40,434–50,529мс. Это разницы браузерных длительностей с немного различающимися границами, не точный CPU-профиль React и не server-only timing.

От видимой оболочки до готового Обзора проходит median **1376,350мс** (586,800–2772,400мс). Парная медиана не равна разности отдельных медиан. HTTPsettlements median1143,048мс. Артефакт расчёта: `.local/auth-speed-release-20261109/benchmark/paired-ui-overhead.json`, исходный after results SHA256 `2147b02bc3a1f9d3ad282cddbf7e3e02333f42adadef7fcb0b6643542c3cb9b5`.

Код опубликованного источника уже применяет нужный клиентский подход: AuthGate принимает пользователя из login response, App начинает импорт страницы и навигационные данные независимо, OverviewPage самостоятельно запрашивает settlements. Дополнительного GETsession в login-chain нет, push/config использует малый auth-read. Переписывать эту логику ради более ранней смены экрана оснований сейчас нет.

**Следующий конкретный участок — серверная фазовая диагностика `readAuth → prepareLogin → mutateAuth`, затем `/api/settlements`.** Требуемые интервалы: начало запроса/base snapshot; ожидание latch и фактические read/validation; gate/admission; KDF; интерактивная очередь и повторное ожидание latch; mutation/serialization; fsync файла+каталога; завершение HTTP. Вложенные интервалы учитывать как spans, не складывать дважды. Event-loop delay/utilization измерять отдельно от времени работы scrypt worker pool и дисковых операций. Для settlements отделить чтение общего core, построение финансового отчёта и сериализацию ответа.

Сначала одинаковый профиль на изолированной актуальной копии: без фоновых записей и с воспроизводимой смешанной нагрузкой. Он проверит механизм; live-выигрыш доказывается только новой сопоставимой before/after серией. Сохранять только агрегаты и случайный request-id, без login, bearer, паролей, содержимого store или provider payload. Не ослаблять KDF/gate/rate limits, свежие права, общий атомарный commit и worker revocation ради цифры.

Фазовая инструментализация пока **не реализована и не опубликована**; ожидание latch/event loop остаётся гипотезой. Сравнение GloPro не доказывает применимость JWT/Redis/GETlogout и не служит основанием менять существующий механизм сессий. Изменения этого дополнения — аналитика и документация; активный релиз428d0ac8 и его отрицательные preservation-флаги прежние.
