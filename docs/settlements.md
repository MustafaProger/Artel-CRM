# Обзор и взаиморасчёты по нашим организациям

## Локальная доработка 28.09.2026

Новая версия реализована и проверена локально: публикация, пуш, банковские операции и массовая миграция истории не выполнялись. Сведения о ранее опубликованной версии находятся ниже и не означают публикацию описанной доработки.

Основной «Обзор» предлагает **НК АРТЕЛЬ / АРТЕЛЬ**, затем **Поставщики / Клиенты**. Это пересборка экрана; финансовые операции, отгрузки, справочники и история не удаляются. Общий клиентский отчёт по прежней очереди доступен отдельно для сверки. Его нельзя складывать с отчётами организаций: это альтернативный совместимый расчёт, а не дополнительные деньги.

### Принадлежность отгрузки

`fields.organization_id` хранит `nk-artel` или `artel`. Названия совпадают с действующим интерфейсом подключений; банковское юридическое написание «АРТЭЛЬ» не создаёт третью организацию. Сбер `sber-nk-artel` и Т-Банк `tbank-nk-artel` относятся к НК АРТЕЛЬ, Сбер `sber-artel` — к АРТЕЛЬ.

Новые формы требуют явного выбора организации. Старые строки без него не распределяются автоматически: они выделяются для проверки и остаются в общем клиентском отчёте. Совместимый API допускает отсутствие поля для старых импортов. Несуществующий идентификатор отклоняется.

### Поставщики

Сумма долга берётся из **`purchase_amount`**, рассчитанного существующими формулами по количеству и единице закупочной цены. Цена единицы не является суммой долга. Каждая пара **наша организация + ИНН поставщика** имеет независимую очередь закупок.

В расчёт входят только сохранённые, исполненные, положительные рублёвые **исходящие** банковские операции поставщику. Проверяются направление, проведение, контрагент, собственные счета и организация. Любое поступление не считается погашением долга поставщику; неизвестные получатели не превращаются автоматически в поставщиков. Переводы между своими счетами исключаются. Неоднозначные операции направляются на проверку.

Платежи погашают самые ранние закупки (FIFO), включая частичную оплату и распределение одного платежа на несколько закупок. Излишек остаётся авансом этой же паре и используется при последующих закупках. Отрицательный баланс — **наш долг поставщику**, положительный — **наш аванс поставщику**.

| Проверочный пример | Результат |
| --- | --- |
| Закупка 738 000 ₽, платёж 300 000 ₽, затем 438 000 ₽ | Долг 738 000 → 438 000 → 0 ₽; история закупки и обоих платежей сохраняется |
| Закупки 400 000 и 600 000 ₽; оплата 700 000 ₽ | Первая закрыта, во вторую направлено 300 000 ₽; осталось 300 000 ₽ долга |
| АРТЕЛЬ должна 300 000 ₽, НК АРТЕЛЬ — 400 000 ₽; АРТЕЛЬ платит 700 000 ₽ | АРТЕЛЬ: +400 000 ₽ аванса; НК АРТЕЛЬ: −400 000 ₽ долга |

Карточка поставщика сохраняет закрытые закупки и платежи. С обеих сторон видны дата, номер/ID операции, банк, счёт, наша организация, исходная сумма, распределённые суммы, остаток долга закупки и аванс платежа. Та же детализация доступна в карточке исходящей банковской операции в «Платежах». Остатки относятся к текущему расчёту.

### Клиенты и совместимость

Клиентский долг считается по **продаже** (`customer_amount`), независимо от закупочного долга поставщику. Для явно привязанных отгрузок используются поступления только их организации. Счёт и банк показывают источник денег; отдельный долг по счетам не вычисляется. Общий итог по ИНН и прежняя общая очередь сохранены в отдельном отчёте.

Если у клиента есть только старая история без организаций, прежняя проекция оплаты его отгрузок сохраняется. При смешанной истории явно привязанные строки получают расчёт своей организации, неопределённые сохраняют исходные оплаты до сверки. Это исключает повторное применение одного поступления в новых и неопределённых строках. Неизвестную прежнюю оплату нельзя считать нулевой.

Согласование юрлиц не закрывает вопросы распределения клиентского долга между счетами, переноса неопределённой истории и исторических оплат/возвратов. Они перечислены в [следующей задаче](next-task-bank-balances.md).

### Сохранность и доступ

Расчёт — чистая проекция сохранённых данных с Decimal. Чтение не создаёт банковских переводов, не меняет исходную оплату, не переписывает хранилище. Повторный импорт использует существующую идентичность **банк + собственный счёт + ID операции банка**. Конфликтующие копии исключаются до сверки. Незавершённые страницы, архивы и неподтверждённые дни Сбера АРТЕЛЬ не участвуют.

Исправление закупки или полная замена выписки пересчитывает распределение. Если платёж отозван/архивирован, он перестаёт гасить долг; если закупка уменьшена/удалена, деньги освобождаются и становятся авансом либо погашают следующую закупку. Это текущая воспроизводимая история по активным исходным документам, а не неизменяемый журнал всех прежних версий распределения. Закрытие долга само по себе ничего из истории не убирает.

Директор/администратор видят полный отчёт. Менеджеры получают серверную проекцию по доступным отгрузкам: чужие ссылки, исходная сумма общего платежа и свободный общий аванс не раскрываются. Расчёт сначала выполняется полностью, затем ограничивается доступ; он не запускается заново по каждому менеджеру.

Ниже сохранено описание предыдущего релиза. Его правило общей очереди относится к совместимому общему отчёту; для явно выбранных организаций действуют правила выше.

Обновление опубликовано 28.09.2026 на [artel-crm.online](https://artel-crm.online), образ `artel-crm:20260928-overview-2911ff2`, код `2911ff2`. Проверки публикации, резервная копия и откат описаны в [отчёте релиза](../ops/production/overview-release-2026-09-28.md).

Взаиморасчёты перенесены в **Обзор**. Отдельная страница удалена, старый адрес `#settlements` открывает `#overview`. В списке рядом с фирмой показан один баланс: долг — красный минус, аванс — зелёный плюс, ноль — нейтральный. Карточка фирмы содержит историю пополнений и списаний за отгрузки, сведения об оплате и источник каждого поступления.

Директор и администратор видят общие итоги. Менеджер с доступом к **Обзору** видит только своих клиентов, свои отгрузки, поступления в своей области доступа и рассчитанные по ним диаграммы. Фильтрация выполняется сервером. Право на Обзор не открывает общий реестр банковских выписок. Назначенный клиент доступен и до первой отгрузки; для исторических клиентов без назначения используется принадлежность отгрузок. Явное назначение клиента другому менеджеру закрывает старому менеджеру доступ.

Для общего клиента с отгрузками разных менеджеров отображаются только поступления, зачтённые в собственные отгрузки, без чужих ссылок и сумм. Свободный общий аванс доступен руководству; карточка сообщает об ограниченной области расчёта. Повторное распределение всей оплаты между менеджерами не выполняется.

Диаграммы показывают поступления и отгрузки по месяцам с выбором периода и крупнейшие долги с переходом к фирме. Балансы и итоговые карточки относятся ко всей сохранённой истории; выбранный период ограничивает диаграмму.

**Отложено:** правила распределения списаний и долга по нашим организациям и банковским счетам нужно отдельно обсудить с пользователем. Напоминание и вопросы — [следующая задача](next-task-bank-balances.md).

По подтверждённому правилу пользователя у покупателя **общий баланс по ИНН** для трёх подключений: Сбер «НК АРТЭЛЬ», Сбер «АРТЕЛЬ» и Т-Банк «НК АРТЭЛЬ». Деньги из любого из них закрывают одну очередь отгрузок. В детализации каждого поступления сохранены банк, наша организация и счёт.

## Как работать

1. Добавьте клиента в справочник с правильным ИНН.
2. Создавайте отгрузки обычным способом. Сумма покупателя увеличивает его задолженность.
3. Загрузите выписку в разделе **Платежи**. Подтверждённые рублёвые поступления сопоставляются с ИНН плательщика и автоматически оплачивают самые ранние неоплаченные отгрузки этого клиента.
4. Откройте **Обзор**. Остаток поступления отражается как аванс. При следующей отгрузке этот аванс используется автоматически. Выберите фирму для просмотра истории.

Повторная загрузка той же банковской операции не прибавляет деньги второй раз. Переименование фирмы не мешает сопоставлению по ИНН. Два разных ИНН имеют отдельные остатки. Банковское списание не считается оплатой клиента; переводы между своими счетами также исключаются.

Пример:

| Событие | Долг | Аванс |
| --- | ---: | ---: |
| Отгрузки 40 000 и 30 000 ₽ | 70 000 ₽ | 0 ₽ |
| Поступление 100 000 ₽ | 0 ₽ | 30 000 ₽ |
| Отгрузка 20 000 ₽ | 0 ₽ | 10 000 ₽ |
| Отгрузка 30 000 ₽ | 20 000 ₽ | 0 ₽ |
| Поступление 10 000 ₽ | 10 000 ₽ | 0 ₽ |
| Поступление 20 000 ₽ | 0 ₽ | 10 000 ₽ |

В отгрузках колонки оплаты и долга используют тот же расчёт. Аванс хранится в расчётах фирмы, поэтому оплата отдельной новой отгрузки не превышает её сумму. Сотрудник видит оплату только своих отгрузок; банковский оборот всех клиентов ему не раскрывается.

## Что требует проверки

Отсутствующий или некорректный ИНН, противоречие ИНН отгрузки и справочника, неизвестная историческая оплата или сумма не заменяются догадкой. Такие строки помечаются для проверки. Поступление с правильным ИНН может создать аванс ещё до появления клиента в справочнике или его первой отгрузки.

Ранее внесённые исторические оплаты и старые привязки XLSX сохраняются. Их нельзя повторно загружать как новые банковские поступления без сверки: идентификатора связи между ручной исторической оплатой и банковской выпиской нет. В текущей задаче пользователь подтвердил отсутствие реальных данных для такого перехода; сценарии проверяются в изолированном тестовом хранилище.

## Получение данных из банка

Распределение выполняется по уже сохранённым выпискам. Страница обновляет расчёт при открытии, возвращении в окно и периодически, а также по кнопке обновления. Она не отправляет платежи и не делает запросы в банк.

Получение новых выписок сохраняет существующий порядок: для трёх подключений доступны ручное обновление и общий отдельно включаемый планировщик. Свежесть расчёта зависит от загруженного периода; дата последней успешной загрузки показана на странице.

Расчёт поддерживает все три подключения. С 24.09.2026 реальное получение выписок локально проверено также для Сбера «АРТЕЛЬ»: [подключение и результаты](sber-statements.md). Отсутствие загруженной выписки показано на странице отдельно для каждого источника.

Старые операции Сбера «АРТЕЛЬ» из отменённой интеграции не участвуют в балансе. Коннектор АРТЭЛЬ публикует полностью полученный и проверенный день через `replaceStatementDay` в `server/banking/statement-publication.ts` внутри атомарной мутации хранилища. Только операции счёта и дня с отметкой `settlementVerifiedDays` становятся доступными расчёту. Пустая подтверждённая выписка тоже публикуется: прежние операции этого дня архивируются, а их оплаты отзываются. Другие дни, счета и подключения остаются без изменений. Незавершённые страницы загрузки и архивы не учитываются.

Ошибка обновления не удаляет последнюю корректную выписку: сохранённые деньги остаются в расчёте, а рядом с источником показывается ошибка. При недоступности самого отчёта страница сохраняет полученные итоги с предупреждением об их актуальности.

## Устройство расчёта

`server/settlements.ts` строит чистую проекцию с точной десятичной арифметикой. Остаток воспроизводится из сохранённых отгрузок и уникальных активных банковских операций после перезапуска. Чтение не меняет хранилище и не создаёт дополнительные платежи.

Расчёт выполняется по всем отгрузкам до фильтров, пагинации и ограничения доступа сотрудников. При изменении/удалении отгрузки или исправлении банковской выписки распределение пересчитывается; освободившиеся деньги снова становятся авансом либо закрывают следующую отгрузку. Исходные суммы оплаты не перезаписываются результатом банковского распределения при редактировании.

Идентичность банковской операции определяется банком, собственным счётом и ID операции банка. Один платёж, попавший в два подключения того же банка и счёта, считается один раз. Одинаковые ID на разных счетах или в разных банках остаются независимыми платежами. Если две копии противоречат друг другу по значимым полям, они выводятся на проверку и не увеличивают баланс. Переводы между своими счетами исключаются и по ИНН, и по известному собственному счёту.

`GET /api/settlements` проверяет право на `overview`: полный отчёт возвращается директору/администратору, менеджеру — проекция его области данных через `server/settlement-scope.ts`. Итоги пересчитываются после фильтрации; общие банковские источники и очередь неразобранных поступлений менеджерам не передаются. Общий `/api/snapshot` не содержит банковского реестра взаиморасчётов.

Старое разрешение `settlements` читается как `overview`, сохраняя совместимость аккаунтов без перезаписи хранилища. В редакторе прав отдельного раздела «Взаиморасчёты» больше нет.
