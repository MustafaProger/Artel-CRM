# Выбор оптимизации CRM — 26.10.2026

Статус: исходное обоснование выбора. Реализация опубликована и проверена 26.10.2026; результаты, измеренный эффект и ограничения приведены в [отчёте о выпуске](saby-access-performance-2026-10-26.md). Ниже сохранены критерии выбора до реализации.

## Решение

Первым выпуском разделить построение оперативных данных и финансовых представлений. Проверки доступа Saby должны получать актуальные данные нужного рейса без вычисления финансовых показателей и общих сводок CRM. Сохранить существующий формат хранилища, единый исполнитель обмена, транзакции и протокол Saby.

Это наиболее обоснованный первый шаг по сочетанию ожидаемого эффекта и объёма изменений: предыдущий профиль выявил затраты на общий снимок, а текущий код вызывает его перед каждым внешним запросом Saby. Проверка прав сама по себе не использует денежные результаты.

## Основания в коде

Исследованы исходники выпуска `.local/etrn-refresh-scope/source`:

- `trip-saby-scheduler.ts`: `checkAccess` читает OperationsStore и вызывает `currentSnapshot` через request guard перед каждым сетевым запросом.
- `auth-scope.ts`: `requireWholeTrip` и `ownsShipment` используют состав рейса, роль, менеджера, принадлежность строк, закрепление клиентов и происхождение доставки из общей заявки.
- `trip-saby-signing.ts`: `authorizeSigningActor` дополнительно сверяет текущую учётную запись, поручение, попытку и связанный документ, включая инициатора восстановления.
- `trip-saby-workflow.ts`: `authorizeAutomaticTripSaby` сверяет доставки с обязательной ЭТрН, политику/выбранные сертификаты и основание водительского подтверждения.
- `shipment-operations.ts`: общий `currentSnapshot` рассчитывает все отгрузки, по умолчанию взаиморасчёты с банками, показатели сотрудников, обзор и месячные итоги.

Перед реализацией проверить свежий серверный drift и работать от актуального выпуска; основной dirty checkout не является надёжной базой для публикации.

## Сравнение вариантов

| Вариант | Оценка для текущей CRM |
|---|---|
| Увеличить ресурсы | Свежая диагностика не обнаружила дефицит RAM. Дополнительные ресурсы не убирают повторные вычисления. Не выбран первым шагом. |
| Кэшировать готовый результат на несколько секунд | Неприемлемо для проверок актуальных прав и оснований подписи: появляется окно устаревания. |
| Кэшировать весь снимок по общей revision | Возможен выигрыш между записями, но служебные записи Saby и банков тоже меняют revision. Это ограничивает повторное использование. Не основной механизм. |
| Вынести весь Saby в отдельный процесс | Может уменьшить блокировку HTTP, но оставляет лишние расчёты, добавляет расход памяти и требует межпроцессной защиты от двойного исполнения. Резервный следующий этап. |
| Сразу перейти на SQLite/PostgreSQL | Может улучшить выборочное чтение, но потребует миграции общего хранилища, транзакций и проверок всех подсистем. Не оправдано как первый фикс найденного пути. |
| Разделить оперативные данные и финансовые расчёты | Выбранный вариант: устраняет конкретную ненужную работу без миграции бизнес-данных и изменения исполнителя обмена. |

## Состав первого изменения

1. Выделить общий слой сборки и нормализации оперативных полей из существующего пути. Использовать его и в полном снимке, и в лёгком контексте прав. Не дублировать правила владельцев, исходных XLSX-строк, удалений, назначений и общих заявок.
2. Добавить явный тип контекста авторизации: текущие учётные записи, менеджеры/закрепления, оперативные строки рейса, связанные справочники и существующие основания обмена. Не маскировать частичный объект приведением к полному `Snapshot`.
3. Перевести request guards на этот контекст. Перед каждым внешним запросом по-прежнему читать актуальные данные; отзыв прав, удаление доставки, смена состава ЭТрН или поручения должны останавливать следующий запрос.
4. Убрать повторные линейные поиски в циклах: построить индексы по ID один раз для соответствующего снимка. Сохранить порядок, правила нормализации и обработку дубликатов.
5. Сохранить проверку целостности хранилища. Если старая сборка снимка обнаруживала повреждение или несогласованность, новый путь не должен молча пропустить ошибку. Проверки и расчёты разделять явно.

Один лишь `currentSnapshot(..., false)` отключает только банковский этап: расчёты остальных отгрузок, общий обзор и месяцы остаются. Этого недостаточно как окончательного решения.

## Последующие изменения — только по замерам

Если полный JSON-разбор остаётся существенным, отдельно рассмотреть ограниченный неизменяемый кэш проверенного разобранного содержимого с точным обнаружением внешних изменений. Сначала сравнить стоимость JSON.parse, клонирования и узких выборок. Нельзя без проверки заменить их structuredClone или выдавать общие изменяемые ссылки. Нынешние тесты защищают в том числе неизвестные поля, отрицательный ноль, миграции, внешнюю замену с тем же размером/mtime и отзыв сессии.

Расчётные представления можно повторно использовать по точному набору зависимостей, ограничивая память кэша. Служебная отметка Saby не должна автоматически приводить к пересчёту денежных итогов, если их входы не менялись. Общей revision и TTL недостаточно для такой схемы. Кэш прав по времени не вводить.

Если после сокращения вычислений пользовательские запросы всё ещё задерживаются фоновыми задачами, рассмотреть выделенный процесс/пул вычислений с единственным владельцем планировщика и проверкой блокировок. Не добавлять второй активный исполнитель Saby.

## Приёмка

- Сначала снять времена авторизованных рабочих API, задержку event loop, CPU и времена появления содержимого основных экранов. Повторить при активной фоновой обработке на одинаковом наборе данных и сценарии.
- На изолированной копии сравнить решения старых и новых проверок: разрешение/отказ, состав доступных строк, удалённые и смешанные рейсы, исторические менеджеры, общие заявки, исключённые из ЭТрН доставки.
- Отдельно изменить права и основание поручения между двумя внешними запросами: следующий запрос должен быть остановлен до отправки.
- Проверить неизменность финансовых результатов, XML/manifests, выбранных подписей, защит от повторных Create/Prepare/Execute, транзакций и истории. Для испытаний обмена использовать имитацию провайдера, не реальные подписи.
- Цель для основного горячего пути: минимум двукратное снижение времени проверки доступа на контрольном наборе. Это критерий приёмки, а не обещание двукратного ускорения всей CRM.
- Если цель не достигнута или ухудшились p95 рабочих API/память/корректность, решение пересмотреть до публикации. Само по себе снижение CPU не доказывает устранение задержек пользователя.
