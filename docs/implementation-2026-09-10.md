## Хранение и миграции

Стек сохранён: React 19, TypeScript, Vite, Node API, decimal.js. SQL-базы и SQL-миграций нет. Локальное рабочее состояние — `data/local-operations/operations.json` или `ARTEL_STORE_DIR`; production — приватный Blob `artel/operations.json`. Источник XLSX/JSON остаётся отдельным архивным снимком с контрольными суммами.

Изменения совместимы со старым состоянием: опциональные `accounts`, `work`, метки удаления справочников, отметка применения автопарка и `fields.shipment_type`. Они сохраняются обычной атомарной транзакцией, без отдельной команды миграции. Финансовые значения остаются десятичными строками; расчёты используют decimal.js с точностью 80, интерфейс выводит денежные суммы с двумя знаками.

Пароли хранятся как scrypt-хеши с индивидуальной солью. Случайные сеансы хранятся на сервере в виде хешей; cookie HttpOnly / SameSite=Strict, в production также Secure. Сеанс действует 8 часов. Выход, изменение пользователя/пароля и отключение пользователя отзывают соответствующие сеансы. Есть ограничение попыток входа и защита последнего директора. Область доступа проверяется на чтении и повторно внутри транзакции изменения. Локальный адрес и Origin / cloud same-origin защита сохранены.

Запуск локальной версии:

```sh
npm run dev
```

Открыть `http://127.0.0.1:5173`, создать директора на странице первого входа, затем пользователей в «Команды и роли». Тестовых пользователей в рабочем локальном или production-хранилище нет.

Перед будущей публикацией полного обновления необходимо задать **серверную** переменную `ARTEL_SETUP_TOKEN` в production Vercel. При первом входе через HTTPS она подтверждает право создать директора; после создания директора переменную можно убрать. Пароли и ключи в клиентскую сборку и Git не включать. Preview должен использовать собственный Blob и собственный ключ первоначальной настройки; подключать его к production ради пустого состояния не нужно. `requireAuthentication:false` применяется только явным серверным адаптером изолированных domain-тестов; runtime Vite и cloud его не используют.

## Очистка production: причина, резервная копия, проверка

Причина расхождения подтверждена по коду и живым данным: локальное и облачное рабочие состояния независимы, а локальная очистка не изменяла Blob. Production API до очистки возвращал 2 098 отгрузок, 2 979 платежей и 60 складских сводок. Browser storage хранит настройки интерфейса; операции туда не записываются. Сборка скачивает архивный источник, но не заменяет рабочий Blob. API отвечает без кеширования.

В рабочем состоянии очищены `shipments` и `paymentAllocations` (до очистки привязок было 0). Исторические отгрузки, платежи и складские сводки из неизменяемого источника выведены из рабочего учёта сохранённой отметкой `sourceOperationsCleared`. Это постоянное состояние хранилища; новые отгрузки продолжают записываться и читаться. Архивный XLSX/JSON сохранён для восстановления и не используется как повторный seed операций. UI не подменяет ответ пустыми списками.

Сохранены все 675 компаний, справочники и их поля, назначения, настройки. Учётные записи и «Работа» в исходной production-версии ещё отсутствовали; функция очистки сохраняет их, если они есть. Перед записью и после очистки выполнено сравнение сохраняемых данных. Производный список дублей и связи с удалёнными операциями не трактуются как самостоятельные бизнес-записи.

Резервная копия: `qa/cloud-reset-2026-09-10T10-57-29-310Z/operations-before.json`, права файла 0600. Проверены контрольная сумма оболочки, SHA-256 файла, идентичность источника и соответствие живого API выбранному Blob. `plan.json` фиксирует production-адрес, ETag и количество операций. `applied.json` подтверждает условную запись и повторное чтение. `live-create-check.json` подтверждает создание / повторное чтение / удаление после повторного деплоя. `production-verification.json` и снимок `production-empty-after-redeploy.png` — проверка опубликованного адреса и перезагрузки браузера.

В ходе проверки выявлена самостоятельная ошибка записи: сжатый Blob GET возвращал слабый `W/` ETag, а If-Match требует подходящую версию объекта. Сервер теперь запрашивает несжатое представление и отклоняет слабую версию. Условная запись сохранена. Пять тестов cloud adapter проходят; production создание после точечного деплоя вернуло 201. Механизм условной записи описан в [документации Vercel](https://vercel.com/docs/vercel-blob/using-blob-sdk).

Команды обслуживания (выполнять из корня; env-файл с production-доступом не входит в Git):

```sh
# Только проверить текущее состояние.
ARTEL_MAINTENANCE_TARGET=https://artel-crm.vercel.app node --env-file=.vercel/production.env --import tsx scripts/cloud-operations.ts verify qa/cloud-reset-2026-09-10T10-57-29-310Z

# Проверить возможность восстановления, ничего не записывая.
ARTEL_MAINTENANCE_TARGET=https://artel-crm.vercel.app node --env-file=.vercel/production.env --import tsx scripts/cloud-operations.ts restore-check qa/cloud-reset-2026-09-10T10-57-29-310Z

# ВОССТАНОВЛЕНИЕ старых операций — выполнять только при необходимости отката.
ARTEL_MAINTENANCE_TARGET=https://artel-crm.vercel.app node --env-file=.vercel/production.env --import tsx scripts/cloud-operations.ts restore qa/cloud-reset-2026-09-10T10-57-29-310Z
```

`restore-check` успешно проверен без записи. `restore` в этом задании не запускался. Скрипт откажется перетирать новые рабочие данные или настройки. Допускается только известная удалённая контрольная запись из протокола QA; для прочих изменений после очистки потребуется отдельно проверяемое объединение с резервной копией. Повторная очистка выполняется через новый `plan` и затем `apply <каталог плана>`, с новым бэкапом и совпадающим ETag. Ни одна из этих команд не вызывается при запуске, входе или деплое.

## Открытые вопросы

1. Цена продажи за литр АЗС: подтвердить или отклонить `сумма покупателя / литры`. До подтверждения формула не применяется.
2. КВП АЗС: правило отсутствует; новые значения не выдумываются и не уменьшают утверждённую прибыль.
3. Дата оплаты: подтвердить отдельный столбец в таблице. Схема и существующие значения сохранены; дата доступна в редакторе.
4. Оплата, долг и дни: использована действующая логика — только связанные платежи, долг = оплата − сумма покупателя, дни скрываются при полной оплате. Для другого поведения АЗС нужно отдельное правило. Интерфейс создания привязок банковских платежей не расширялся.
5. ЗП: формулы, начисления и процесс выплат не заданы; реализована только структура.
6. Сбербанк: в коде нет интеграции или банковского клиента. Есть только реквизиты компаний и чтение исходной выписки. Нужны конкретный продукт/API банка и его документация, sandbox / production-доступ, способ авторизации и сертификаты при необходимости, счета и организация, направление обмена, состав данных, периодичность, правила сопоставления и обработки дублей. Обмен не имитировался, банковские операции не инициировались.
7. Полное обновление, включая обязательный вход, ещё не опубликовано. До него нужно настроить production bootstrap и создать директора после публикации. Проверка разных пользователей выполнена локально, не в production.
