# Подпись Saby из CRM: проверенные возможности и условия, 30.09.2026

Это исследование протокола и план реализации. Прямое подписание из CRM **не реализовано и не проверено на действующем документе**. При исследовании не вызывались подготовка, выполнение этапа, регистрация сертификата, активация ключа или отправка SMS. Закрытые ключи, ПИН-коды и персональные реквизиты в документ не включены.

## Подтверждённая ситуация

Пользователь сообщил, что работает собственной учётной записью сотрудника с правом подписи; в Артэль подписание через Saby происходит сразу, без дополнительных окон. Позднее прямо подтвердил: **у НК Артэль подписи нет**. Отсутствие подписи перевозчика — реальное препятствие для полного подписанного обмена, а не просто предположение по пустому API-ответу.

Основной агент 30.09.2026 повторил отдельную авторизацию двух кабинетов и чтение `sabyCertificate.List` с `AddTrustedCertificates=true`, `PageSize=20`:

| Кабинет | Результат повторной проверки чтением |
| --- | --- |
| Артэль | 1 доступный зарегистрированный сертификат; `Certificate.Type="Client"`, `IsMobile=false` |
| НК Артэль | 0 сертификатов для текущего пользователя, включая доверенные |

Результат передан основным агентом в этой сессии; исследователь протокола не выполнял повторных запросов в аккаунты. Историческая проверка 29.09.2026 и её приватные доказательства описаны в [предыдущем отчёте](./saby-signing-api-2026-09-29.md); срок/валидность из того отчёта не выдаются здесь за новое измерение. Сетевой timeout браузера под VPN не доказывает недоступность API: основной агент подтвердил чтение через `curl --interface en0`.

`Client` не означает, что обязательно нужен новый USB-носитель. Это тип зарегистрированного сертификата; существующая установка Saby может уже использовать ключ на доступном устройстве или дистанционное подписание. Мгновенная подпись в веб-интерфейсе не доказывает, какой именно механизм используется и готов ли он принимать отложенные задания API.

## Наименьший путь к кнопке в CRM

Первым кандидатом является штатное **отложенное подписание Saby без дополнительного подтверждения**. CRM вызывает действие с `Сертификат.Ключ.Тип="Отложенный"`; вариант `"ОтложенныйСПодтверждением"` предназначен для отдельного подтверждения. Эти значения документированы в [методе выполнения действия](https://saby.ru/help/integration/api/all_methods/make_doc). Значение `Client` из списка сертификатов и режим `Отложенный` в запросе действия относятся к разным полям и не противоречат друг другу.

Этот путь позволяет инициировать подпись из CRM, сохраняя обработку ключа в установленном механизме Saby. Для него документация требует доступного ключа в СКЗИ, работающего десктопного Saby, входа владельца либо доверенного пользователя, активации ключа и включённого дистанционного подписания. Настройку проверяют отдельно для каждой организации. Если подтверждение требуется политикой доверия, код CRM не должен обходить её. Отложенные действия поддерживаются только для внешнего ЭДО. [Настройка отложенного подписания](https://saby.ru/help/integration/api/sequence/delegate/).

Для Артэль следует сначала установить, выполняются ли эти условия в уже используемой рабочей среде. Покупка нового носителя заранее не требуется. Для НК Артэль сначала подключается законно доступная подпись уполномоченного подписанта; выдача роли сотруднику сама по себе ключ не создаёт. Права/доверенность и регистрацию проверяют в кабинете НК отдельно.

Важное ограничение: отложенная задача не гарантирует жёсткую привязку фактической подписи к переданному отпечатку. Saby допускает подходящую по регламенту собственную или доверенную подпись исполнителя; сведения выбора не сохраняются как обязательная блокировка. Поэтому после обработки CRM должна прочитать документ и сопоставить фактического подписанта/организацию с ожидаемой стороной. [Условия выполнения действия, комментарий 6](https://saby.ru/help/integration/api/all_methods/make_doc).

## Точный контракт подготовки и выполнения

Общий JSON-RPC endpoint опубликован как `https://online.sbis.ru/service/?srv=1`; для транспортного обмена TMS публикует `https://tms.saby.ru/service/`. Ниже адаптированные структуры официальных примеров: значения в угловых скобках — placeholders, не проверенные рабочие идентификаторы.

### Подготовка актуальных файлов

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.ПодготовитьДействие",
  "params": {
    "Документ": {
      "Идентификатор": "<document-id>",
      "Этап": {
        "Название": "Отправка",
        "Действие": {
          "Название": "Отправить",
          "Сертификат": { "Отпечаток": "<certificate-thumbprint>" }
        }
      }
    }
  },
  "id": 1
}
```

Структура сверена с [публичным JSON-примером запроса](https://online.saby.ru/disksharedrest/a8f10408-5f99-44f7-b981-c31750c020e4_add4558f-8ced-4e73-8da8-12b2bc6244c3). В рабочей реализации предпочтительны `Документ.Редакция.Идентификатор` **вместо** `Документ.Идентификатор` и точный `Этап.Идентификатор`. Подготовка может менять XML; подпись относится только к итоговым байтам. [Описание подготовки](https://saby.ru/help/integration/api/all_methods/develop_doc).

В скачанном [официальном ответе](https://online.saby.ru/disksharedrest/0b4e0414-7cb6-41c1-889d-ada892a0df40_6ab371a5-e5e3-4991-9b8b-4b3513ed044d) **`result` сам является документом**: непосредственно содержит `Идентификатор`, массивы `Редакция` и `Этап`; дополнительного `result.Документ` нет. Внутри этапа `Действие` и `Вложение` — массивы. Поля вложения включают `Идентификатор`, `Модифицирован`, `Файл.Имя`, `Файл.Ссылка`. Общая схема также описывает `Файл.Хеш` при соответствующей подготовке; старый пример его не содержит, нельзя требовать наличие хеша в каждом ответе. Фильтровать реальные файлы для подписи нужно по данным подготовки, а не подписывать все вложения подряд.

### Отложенное действие

```json
{
  "jsonrpc": "2.0",
  "method": "СБИС.ВыполнитьДействие",
  "params": {
    "Документ": {
      "Идентификатор": "<document-id>",
      "Этап": {
        "Название": "Отправка",
        "Действие": {
          "Название": "Отправить",
          "Сертификат": {
            "Ключ": { "Тип": "Отложенный" },
            "Отпечаток": "<certificate-thumbprint>"
          }
        }
      }
    }
  },
  "id": 2
}
```

Основа — [публичный запрос с подтверждением](https://online.saby.ru/disksharedrest/0c8b677b-bdf6-4506-8fd2-420544e0e2a7_e208ee0b-14cc-4e5b-a665-d76654836039); здесь изменено только документированное значение режима на `Отложенный`. Это **не результат успешного вызова из CRM**. В официальном [ответе отложенной обработки](https://online.saby.ru/disksharedrest/b5db64d1-fbb8-4deb-93f2-3269be53be8d_b5304501-7904-411a-8333-1034105a04db) `result.Состояние.Код="23"`, `Название="Ожидает подписания"`. При таком состоянии отправку завершённой считать нельзя.

Документация имеет расхождение формы `Действие`: общий контракт и обычный пример используют массив из одного объекта, отдельный официальный deferred-пример — объект. Клиент должен зафиксировать принятую TMS форму интеграционной проверкой; не объявлять обе формы подтверждёнными именно для ЭТрН.

### Альтернатива: локальная отсоединённая подпись

Если штатный deferred-путь не подходит, возможен отдельный браузерный криптографический адаптер: сервер подготавливает документ и передаёт только окончательные байты/хеш, доступное устройство подписывает, CRM отправляет полученную подпись. Проверенный фрагмент `params` из [обычного официального запроса](https://online.saby.ru/disksharedrest/2d9efd32-9e6f-4913-b4ea-53335f735be0_f47081dd-92ae-47cd-b2e8-3e125f8e3f87):

```json
{
  "Документ": {
    "Идентификатор": "<document-id>",
    "Этап": {
      "Название": "Отправка",
      "Действие": [{
        "Название": "Отправить",
        "Сертификат": { "Отпечаток": "<certificate-thumbprint>" }
      }],
      "Вложение": [{
        "Идентификатор": "<prepared-attachment-id>",
        "Подпись": [{ "Файл": {
          "Имя": "<attachment-name>.sgn",
          "ДвоичныеДанные": "<base64-detached-signature>"
        }}]
      }]
    }
  }
}
```

`ДвоичныеДанные` здесь содержат файл подписи, **не исходный XML и не голый хеш**. Прямой публичный контракт вызова Saby Plugin из произвольного CRM origin не подтверждён. Существование API CryptoPro Browser plug-in само по себе не означает, что нужный компонент уже установлен или применим к текущей среде. Такой адаптер — отдельная реализация и отдельная проверка совместимости; для текущего выпуска его нет.

## Что можно проверить только чтением

| Метод | Что узнаём | Чего он не доказывает |
| --- | --- | --- |
| `sabyCertificate.List` | Зарегистрированные сертификаты пользователя; доверенные при `AddTrustedCertificates=true` | Доступность закрытого ключа в эту минуту |
| `sabyCertificate.List` с `Parameter.Employee` | Сертификаты конкретного сотрудника при достаточных правах | Что они доверены текущему пользователю; `AddTrustedCertificates` для такого поиска запрещён |
| `sabyCertificate.Read` с `Parameter.CertificateThumbprint` | Детали сертификата, владелец, организация, срок/валидность | Готовность desktop/СКЗИ для сертификата `Client` |
| `СБИС.ПроверитьСертификаты` | Проверка действительности/отзыва сертификата | Онлайн-доступность устройства и готовность подписи |

Источники: [List](https://online.sbis.ru/page/kbase_entity/7fce61eb-e6ae-438c-90ac-20e4431aa6df?folderId=d1be9d28-1ddb-4aec-9f0f-a44a447a1b94), [Read](https://online.sbis.ru/page/kbase_entity/7fce61eb-e6ae-438c-90ac-20e4431aa6df?folderId=e99d9676-214a-47e3-86a5-4d903269ea66), [ПроверитьСертификаты](https://link.saby.ru/page/kbase_entity/7fce61eb-e6ae-438c-90ac-20e4431aa6df?folderId=e6320b65-a55b-44b3-8161-d7acd199cee9).

`CertificateAccess.Available` в Read/List описан **только для Cloud**, принадлежащих или доверенных пользователю. Применять его отсутствие к `Client` как признак недоступности нельзя. Публичного read-only признака «Client ключ сейчас доступен desktop и готов выполнить deferred» в просмотренных контрактах не найдено.

`sabyCryptoOperation.Create` создаёт операцию, это не диагностическое чтение. В [контракте](https://link.saby.ru/page/kbase_entity/7fce61eb-e6ae-438c-90ac-20e4431aa6df?folderId=d0f33c07-980b-4e16-bb60-1bcb277aba3e) сказано о некоторых типах сертификатов, а универсальная работа с текущим `Client` не подтверждена. Его не следует пробовать как «проверку доступности». Активация сертификата и запрос кода также не являются чтением.

## Ответ перевозчика: титул 1110362

Официальный [TMS API заказа-заявки](https://link.sbis.ru/page/kbase_entity/2ecadb1a-5bd4-4858-83f4-74d83eb5735a?folderId=8f551622-a492-491f-8e75-605e0c41998d) описывает генерацию отправительского `1110361`: `СБИС.СгенерироватьВложение`, тип `ЗаказЗаявка`, подтип `1110361`, версия и подстановки. Для перевозчика описана запись XML ответного титула через `СБИС.ЗаписатьВложение` с ID входящего документа, затем действие `Утверждено` либо `Отклонено`.

Точный запрос/ответ **генератора `1110362` не подтверждён** найденными официальными материалами. Подмена `1110361` на `1110362` без отдельного контракта недопустима. Для реализации нужны официальный XSD/спецификация ответа перевозчика и подтверждённый поддерживаемый способ генерации, либо локальное формирование XML с проверкой по этой схеме. Публичную Postman-коллекцию обнаружили, но её JSON в этой проверке не удалось получить; содержимое не считается исследованным.

Первое подписывающее действие ЭТрН `Погружен` — фактическое событие погрузки, а не универсальная отправка заявки. Выбирать его автоматически ради продвижения цепочки нельзя. [TMS API ЭТрН](https://online.saby.ru/page/kbase_entity/2ecadb1a-5bd4-4858-83f4-74d83eb5735a?folderId=f6d99b24-2393-4782-8f65-16a9e0f9e665).

## Условия реализации и приёмки

1. Подключить подпись НК Артэль и права/полномочия её подписанта; повторно прочитать сертификаты именно этого кабинета.
2. Для Артэль проверить существующий механизм подписи и настройки deferred; не требовать новый носитель, если действующая среда уже обеспечивает нужный доступ.
3. Зафиксировать генерацию и ФЛК титула `1110362`; выбрать действие из реально доступного этапа.
4. Реализовать серверную задачу подписи, привязанную к аккаунту, организации, документу, редакции, этапу, действию и вложениям. Браузер не должен выбирать произвольный чужой document ID, URL скачивания или подменять подготовленные байты. Ключ/ПИН остаются в существующей криптографической среде.
5. После явного действия пользователя инициировать один переход. При timeout сначала перечитать состояние, не повторять подпись/отправку вслепую. Мониторинг каждую минуту должен только читать и показывать ожидание/ошибку/завершение; сам по себе он не подписывает.
6. Отдельно проверить действительный документ: подготовка → подпись нужной стороны → read-back подписи и состояния → защита от дубля после неопределённого ответа → следующий этап в другом кабинете. Общий HTTP 200 либо статус 23 не являются приёмкой подписания.

До этих проверок корректный продуктовый статус — доступный обмен/мониторинг с явно отображаемой необходимостью подписи НК, а не рабочая кнопка «Подписать» с неподтверждённым механизмом.
