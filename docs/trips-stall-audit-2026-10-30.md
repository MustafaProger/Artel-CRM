## Механизм общей ошибки и почему установленное исправление не помогло №47–49

1. В прежней версии `etrn-service.ts:670–673` отсутствие нативной связанной ЭТрН порождало `SabyError('unknown', ..., true)` с текстом со скриншота.
2. В обработчике этой ошибки (`:749–756`) при отсутствии ID/намерения создания выбирался `status='error'`, несмотря на признак неопределённости.
3. Workflow останавливает цикл на первой доставке без `draft` и сохраняет `phase='error'` — нынешний `server/trip-saby-workflow.ts:565–585`.
4. Планировщик исключает `error` — `server/trip-saby-scheduler.ts:41–55`. Поэтому отсутствие новых проверок с вечера 29.10 закономерно; общий фон CRM работает, что видно по обновлениям №45 и других записей.
5. В нынешнем коде ожидание исправлено: возвращается `pending + waitingForNativeDraft` — `server/etrn-service.ts:744–752`. Но этот код не достигается для старых записей, уже исключённых из планировщика.
6. Разрешение нового протокола `orderConsignmentCreationVersion=2` добавляется при создании нового workflow (`server/trip-saby-workflow.ts:118`). Исторические записи автоматически его не получают. №45 переведён адресно отдельным восстановлением; №47–49 остались на прежнем протоколе.

Просто вернуть старые рейсы в очередь недостаточно: без адресного перехода на v2 они продолжат ждать нативный документ. Это явно покрыто `tests/etrn-order-creation.test.ts:206–210`.

Все ссылки на текущие исходники относятся к `.local/auth-performance-release-20261030/source/`; старый участок — `.local/address-receivers-20261029/source/`. Текущие 782 файла побайтно совпали с manifest действующего выпуска.

В **08:23:23 МСК** выполнен один адресный запрос `СБИС.СписокСлужебныхЭтапов` по ID №43, организации отправителя и с явным `Блокировать=Нет`. Saby вернул пустой массив документов без ошибки. Для текущей интеграционной учётной записи служебный этап не показан; это не доказывает его отсутствие в кабинете владельца подписи или внутренней очереди Saby. По официальному API без явного `Блокировать=Нет` запрос мог бы занять события на минуту; такой блокировки аудит не запрашивал. [Параметры метода Saby](https://saby.ru/help/integration/api/all_methods/stage_doc/).

Тип `Отложенный` соответствует режиму без отдельного подтверждения владельца; это отличается от `ОтложенныйСПодтверждением`. Для завершения такого подписания Saby требует доступную подписывающую среду. Наличие действующего сертификата само по себе не доказывает доступность исполнителя. По обычному чтению документа нельзя установить, что именно задержало подпись: состояние исполнителя, очередь или внутренняя обработка Saby. Не доказаны истечение сертификата, выключенный компьютер, неисправность носителя или необходимость ручного подтверждения. [Описание отложенного подписания Saby](https://saby.ru/help/integration/api/sequence/delegate/doc), [требования к подписывающей среде](https://saby.ru/help/integration/api/sequence/delegate/).

## Две неточности интерфейса

- У №47–49 фраза «Автоотправка сохранена. CRM продолжит обмен в фоне» формируется по наличию разрешения `autoAuthorization`, хотя `phase=error` отключает мониторинг. Это противоречие подтверждено кодом `trip-saby-workflow.ts:274–306`.
- У №45 обе ЭТрН созданы, но снимок показывает этап 6. Каждый проход workflow временно записывает `creating_etrn` перед возвратом в `sending_etrn` (`:560`, `:585`). UI может прочитать эту промежуточную фазу и держать её до следующего минутного опроса. Такой механизм подтверждён кодом, но точная причина именно присланного кадра без его HTTP-ответа не доказана. В прочитанном состоянии `sending_etrn` должен отображаться этап 7.
