# Аудит создания прямой ЭТрН — 21.10.2026

## Вывод

Первый шаг CRM основан на неподтверждённом допущении: отдельная запись ConsignmentNote без XML и номера используется как резервирование номера. Специализированная документация показывает запись с XML Т1 либо генерацию XML по подстановкам. Отдельный протокол резервирования пустой ЭТрН там не описан. Это не доказанный запрет Saby и не установленная причина первоначального HTTP500.

Роли в реконструированном запросе №27 правильные: НашаОрганизация, Грузоотправитель и ТранспортнаяКомпания — НК; Грузополучатель — клиент. Endpoint TMS, метод, тип ConsignmentNote и название регламента соответствуют справке. Предварительный TransportOrder в показанной последовательности API не требуется.

## Код и официальный пример

`/Users/mustafa/.codex/worktrees/nk-direct-autostart/Artel-CRM/server/etrn-service.ts:390`: полный титул строится в памяти с временным номером «1», затем Номер и Вложение удаляются. Перед сетью сохраняется reservationAttempted=true. После ответа планируются сохранение ID, чтение номера и загрузка XML в тот же ID. №27 остановился на первой записи; XML не отправлялся. Та же последовательность присутствует в operator-notifications worktree.

`SabyClient.reserveNumberedDocument` — наша обёртка над обычным СБИС.ЗаписатьДокумент, а не специальный метод резервирования Saby. В `docs/saby-protocol-research-2026-09-30.md:21` пустой черновик прямо обозначен как предложение, не проверенное живой записью.

Официальные JSON-примеры записи и генерации раскрыты в браузере. Пример записи содержит Вложение[].Файл.ДвоичныеДанные: base64 XML в Windows-1251. В XML задан НомерТрН, хотя верхнего JSON Номер нет. В генерации НомерТрН также передаёт вызывающая система; результат содержит сформированное вложение. Этот пример не подтверждает выдачу номера реестра.

Общая справка: при отсутствии JSON Номер используется номер формализованного файла либо настройки реестра. Поэтому добавление XML с CRM-UUID или номером рейса не сохраняет автоматически нумерацию Saby. Нельзя самостоятельно выбирать последний номер +1. Требуется подтверждённый источник номера.

Таблица справки говорит не передавать Имя при создании; раскрытый пример содержит Файл.Имя. Это противоречие документации, отсутствие Имя в нашем builder не объявлено ошибкой. Вложенность Файл.ДвоичныеДанные и кодировка совпадают. Наш serializer заполняет УИД_ТрН значением attemptId; в официальном образце УИД отсутствует. До исправления отдельно проверить присвоение операторского УИД и результат Prepare; это не причина первой ошибки, где XML не передавался. Полная пригодность будущего XML для форматно-логического контроля в этом аудите не заявляется.

## Исправленный порядок для ещё не начатой попытки

1. Зафиксировать факты, роли, полномочия и согласованный источник номера; сформировать и проверить XML Т1.
2. Создать документ единственным СБИС.ЗаписатьДокумент с XML. Не подставлять выдуманный provider ID. Пустое резервирование допустимо использовать только после подтверждения Saby для этого endpoint/type.
3. До сети сохранить факт попытки и отпечаток точного запроса; после ответа немедленно сохранить ID. Перечитать документ, проверить номер, стороны, редакцию и XML.
4. Продолжать Т1 и Т2 в том же документе. Неизвестный исход записи означает сверку, а не автоматический повтор.
5. Сохранять безопасную диагностику HTTP/JSON-RPC: метод, время, request ID, коды и очищенные сведения. Повторный вызов не восстановит утраченный ответ №27.

Это спецификация, не опубликованное исправление. Источник номера ещё требует решения; бизнес-нумерация самовольно не менялась.

Чтение старой ЭТрН через TMS успешно. Все 6 RPC — HTTP200 без JSON-RPC ошибки. Состояние №27 до/после совпало полностью: changedPaths=[], protectedStatePreserved=true. Изменяющих RPC и CRM writes — 0.

Примечание — метка поиска, не документированная гарантия серверной дедупликации. JSON-RPC id также не следует считать ключом однократной записи. Пустой поиск не доказывает откат. СписокИзменений не закрывает эту неопределённость: справка предупреждает, что при ошибке запуска завершённых событий может не быть.

Безопасны два пути:

- Saby возвращает существующий ID. Прочитать его в НК, сверить первоначальную попытку, метку, дату, стороны, редакцию и вложения; исключить неоднозначность и чужие изменения. Привязать подтверждённый документ. Если Т1 отсутствует — добавить XML в этот ID с его номером; если есть — сверить и продолжить с подтверждённого этапа.
- Saby подтверждает по журналу откат и отсутствие записи. Сохранить доказательство; подготовить адресное восстановление с историей прежней ошибки и новым однократным вызовом по исправленному протоколу. Не стирать историю и не сбрасывать флаг ради кнопки. Снимки, массы, факты и разрешение сохраняются; актуальные полномочия сверяются повторно.
