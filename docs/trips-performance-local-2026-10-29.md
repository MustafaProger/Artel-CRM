## Аудит цепочки

Замеры пользователя: создание 6,18 с, удаление 7,89 с, карта 4,50 с. Они не повторялись записью в production. Их полное происхождение этим этапом не установлено.

1. До изменения вход в «Рейсы» ждал общего `/api/snapshot?shipments=omit`. `omit` удалял строки из ответа уже после расчёта общего снимка, включая банковские распределения. Затем параллельно запрашивались список рейсов и заявки, даже когда открыта только вкладка заявок.
2. POST/PATCH/DELETE сначала авторизуются свежим чтением, затем входят в общую очередь core, повторно читают актуальные данные под transaction latch, выполняют проверки и записывают весь core. Событие отмены — статус `cancelled`, история и запись идемпотентности сохраняются. Это не физическое удаление записи.
3. После подтверждения UI делал три дополнительных GET: snapshot, shipment-trips и trip-requests. Карточка обновлялась после этой дополнительной работы. Отмена формы также обновляет список — это сохранено для сверки после конфликтов/неизвестного исхода.
4. GET заявок повторно читал хранилище после входной авторизации. Для заявок использовался `currentSnapshot(..., false)`: банковские распределения отключены, но расчёты отгрузок, агрегаты и месячные сводки всё ещё выполнялись.
5. Каждый переход между вкладками обновлял оба списка. Карта загружается отдельным JS-модулем, рисует известные точки из проекции; сегодня/завтра определяются по Москве. Геокодирование неизвестных точек идёт отдельно, с дедупликацией, очередью и локальным кэшем. `/geocode` может ожидать результат до 5 секунд и после ожидания заново проверяет права/версию/адрес. Это ожидание не удерживает бизнес-транзакцию. Сохранение заявки не ждёт внешнего геокодера; локальное чтение/перенос результата старого кэша внутри транзакции возможно.
6. Изображения Яндекса проходят серверный proxy: до и после provider await выполняется свежая авторизация, то есть два чтения на изображение. Существуют cache, ограничение параллельности и частоты. Эти проверки и провайдер не менялись. Время внешнего Яндекса и первичного поиска адресов остаётся отдельной неизвестной частью пользовательских 4,50 с.

Серверная диагностическая выборка только чтением: core **6 168 589 байт**, work **4867 байт**, 147 хранимых shipment overrides, 74 заявки, 3 активные. `banking.operations` содержит 558 строк; это не заявляется суммой всех банковских коллекций. Лимиты 2 CPU/1 GiB. Одно наблюдение CPU 154,89%, память 685,5 MiB; накопительный `nr_throttled=3035` из 13220 периодов. Накопительная статистика не доказывает throttling именно во время пользовательских действий. Сами по себе эти данные не доказывают «медленный диск» или причину всех 6–8 секунд.

## Сравнение вариантов

| Вариант | Польза | Цена/ограничение | Решение |
|---|---|---|---|
| Только оптимистическое скрытие карточки | Быстрее визуальная реакция | Не ускоряет подтверждение, усложняет неизвестный исход | Не выбран |
| Только облегчённые проекции и меньше GET | Быстрее чтение, вход и обновление UI | Почти не устраняет ожидание core backlog | Включён как часть решения |
| Отдельная очередь допуска заявок + прежняя транзакция | Заявка проходит после текущей записи, не ждёт всю пачку core | Полный core всё ещё кодируется и записывается | **Выбран вместе с предыдущим пунктом** |
| Третий файл заявок | Может уменьшить объём записи | Потребуются новый pointer/миграция, multi-file WAL, атомарное потребление заявок рейсами, обновление backup/recovery/tooling | Не требуется для доказанного выигрыша текущего этапа |
| Переход на транзакционную БД | Устраняет перезапись общего JSON в перспективе | Общая миграция CRM и интеграций, существенно шире этой задачи | Отдельный проект при дальнейшем росте |

Выбор подтверждён промежуточным замером: облегчение проекции снизило callback примерно с 6 до 2 мс, но под шестью фоновыми записями создание оставалось около 452 мс. Отдельная очередь затем уменьшила именно ожидание подтверждения. Это не обещание универсальной скорости при любой нагрузке.

## Что изменено

- `mutateTripRequests` использует отдельный FIFO admission lock в существующем Work partition. После допуска — прежние `transaction.lock`, load, проверки, encode, fsync/rename и redo WAL. Активную транзакцию не прерывает. Другая очередь продолжает продвигаться; тест проверяет отсутствие вытеснения всего core потоком заявок. Старый flat adapter и Blob storage используют прежний путь.
- **Нового файла данных нет.** Pointer `artel-work-partition-v1`, core/work layout, общий справочник/ID и согласованный export/backup прежние. `trip-requests-queue.lock` — временная блокировка. Её аварийная очистка добавлена в entrypoint только после захвата lifetime lease; `commit.json` не удаляется.
- Новый контекст рейсов отдаёт компании и справочники через прежний `scopeSnapshot`, без финансового снимка. Сохранены структурная проверка, историческое определение ролей компаний и канонизация менеджеров. Контекст и общая очередь заявок по-прежнему имеют разные, прежние правила видимости. Контекст перемонтируется при смене пользователя/версии доступа.
- GET заявок использует одно свежее входное чтение. Записи и ответы после внешнего ожидания заново авторизуются. Сессии и права не кэшируются по TTL.
- UI применяет только результат успешного POST/PATCH/DELETE. Старый GET не перетирает более позднее подтверждение. Ошибки не скрывают запись и не закрывают диалог. Убраны три GET после успешного изменения заявки. Рейсы загружаются при открытии их вкладок, а переход на карту обновляет только заявки; известные точки доступны сразу.
- В восстановлении потерянного PATCH дополнительно сравнивается дата выполнения: чужая дата больше не считается подтверждением собственного повтора. Исходный idempotency key и тело повторной отправки сохраняются.

## Воспроизводимый HTTP ABBA

`benchmark-final.json`, исходные `abba-0-baseline.json` … `abba-3-baseline.json`. Одна машина macOS/Node, loopback, порядок baseline → candidate → candidate → baseline. 30 образцов на действие/режим/версию, всего 360 HTTP-действий; 3500 синтетических банковских операций, 180 отгрузок, реальный split store с core 6 552 241 байт (6,25 MiB). Внешних вызовов 0. Измеряется получение полного успешного HTTP-ответа после фиксации, не анимация. Во время этой серии другие QA-процессы этого чата не запускались; нагрузка остальных приложений машины не контролировалась.

| Действие | До без нагрузки, медиана/p95 мс | После без нагрузки | До с 6 core-записями | После с 6 core-записями |
|---|---:|---:|---:|---:|
| Создать | 86,9 / 99,1 | 78,9 / 86,5 | 476,6 / 613,3 | 148,2 / 178,2 |
| Список | 27,9 / 29,7 | 12,6 / 18,4 | 94,0 / 107,6 | 12,5 / 12,9 |
| Удалить | 90,3 / 99,9 | 78,4 / 84,8 | 490,3 / 593,7 | 151,7 / 177,6 |

Под нагрузкой admission+load создания: медиана 401,6 → 76,4 мс; удаления 416,6 → 82,4 мс. Сам commit (кодирование/валидация/файловая запись вместе) остаётся около 55–64 мс. Полная пачка «6 core + создание»: 476,6 → 474,0 мс; «6 core + удаление»: 490,4 → 477,0 мс. Ускорена очередность пользовательского ответа, а не сокращён объём всех записей. Данные остальных банковских строк сверены точно.

`reads` в отдельных JSON считает вызовы фасада `OperationsStore.read`, а не физические syscalls: mutation дополнительно загружает данные внутри partition. У GET сокращение 2 → 1; при записи входное чтение и свежая транзакционная загрузка сохранены.
