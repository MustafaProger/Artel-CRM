# Новые заявки №13 и №14 — 07.10.2026

## Подтверждённая причина

Новые отгрузки сохранены в CRM; Saby уже присвоил общим заявкам номера 13 и 14. Обе автоматические цепочки остановились до первого Prepare/Execute отправителя с сообщением «Saby не вернул единственный доступный этап и титул для подписания». Поручение, выбранные сертификаты и исходные документы существовали; повторное создание отгрузок не требуется.

Чтение Saby показало одинаковый ответ: исходящий `TransportOrder`, состояние `0`, `ТекущиеЭтапы: []`, единственный `Этап` «Отправка» с действием «Отправить». Действие содержит выбранный сертификат с активным ключом `Отложенный`. Код считал наличие пустого `ТекущиеЭтапы` запретом использовать переданное самим Saby действие. Поэтому ошибка сохранялась как постоянная блокировка, а планировщик её больше не проверял.

Это отдельная причина от прежних ошибок №11. Повторная настройка доверия, МЧД или сертификатов для исправления этого дефекта не требовалась.

## Изменение

- Только для исходящего черновика `TransportOrder` в состоянии `0` с явным пустым массивом текущих этапов разрешён первоначальный этап «Отправка» из ответа Saby. Завершённые, неактуальные, служебные и неоднозначные этапы не принимаются. Непустой или некорректный список текущих этапов не подменяется резервным поиском.
- Существующее автоматическое поручение может продолжиться только после этой точной ошибки предварительной проверки, если нет никаких сохранённых признаков Prepare, файлов, Execute или начатой обработки перевозчика. Права, неизменность поручения/политики, стороны, редакция, содержимое и доступность сертификата снова проверяются штатным путём.
- Неоднозначные ранее начатые попытки, ручные поручения и другие блокировки не перезапускаются. Новые документы взамен существующих не создаются.
- Режим выбранной подписи проверяется по текущему действию из свежего `ПрочитатьДокумент` до подготовки, после неё и перед Execute. Дублирующее требование того же объявления режима в ответе `ПодготовитьДействие` удалено: подготовка использует сертификат для реквизитов подписанта, а режим задаётся при выполнении. Отзыв текущей возможности всё равно запрещает Execute.

Официальная документация: [структура документа и этапов](https://saby.ru/help/integration/api/all_methods/object), [подготовка действия](https://saby.ru/help/integration/api/all_methods/develop_doc). Конкретная форма ответа с пустым массивом установлена непосредственным чтением №13 и №14, а не предположением по документации.

### Различие способов

[Saby документирует дистанционную работу](https://saby.ru/help/ep/additionally/coding/remote_use): пользователь может подписывать на устройстве без собственного носителя, обращаясь к ключу на другом устройстве. Для разных кабинетов нужны соответствующие подключения приложения; доверие позволяет использовать подпись другому сотруднику. Это объяснение возможного механизма, а не подтверждение конкретной установки пользователя.

В [инструкции внешней обработки](https://saby.ru/help/integration/1C_set/modul/sign_doc) дистанционное и отложенное подписание описаны раздельно: первое в этой обработке использует ExtSDK2, второе поддерживается ExtSDK2 и API. Поэтому нативную кнопку нельзя автоматически приравнивать к реализованному deferred-запросу. Эта инструкция сама по себе не устанавливает отсутствие иных API дистанционного подписания.

По [описанию Execute](https://saby.ru/help/integration/api/all_methods/make_doc) для отложенного режима документирован `Ключ.Тип`; обязательности передачи всего объекта ключа, отдельного поля пользователя или подписанта не установлено. `Исполнитель`/`Подразделение` перечислены как необязательные; явное требование исполнителя CRM проверяет. Комментарий 6 допускает окончательный выбор подходящей собственной/доверенной подписи обработчиком, поэтому обязательна сверка фактического сертификата после выполнения.

### Что проверено в существующей реализации и архивах

### Личная КЭП и МЧД — отдельная альтернатива

[ФНС разъясняет](https://www.nalog.gov.ru/rn53/news/activities_fts/15155637/), что представитель может использовать одну личную КЭП для нескольких организаций с МЧД от каждой. [Saby предусматривает МЧД для перевозочных документов](https://saby.ru/help/ep/mchd/create), в том числе стороннему представителю. Доверенность подтверждает полномочия, а документ всё равно подписывается электронной подписью. Доверие к использованию существующей чужой подписи и собственная КЭП с МЧД — разные способы; скриншоты доверия не устанавливают наличие или отсутствие отдельной МЧД у пользователя.

Текущая CRM этот альтернативный сценарий полноценно не реализует: `normalizeSigningCertificate` требует корпоративный ИНН/КПП, политика запрещает один отпечаток для обеих сторон; нет полного процесса регистрации/проверки/прикрепления МЧД. Формат транспортного документа допускает электронную доверенность, но одного снятия фильтров недостаточно. Это ограничение реализации, **не установленная причина** ожидания текущих выбранных КЭП. Менять подписанта/полномочия уже подготовленных №13/14 нельзя.

Мобильный способ и Госключ нельзя автоматически считать безоператорной заменой. На странице мобильной ЭП ответ скрытого раздела о подписании без подтверждения прочитать не удалось; абсолютную невозможность такого режима эта проверка не устанавливает. Метод `sabyCryptoOperation.Create` описывает работу с мобильной ЭП, допустимость использования текущих `Client` КЭП им не подтверждена.
