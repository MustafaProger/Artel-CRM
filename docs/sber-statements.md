# Выписки Сбера для ООО «НК АРТЭЛЬ»

Реализовано 16.09.2026. Сервер локальной CRM получает реальные данные промышленного Sber API. Публикация этой версии CRM и настройка её облачного окружения в эту проверку не входят.

## Работа в CRM

Откройте **Платежи → Банковские подключения → СберБизнес — НК АРТЕЛЬ**. Начальный период — с 01.09.2026 по текущую дату Москвы. Выберите даты, нажмите «Показать период», затем «Обновить из банка», если нужно получить свежие сведения. Один выбранный период ограничен 31 днём.

Верхняя таблица показывает начальный остаток, поступления, списания и конечный остаток каждого дня. Переключатель скрывает только дни, для которых банк подтвердил нулевые поступления и списания. «Не передано» означает отсутствие значения в ответе банка.

Нажмите дату для просмотра операций дня. Поиск учитывает название контрагента, ИНН, счёт, назначение и номер документа. Фильтр направления оставляет поступления или списания. «Показать весь период» отменяет выбор дня.

Нажмите операцию для полного назначения, реквизитов плательщика и получателя и сведений о документе. Кнопка загрузки подробностей запрашивает отдельный банковский ресурс. Время показывается только при его наличии в ответе; время без часового пояса сохраняется как передано банком.

При сбое полная сохранённая выписка остаётся доступной. «Продолжить загрузку» повторяет незавершённый день и загружает оставшийся период. Закрытие экрана прекращает автоматическое продолжение; уже выполненный серверный шаг может завершиться, а прогресс сохранится. Время успешной синхронизации меняется после полной загрузки периода. Это интеграция только для просмотра: отгрузки и распределение платежей не изменяются.

## Серверная конфигурация

Локальные секреты находятся в игнорируемой `.env.local` с правами `0600`. В размещённой CRM требуются защищённые серверные переменные окружения. Значения не нужно копировать в документацию или клиентский код.

| Переменная | Назначение |
| --- | --- |
| `ARTEL_BANK_SBER_NK_CLIENT_ID` | Идентификатор сервиса |
| `ARTEL_BANK_SBER_NK_CLIENT_SECRET` | Секрет сервиса |
| `ARTEL_BANK_SBER_NK_TLS_PFX_BASE64` | Контейнер клиентского сертификата в base64 |
| `ARTEL_BANK_SBER_NK_TLS_PASSPHRASE` | Пароль контейнера |
| `ARTEL_BANK_SBER_NK_TLS_CA_BASE64` | Доверенная PEM-цепочка в base64 |
| `ARTEL_BANK_SBER_NK_ACCESS_TOKEN` | Первоначально выпущенный ключ доступа |
| `ARTEL_BANK_SBER_NK_REFRESH_TOKEN` | Первоначальный ключ обновления |
| `ARTEL_BANK_SBER_NK_ACCESS_TOKEN_EXPIRES_AT` | Необязательный подтверждённый срок access token, миллисекунды Unix |
| `ARTEL_BANK_ENCRYPTION_KEY` | 32 байта ключа AES: 64 hex-символа либо base64 |

Новая пара токенов сохраняется в зашифрованном виде в `OperationsData.sber.encryptedTokens` и имеет приоритет над первоначальными переменными. Ключ шифрования сохраняйте вместе с резервной копией конфигурации; его произвольная замена сделает сохранённую пару нечитаемой. Все запросы выполняются через mTLS с проверкой цепочки и имени сервера. Неизвестный `redirect_uri` не требуется для использования выпущенного токена и refresh grant.

Рабочие банковские записи хранятся отдельно в `OperationsData.sber`. Локальное хранилище использует атомарную запись, облачное — существующий механизм Blob с проверкой версии. Каждый запрос, включая обновление токенов, защищён общей блокировкой соединения. Новая пара сохраняется до следующего запроса выписки. Содержимое банковских ошибок не попадает в логи или браузер: оно может содержать ключ доступа.

## Получение и проверка данных

Используются только GET-ресурсы выписки и POST обновления токенов на `https://fintech.sberbank.ru:9443`:

- `/fintech/api/v2/statement/summary`: `accountNumber`, `statementDate`.
- `/fintech/api/v2/statement/transactions`: те же параметры и `page`, начиная с 1. Продолжение — по `_links` с `rel=next`; произвольные URL банка не вызываются.
- `/fintech/api/v2/statement/transactionId`: `id`, `accountNumber`, `operationDate`.
- `/ic/sso/api/v2/oauth/token`: `grant_type=refresh_token`, `client_id`, `client_secret`, `refresh_token`.

Один шаг синхронизации получает одну страницу. Данные дня публикуются атомарно после получения всех страниц и сверки доступных итогов. Повторная загрузка заменяет полный день, удаляет устаревшие записи этого дня и исключает дубли по банковскому идентификатору и счёту. JSON-числа сразу разбираются как строки, расчёты используют десятичную арифметику. Неизвестные суммы не превращаются в нули. При расхождении оборотов или остатков предыдущий день остаётся доступным, а новый запрос начинается с первой страницы.

Локальная служебная загрузка с теми же проверками:

```sh
node --import tsx scripts/sber-sync.ts 2026-09-01 2026-09-16
```

Команда обращается к промышленному банку и сохраняет выписки в локальном рабочем хранилище. Секреты в аргументах не передаются. Для размещённой CRM синхронизация запускается из её авторизованного интерфейса после отдельной настройки серверного окружения.

## Фактически проверено 16.09.2026

- Сертификат прочитан с сохранённым паролем, соответствует сервису и действует до 14.09.2027. Проверка сертификата сервера включена; реальные запросы прошли.
- За 15.09.2026 банк вернул: начало 328 528,12 ₽; поступления 5 963 464,47 ₽; списания 3 300 000,00 ₽; конец 2 991 992,59 ₽. Все значения совпали с предоставленной сверкой. Они не используются как данные приложения.
- За 01–16.09.2026 получены 16 дневных выписок и 136 операций. Суммы операций сверены с оборотами, баланс сходится во все 16 дней.
- Повторная промышленная загрузка того же периода сохранила те же 136 уникальных банковских идентификаторов: дублей нет. Контрольные суммы отгрузок, справочников, распределений платежей, работы и Китая до и после повторной загрузки совпали.
- Отдельный промышленный запрос подробностей вернул ту же операцию. Реальный refresh grant вернул новую пару; она сохранена, запрос с новым access token успешно выполнен. Тем самым секрет сервиса был действителен на момент проверки; его будущий срок действия отдельно не подтверждался через API.
- Подробные результаты проверки и повторной загрузки: локальный `qa/sber/live-verification.json`. Он не входит в Git. Тестовые ответы и реальные банковские данные не смешиваются.

Автоматические проверки: все 148 тестов `npm run test:api`, `npm run lint`, `npm run build` прошли. `node --import tsx scripts/verify_sber.mjs` проверил выбор дня, фильтры, подробности, повторную синхронизацию, сохранение данных при ошибке, восстановление после отказа банка и запрет будущих дат. Экраны и диалог проверены при ширинах 1440, 768, 390 и 320 px: нет горизонтального переполнения страницы; Axe WCAG A/AA не обнаружил нарушений, ошибок JavaScript нет. Browser QA использует изолированное временное хранилище и синтетические банковские ответы. Сведения о фактическом промышленном запросе приведены отдельно выше.
