# Хранение данных Artel CRM

На текущем этапе используется локальная выгрузка в JSON. База данных и облачный сервис не развёрнуты. Для будущей общей CRM с несколькими менеджерами рекомендуется PostgreSQL; для небольшого приложения на одном компьютере можно рассмотреть SQLite.

Официальные источники проверены 9 сентября 2026 года. Ниже приведена рекомендация по архитектуре, а не выбранный тариф хостинга.

| Вариант | Для чего подходит | Стоимость ПО | Ограничения и работа по эксплуатации |
| --- | --- | --- | --- |
| JSON сейчас | Перенос, проверка и сохранение исходной выгрузки | Формат не требует платной БД | Сам по себе не даёт транзакций, связей между записями, одновременного редактирования и разграничения доступа |
| SQLite | Локальное приложение или небольшой сервер с умеренным числом записей | Основной код находится в общественном достоянии | Один писатель одновременно; файл БД должен находиться рядом с приложением, не на общей сетевой папке для прямой записи с разных ПК |
| PostgreSQL | Общая CRM, связанные компании/отгрузки, параллельная работа | Бесплатная открытая лицензия PostgreSQL, включая коммерческое использование | Нужен работающий сервер БД; необходимо организовать доступ, резервное копирование, восстановление и обновления |

SQLite работает внутри приложения без отдельного серверного процесса. Это упрощает локальный запуск. Ограничение одним писателем и рекомендации по сетевому доступу подтверждены документацией проекта. [Архитектура SQLite](https://www.sqlite.org/serverless.html), [сценарии использования SQLite](https://www.sqlite.org/whentouse.html), [условия использования SQLite](https://www.sqlite.org/copyright.html).

PostgreSQL разрешает использование без лицензионной платы. Для этой CRM он предпочтителен как будущая центральная БД: компании, отгрузки и пользователи образуют связанные данные, а менеджеры будут работать параллельно. Это наш вывод из требований проекта. PostgreSQL поддерживает ограничение видимости строк через Row-Level Security; эти политики нужно проектировать и тестировать вместе с серверной авторизацией. Они не появляются автоматически после установки БД. [Лицензия PostgreSQL](https://www.postgresql.org/about/licence/), [описание PostgreSQL](https://www.postgresql.org/about/), [политики доступа к строкам](https://www.postgresql.org/docs/current/ddl-rowsecurity.html).

Бесплатная лицензия не означает бесплатный хостинг. На собственном компьютере можно использовать PostgreSQL без оплаты за ПО, но доступность сервиса зависит от включённого компьютера, диска и сети. Для удалённой командной работы сервер, резервные копии и сопровождение могут стоить денег. Бесплатный облачный тариф, если он будет выбран позже, нужно отдельно проверить по лимиту хранилища, остановке при простое, резервным копиям, доступности из нужного региона и условиям использования. Обещания постоянно бесплатного хостинга здесь нет; конкретный провайдер пока не выбран.

## Как сохранить возможность миграции

- Сохранять исходную выгрузку отдельно от нормализованных сущностей и отчёта проверок. У каждого значения или записи должна оставаться ссылка на источник: файл, лист и строку; для прямого импорта из Google — также идентификатор таблицы и момент выгрузки.
- Не терять исходные значения при нормализации. ИНН, КПП, ОГРН, счета, телефоны и коды хранить строками; отсутствие значения отличать от нуля. Для денежных сумм выбрать точное представление: десятичные строки с валютой либо целые минимальные единицы; не использовать двоичные `float` как единственный источник финансовой суммы.
- Использовать устойчивые идентификаторы и явные связи. В текущей выгрузке отгрузки содержат `customer_id` (покупатель), `supplier_id` (поставщик), `carrier_id` (перевозчик), а платежи — `counterparty_id`. Контроль доступа менеджера к отгрузке опирается на её владельца и владельца покупателя по `customer_id`; ссылки на поставщика/перевозчика и владение компанией не открывают чужие карточки или финансовую выписку. Неподтверждённую связь или владельца оставлять `null` и выносить в отчёт проверки. Не объединять компании только по похожему названию.
- Фиксировать версию формата, время импорта и контрольную сумму исходного файла. Повторный импорт того же источника не должен создавать дубликаты; источник и нормализованные данные должны позволять проверить это.
- При внедрении БД сначала импортировать в промежуточные таблицы, проверить количество записей, связи и контрольные суммы/суммы. После проверки переносить в рабочие таблицы транзакционно. Сохранить исходный JSON для воспроизводимой сверки.
- Добавить пользователей и владельцев отдельным этапом после подтверждения соответствия реальным сотрудникам. Модель доступа описана в `access-model.md`; текущий JSON не является многопользовательским хранилищем с авторизацией.

Для выбора места размещения PostgreSQL позже понадобятся число одновременно работающих пользователей, ожидаемый объём данных и вложений, необходимость доступа вне офиса и требования к резервному восстановлению. До этого локальный JSON закрывает задачу выгрузки без преждевременного подключения платных сервисов.
