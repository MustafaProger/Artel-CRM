# Банковские выписки в «Платежах»

Реализовано локально 14.09.2026. Реальные банковские подключения и промышленная инфраструктура не проверены: банковские доступы не предоставлены. Проверки адаптеров и синхронизации используют синтетические ответы; браузерные проверки работают с отдельным временным хранилищем. В приложение тестовые операции не добавляются.

## Подключения

| Подключение | Компания | Префикс серверных переменных |
| --- | --- | --- |
| СберБизнес | НК АРТЕЛЬ | `ARTEL_BANK_SBER_NK` |
| СберБизнес | АРТЕЛЬ | `ARTEL_BANK_SBER_ARTEL` |
| Т-Банк | НК АРТЕЛЬ | `ARTEL_BANK_TBANK_NK` |

В каждом подключении поддерживается несколько счетов. Компании и распределение банков подтверждены пользователем. Названия не используются для автоматического сопоставления контрагентов.

## Текущая архитектура и сохранность данных

- React 19 / Vite, собственный Node middleware `server/local-api.ts`; облачный обработчик `server/cloud-handler.ts`, Vercel Functions с пределом одного запроса 60 секунд.
- Источник XLSX — неизменяемая проверяемая выгрузка `data/local-xlsx-final`. Операционное состояние — JSON-конверт с SHA-256 и ревизией: локальный `OperationsStore` с файловой блокировкой и атомарным rename; в production `BlobOperationsStore` с private Blob и условными ETag-записями. Предел конверта — 64 MiB.
- Новое необязательное поле `OperationsData.banking` совместимо со старыми файлами. Существующие платежи, отгрузки, справочники, назначения менеджеров, распределения платежей и формулы не изменяются. Чтение раздела не запускает миграцию банковских данных или сетевую загрузку.
- Банковские записи не добавляются в `Snapshot.payments`, `paymentAllocations`, сводки отгрузок или задолженность. В модели только зарезервированы `counterpartyId`, `allocations[]`, `importedSourceIds[]`; сейчас они остаются пустыми.
- В справочнике есть устойчивый ID компании, ИНН, КПП, счёт и банковские реквизиты. Привязка к нему не выполняется. Совпадение названий не является доказательством связи.
- Существующая XLSX-выписка сохранена во вкладке «Архив из файла», включая поиск, период, направления, детализацию и CSV. Её строкам не хватает ID банка, нашего счёта и полных реквизитов. Поэтому суммы XLSX и API не объединяются. Автоматически удалять предполагаемые дубли по названию/сумме опасно. Для будущего импорта с банковскими ID предусмотрено поле `importedSourceIds`.
- Действующая сессионная авторизация и same-origin проверки сохранены. Все банковские списки, детали, PDF, CSV и ручная синхронизация требуют директора или администратора; менеджеры получают 403. Банковские данные не попадают в общий snapshot.

## Интерфейс и точность

Карточки подключений, перечень счетов, состояние доступа, время последней полной успешной синхронизации и загруженный период. Общая таблица и переход в отдельное подключение. Поиск по сторонам платежа, ИНН, назначению и номеру; период, направление, счёт, исходный статус банка; пагинация 10/25/50/100.

Итоги и CSV вычисляются на сервере по одному набору фильтров, по всем страницам. JSON-числа банка сохраняются строками до разбора ответа, затем суммы обрабатываются `decimal.js` с точностью 80 значащих цифр. Форматирование в браузере также не переводит деньги в `Number`. Суммы группируются по валюте счёта; конвертация не производится.

Боковая карточка содержит обе стороны, номер и даты документа, дату проведения, ID банка, наш счёт, сумму, валюту, направление, статус и назначение. Все дополнительные поля ответа, включая налоговые, комиссии, валютные и SWIFT-реквизиты, доступны в раскрываемом списке с их исходными ключами. НДС из текста назначения не превращается в подтверждённое поле НДС. Отсутствующие статусы/реквизиты отмечаются явно. PDF возвращает банк, CRM не генерирует поддельные банковские формы.

## Адаптеры и официальные источники

Документация проверена 14.09.2026. Подтверждение работы на реальных счетах требуется отдельно.

### СберБизнес

- [Обзор](https://developers.sber.ru/docs/ru/sber-api/overview).
- [Выписка по счёту](https://developers.sber.ru/docs/ru/sber-api/specifications/statement/transactions): `GET /fintech/api/v2/statement/transactions`, параметры `accountNumber`, `statementDate`, `page`, `curFormat=curTransfer`.
- [Операция по выписке](https://developers.sber.ru/docs/ru/sber-api/specifications/statement/transactions-id): `GET /fintech/api/v2/statement/transactionId`, параметры `id`, `accountNumber`, `operationDate`. Вызывается при открытии/обновлении карточки; сохранённая карточка доступна при ошибке запроса.
- [Банковская форма операции](https://developers.sber.ru/docs/ru/sber-api/specifications/statement/transaction-id-print): `GET /fintech/api/v2/statement/transactionId/print`, `format=PDF`; декодируется поле `file`.
- [Обновление токенов](https://developers.sber.ru/docs/ru/sber-api/specifications/oauth/oauth-token-post): `POST /ic/sso/api/v2/oauth/token`, `grant_type=refresh_token`.
- Промышленный адрес: `https://fintech.sberbank.ru:9443`. Пагинация по `_links` с `rel=next`: извлекается только проверенный номер следующей страницы, произвольный URL банка не посещается.
- `DEBIT` — списание; `CREDIT` — поступление. Статус платёжного поручения не выдумывается: его нет в выбранном ресурсе выписки. `operationId` — ключ движения; поручение отдельной записью движения не загружается.
- История: предыдущие 5 лет плюс текущий год. При неизвестном или неполном формате, отсутствии валюты/ID/направления, ошибке доступа либо недоступной выписке страница не считается успешно загруженной.
- Банковские методы выписок имеют ограничение 5 TPS; запросы подключений сериализуются и выдерживают паузу. Детали/печать используют ту же блокировку, что и синхронизация.

### Т-Банк

- [Сценарий и статусная модель](https://developer.tbank.ru/docs/products/account-info).
- [Выписка](https://developer.tbank.ru/docs/api/get-api-v-1-statement): `GET https://business.tbank.ru/openapi/api/v1/statement` с `operationStatus=Transaction`, `limit=1000`, `cursor` из `nextCursor`. Начало включительно, конец исключительно; даты выбранного московского дня преобразуются в UTC.
- История с июня 2023 года. Загрузка ограничена подтверждёнными транзакциями. Авторизации и холды не включаются в реальные движения.
- `Credit` — поступление, `Debit` — списание. Используются `accountAmount` и `accountCurrencyDigitalCode` (сумма в валюте нашего счёта), а не сумма валюты покупки. `payer` и `receiver` сохраняются без перестановки. `counterParty` и остальные поля остаются в дополнительных данных; отсутствующие стороны по ним не угадываются.
- [Подтверждающий документ](https://developer.tbank.ru/docs/api/get-api-v-1-payment-document): `GET /openapi/api/v1/payment-document`, параметры `operationId`, `operationDate`, `accountNumber`; поле `fileData`, Base64 PDF. Метод ограничен 1 RPS. Он доступен не для каждого типа движения.
- [Событие операции](https://developer.tbank.ru/docs/intro/webhooks/account-info): защищённый Bearer-токеном POST `/api/banking/webhooks/tbank-nk-artel`. Номер счёта проверяется по серверному списку. Повторы дедуплицируются по хешу тела; событие только ставит запрос сверки, не создаёт денежное движение. ID вебхука может отличаться от ID выписки.

## Как выполняется синхронизация

1. Директор/администратор выбирает начальный и конечный день и запускает загрузку истории. Сервер проверяет допустимую глубину истории и список счетов.
2. В хранилище создаётся задание с периодом, текущим счётом, днём и курсором. Каждый запрос обрабатывает одну страницу; фронтенд продолжает задание, пока открыт раздел. Периодическое серверное выполнение продолжает его и без браузера.
3. У подключения есть lease на 45 секунд с уникальным идентификатором владельца. Проверка владельца при записи запрещает запоздалому запросу затереть результат нового процесса. CAS-конфликты Blob повторяются только вокруг чистых изменений хранилища, сетевой запрос банка не выполняется внутри `mutate`.
4. Страницы одного дня временно накапливаются в задании. Только после последней страницы атомарно заменяется набор операций одного счёта за этот день. До этого старая полная версия доступна пользователю.
5. Повторные ID обновляют запись. Уникальность разделена по подключению, нашему счёту и ID банка. При смене банковского ID или удалении движения старая версия перемещается в `archivedOperations`, исключаясь из текущих оборотов. Архив технических версий сохраняется на сервере; отдельного интерфейса его просмотра сейчас нет.
6. Последняя успешная синхронизация обновляется только после всех дней и счетов выбранного задания. Успех одной страницы не выдаётся за успех всего периода.
7. Временные ошибки получают до пяти попыток с нарастающей задержкой и учётом `Retry-After`. При 401 Сбера сохранённый refresh token не удаляется: access token помечается просроченным. При постоянной ошибке или исчерпании повторов нужен ручной повтор. Сохранённые данные остаются доступными.

После первой загрузки автоматическая сверка охватывает последние 7 дней и весь пропущенный период после последнего успешного запуска. Интервал нового задания — минимум 15 минут; вебхук Т-Банка может запросить более раннюю сверку. Изменения банка старше окна сверки потребуют ручного повторного запроса того периода. Первоначальная история не выбирается автоматически.

### Планировщик

- `ARTEL_BANK_SYNC_ENABLED=true` включает автоматическую работу.
- Локальный Vite/preview проверяет задания каждые 30 секунд, только пока процесс запущен.
- В Vercel нет постоянного фонового процесса. Добавлен `.github/workflows/banking.yml`: запуск каждые 5 минут, несколько коротких обращений к `/api/banking/dispatch`. Используется GitHub OIDC с проверкой repository ID, owner ID, ветки, конкретного workflow и audience. Также поддерживается существующий `CRON_SECRET` для доверенного внешнего планировщика.
- Расписание не развёрнуто и не подтверждено этой реализацией. GitHub может задерживать scheduled jobs. Для строгого SLA нужен управляемый внешний планировщик и наблюдение за ошибками.
- Большая история требует многих коротких запросов. При росте банковских данных следует вынести их в отдельную транзакционную БД: весь JSON-конверт сейчас имеет лимит 64 MiB. Это ограничение существующего хранения; превышение не перезаписывает данные.

## Что нужно для реальных операций

1. Для каждого подключения указать подтверждённые номера наших счетов и валюты в `<PREFIX>_ACCOUNTS` — JSON-массив объектов `number`, `currency`. Сейчас список намеренно задаётся на сервере, автоматическое обнаружение всех счетов банка не реализовано. Успешная загрузка выписки подтверждает доступ к указанному счёту.
2. Для каждого Сбера: подключение нужного набора Sber API по договору; согласие организации на доступ к счетам; разрешение `GET_STATEMENT_ACCOUNT`, это же разрешение используется для печатной формы; `CLIENT_ID`, `CLIENT_SECRET`, первичный `REFRESH_TOKEN`; зарегистрированный клиентский TLS-сертификат и закрытый ключ, доверенная цепочка банка. Первичная интерактивная выдача согласия/токенов выполняется через процедуру банка, UI OAuth onboarding в CRM сейчас не добавлен.
3. Сертификаты задаются `<PREFIX>_TLS_CERT_PATH`, `_TLS_KEY_PATH`, при необходимости `_TLS_CA_PATH`. В Vercel можно использовать `_TLS_CERT_BASE64`, `_TLS_KEY_BASE64`, `_TLS_CA_BASE64` в защищённых серверных переменных. Нужна проверка исходящего mTLS на порт 9443 из выбранного хостинга и совместимости выданных сертификатов с Node TLS. [Требования Сбера к TLS](https://developers.sber.ru/docs/ru/sber-api/start/tls). Неподдерживаемая криптография потребует отдельного совместимого шлюза; проверки TLS не отключаются.
4. `ARTEL_BANK_ENCRYPTION_KEY` — отдельный случайный 32-байтовый ключ в hex (64 символа). Ротируемые токены сохраняются AES-256-GCM с привязкой к ID подключения; исходные ключи остаются в серверном окружении. Потеря ключа делает сохранённые токены недоступными. Ни реквизиты доступа, ни ответы OAuth не выводятся в журналы и клиентские ответы.
5. Для Т-Банка: `<PREFIX>_TOKEN` с правами «Информация о счетах компании» и «Информация об операциях компании» для НК АРТЕЛЬ. Отдельный `<PREFIX>_WEBHOOK_TOKEN` и регистрация защищённого HTTPS callback у банка нужны для событий; до регистрации работает периодическая выписка.
6. Вебхуки Сбера пока не активированы: [банк требует mTLS и проверку ГОСТ JWS](https://developers.sber.ru/docs/ru/sber-api/start/webhooks/security). В текущем Vercel/Node окружении такого входящего шлюза нет. Небезопасный обход проверки подписи не добавлен. Нужны совместимый шлюз, банковский публичный ключ/цепочка и согласованные события; пока используется периодическая сверка.
7. Перед промышленным включением сделать резервную копию действующего хранилища, настроить доступы, развернуть код/планировщик, загрузить короткий период каждого счёта и сверить количество, суммы, валюты, стороны и печатную форму с выпиской банка. Только затем расширять историю и включать расписание.

Создание, подписание и отправка платежей, автоматическое пополнение баланса, разнесение авансов, проводки и интеграция с отгрузками отсутствуют по границам задачи.

## Продолжение промышленного подключения 14.09.2026

Первоначальные формулировки выше описывают состояние до выдачи сертификата. Сейчас получен существующий PKCS#12 для сервиса `88091` (НК АРТЭЛЬ). Пароль введён владельцем в локальную форму; Node `createSecureContext` успешно открыл контейнер. Локальная проверка с клиентским сертификатом: TCP 9443 доступен, серверный TLS проверен, HTTP 401 без OAuth-токена. Это проверка транспорта, не доступа к счёту.

### Доверенная цепочка

Архив `chain_prom.zip` по ссылке из [TLS-документации](https://developers.sber.ru/docs/ru/sber-api/start/tls) содержит `SberAPI Root CA` и `SberAPI CA`. Фактический сервер `fintech.sberbank.ru` использует цепочку `SberCA Ext` → `SberCA Root Ext`; одного архива недостаточно. Корень получен по [официальной ссылке Сбера](https://cdn-app.sberdevices.ru/misc/0.0.0/assets/bsm-docs/6020194e_sberca-root-ext.crt), опубликованной на странице авторизации. Проверка сертификатов не отключалась. Дополнительные CA применяются только к банковским запросам, системное доверие macOS не меняется.

Поддерживаются `_TLS_PFX_PATH` / `_TLS_PFX_BASE64` + `_TLS_PASSPHRASE`. Одновременная передача PFX и PEM cert/key запрещена. В production используются только защищённые серверные переменные. При диагностике HTTP 202 выписка повторяется не раньше чем через 60 секунд, включая `Retry-After: 0`.

### Первичная авторизация в CRM

- Директор/администратор запускает POST `/api/banking/connections/sber-nk-artel/authorize` из «Платежи → Подключение». Права фиксированы: `openid GET_STATEMENT_ACCOUNT inn orgFullName accounts`. Широкий scope из карточки сервиса не переносится.
- Callback: `https://artel-crm.vercel.app/api/banking/oauth/sber/callback`. Его нужно отдельно зарегистрировать в карточке сервиса до реальной авторизации.
- Настройки на сервере: `_REDIRECT_URI`, `_EXPECTED_INN`, `_OAUTH_ISSUER` (точное подтверждённое значение `iss`), `_ACCOUNTS`, client ID/secret, TLS и ключ шифрования. Неизвестный issuer нельзя подставлять наугад. Пока настройки неполны, начало авторизации отклоняется.
- PKCE S256 подтверждён в текущей интерактивной спецификации `/oauth/authorize` и модели TokenRequest официального [SDK](https://github.com/GreenBankTeamRu/SDK). Verifier и nonce хранятся зашифрованными. State живёт 10 минут, связывается с отдельной HttpOnly/Secure/SameSite=Lax cookie и исходной сессией CRM. Общая cookie остаётся SameSite=Strict, прочие cross-site API запрещены.
- Callback атомарно потребляет state до обмена кода. Проверяются действующая сессия и роль инициатора, браузер, срок, точный callback, конфигурация организации/счетов, nonce, issuer, audience/azp, срок ID token, ИНН и разрешённые счета. Конкурирующая новая авторизация не позволяет старому ответу перезаписать токены.
- ID token принимается исключительно из прямого ответа фиксированного Token Endpoint через проверенный mTLS. Для такого back-channel ответа используется разрешённая [OIDC Core §3.1.3.7(6)](https://openid.net/specs/openid-connect-core-1_0.html#IDTokenValidation) аутентификация эмитента через TLS. Независимая проверка ГОСТ/CMS-подписи здесь не выполняется; клиентские ID token не принимаются. Это не реализация проверки подписей вебхуков.
- Более широкие права отклоняются. Ротируемые токены сохраняются AES-256-GCM в приватном operations-store; после onboarding исходный `REFRESH_TOKEN` в окружении не нужен. При обновлении токена проверяется отсутствие расширения подтверждённых прав.

### Локальный ввод секретов

`node scripts/setup_sber_secrets.mjs /absolute/path/to/certificate.p12` открывает форму на `http://127.0.0.1:8789`. Только loopback, проверка Host/Origin и CSRF; секреты сохраняются в `.vercel/sber-private/` (каталог 0700, файлы 0600, исключены Git). После успешного сохранения сервер закрывается. Поле настроек принимает буфер кнопки «Скопировать настройки»; содержимое требует проверки перед переносом в env и не выполняется как код. Не подставлять `[SENSITIVE]` из Vercel env pull.

### Диагностика возврата и разделение окружений — 14.09.2026

При разборе неудачного входа production содержал `oauthAttemptHash`, но уже не содержал `encryptedOAuth` и `encryptedTokens`. Это подтверждает потребление попытки, но прежняя реализация не сохранила причину отказа. По старому общему сообщению нельзя достоверно определить конкретную проверку токена. Значение issuer не изменено без подтверждённого ответа банка.

Теперь callback возвращает страницу с понятной причиной и ссылкой в «Платежи». Ошибки формата, issuer, audience, nonce, subject и срока разделены; старые ссылки не переиспользуются. Для отказов проверки токена сохраняются только статическая причина, время и, если он является корневым HTTPS-адресом в домене sberbank.ru, публичный issuer. Коды, nonce, токены и личные claims в диагностику не включаются. Существующие рабочие токены при неудачном переподключении сохраняются. Значение token_type сравнивается без учёта регистра.

Локальные настройки загружаются сервером Vite из `.env.local`. Секреты и сертификаты не входят в Git и клиентскую сборку. Локальное хранилище не заменяется production-хранилищем. При несовпадении текущего Host с зарегистрированным callback кнопка входа заблокирована с объяснением; backend также отклоняет запуск без записи OAuth-попытки.

Порядок переноса на собственный сервер:

1. Проверить изменения на локальных тестах и отдельном хранилище.
2. Для настоящего OAuth в локальном окружении предоставить ему собственный доверенный HTTPS-адрес и зарегистрировать точный callback в Сбере. Текущий `http://127.0.0.1:5173` не является зарегистрированным callback. Не пересылать код через Vercel в локальную CRM и не ослаблять проверку браузера.
3. На сервере настроить его `_REDIRECT_URI`, подтверждённый `_OAUTH_ISSUER`, сертификат, список счетов и серверные секреты. При переносе зашифрованных банковских данных сохранить соответствующий `ARTEL_BANK_ENCRYPTION_KEY` через защищённый канал.
4. Выполнить новый вход из целевой CRM и проверить короткий период выписки. Только затем включать расписание.

Проверки изменения: 109 API-тестов, lint и build; отдельно проверены отрицательный ответ банка, сохранение предыдущих токенов, безопасная диагностика и блокировка смешения окружений. Локальный mTLS получил ожидаемый HTTP 401 без OAuth-токена, сертификат сервера проверен. Реальная авторизация и загрузка выписки ещё требуют повторного входа владельца.


### Явный запрос идентификационных полей

Следующая реальная попытка завершилась `issuer_mismatch` (14.09.2026, 13:08:22 UTC). Значение issuer не попало в прежнюю диагностику: она разрешала только корневые URL. Это не доказывает конкретный правильный адрес и также не исключает отсутствие поля `iss`.

В ссылку добавлены `iss aud sub`, перечисленные в [официальном примере Сбера](https://developers.sber.ru/docs/ru/sber-api/specifications/oauth/oauth-authorize-get); банковская операция остаётся только `GET_STATEMENT_ACCOUNT`. Проверки эмитента и личности не ослаблены. Отсутствующий issuer теперь отличается от несовпадающего. Диагностика сохраняет точный публичный HTTPS issuer в домене sberbank.ru, включая путь, и результаты всех проверок в виде булевых флагов. Значения личных полей и токены не сохраняются. Ожидаемый issuer не заменяется автоматически данными из ответа банка.

Локально проверены шесть OAuth-тестов, сборка и lint. Для подтверждения фактического ответа требуется новая авторизация: предыдущий одноразовый код уже использован.

Следующая диагностика подтвердила наличие issuer и успешные проверки audience, azp, nonce, subject и времени, при отсутствии реквизитов компании в ID token. Добавлен фиксированный mTLS-запрос `GET /ic/sso/api/v2/oauth/user-info` с заголовком Bearer, как в официальном Java SDK; ответ представляет собой компактный JWT. UserInfo принимается только после проверки ID token, с совпадающим sub, проверкой имеющихся iss/aud/exp, затем ИНН и разрешённых счетов. Реквизиты, уже присутствующие в ID token, не заменяются сведениями UserInfo. Публичный issuer в диагностике сохраняется как ограниченный идентификатор: это метаданные для ручной сверки, адрес не вызывается и не становится доверенным автоматически. [UserInfo Сбера](https://developers.sber.ru/docs/ru/sber-api/specifications/oauth/oauth-user-info-get). Проверены 20 банковских тестов, lint и build.
