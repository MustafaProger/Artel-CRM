## Предметный облачный кандидат и его ограничения

Найден именно размещённый у производителя **Сервис электронной подписи КРИПТО-ПРО**. Официально описаны HSM-хранение на сервере и REST/SOAP/HTTP API без покупки собственного оборудования. Это кандидат для проверки условий, а не уже выбранное решение. [Описание сервиса](https://dss.cryptopro.ru/).

В стандартном регламенте №3 от 28.11.2025 пункт 6.2.3 требует вторичную аутентификацию через мобильное приложение. Поэтому стандартную схему нельзя считать доказанным решением без телефона. Этот пункт сам по себе не определяет частоту подтверждений каждой конкретной операции. [Регламент СЭП, стр. 7](https://dss.cryptopro.ru/reglament/dssreglament.pdf).

Отдельная схема со сторонним УЦ предусматривает серверное хранение, API и выбор методов аутентификации с учётом вида подписи. Нужен ответ провайдера о конкретной комплектации **КЭП**, постоянной автономной работе, типах подписантов и применимости к Saby. Загрузка публичного сертификата в сервис не означает доступ к его закрытому ключу; возможность использовать нынешние КЭП или необходимость нового выпуска не установлена. [Схема со сторонним УЦ](https://dss.cryptopro.ru/external-cc.html).

Saby документирует передачу готового файла подписи в `СБИС.ВыполнитьДействие` через `Этап.Вложение.Подпись.Файл.ДвоичныеДанные`. Следовательно, отдельный криптографический API имеет документированную точку подключения. Совместимость конкретных КЭП, форматов и регламентов заявок/ЭТрН ещё требует проверки. [Execute API](https://saby.ru/help/integration/api/all_methods/make_doc).

Штатный `Отложенный` по-прежнему предусматривает доступный исполнитель с приложением Saby, СКЗИ и ключом. Документация не подтверждает наличие такой управляемой услуги у самого Saby. [Отложенное подписание](https://saby.ru/help/integration/api/sequence/delegate).

3. Зафиксировать контракт исполнителя: какие байты подписываются, формат подписи, идентификатор задания, безопасная квитанция, правила сверки после тайм-аута и перезапуска. Не предполагать идемпотентность сервиса.

## Независимая работа с кодом

Подтверждён разрыв оснований проверки: `etrn-linked-draft.ts` сохраняет полный нативный XML и отдельно проверяет нужные поля CRM, тогда как `etrn-dispatch.ts:120,163` и `saby-consignment-evidence.ts:67` снова сравнивают его с генерируемым шаблоном. Сохранность нативного XML сама по себе не доказывает основание подписать все дополнительные деловые поля.

Следующий шаг — приватное структурное сравнение `beforeBase64`, `filledBase64` и шаблона из того же snapshot/номера. Наружу выводятся только пути и категории различий. Для каждого отличия требуется основание: эквивалентная форма, подтверждённый реквизит, сведения подписанной заявки либо неподтверждённое деловое утверждение. Замена всего сравнения на `filledBase64` без этого разбора не принята. Старые документы могут служить доказательствами без восстановления или продолжения их цепочек.

Локально исправлена только ложная диагностика: повторный опрос теперь сохраняет `blocked` и исходную причину отказа до Prepare, если нет signing binding/манифеста, признаков Execute, подготовки или записи ответа перевозчика. При неоднозначных признаках прежний `unknown` сохранён. Проверки XML не ослаблены, повторные сетевые действия не разрешены.

Файлы: `server/etrn-dispatch.ts`, `tests/saby-consignment-dispatch.test.ts`. Целевой набор — **11/11**, TypeScript и ESLint прошли; независимый обзор не выявил замечаний. В расширенном наборе — **63/66**. Те же три отказа соседних `OperationsStore wrapper` воспроизведены в изолированной копии с исходным `etrn-dispatch.ts` из HEAD: **19/22**. Причина тестовой фикстуры: `withRequestGuard()` создаёт базовый `SabyClient`, теряются overrides `StoreClient`, после чего сохранённый транспорт теста бросает `Network forbidden` при проверке организаций. Реальных вызовов Saby нет; отдельная трассировка подтвердила отсутствие внешней сети. Фикстура в этой задаче не изменялась. Исправление пока только локальное; оно не запускает подпись и не завершает интеграцию.
