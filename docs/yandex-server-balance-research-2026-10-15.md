### Свежесть документации и срок доступа

Полный официальный справочник получен системным `/usr/bin/curl` с включённой TLS-проверкой. Размер 887 683 байта; SHA-256 `160fe98f56e9d4452dc763066c4b984a065e7cbd9eb89f11ab63589ecd702c1c` совпадает с 14 октября. Проверены весь текст и каталог методов. Отсутствуют `balance`, `contracts`, `available_funds`, `overdraft`; русские упоминания баланса относятся к правам пользователя в кабинете.

[Начало работы](https://taxi__business-api.docs-viewer.yandex.ru/ru/concepts/quickstart.md) прямо описывает ограниченный срок OAuth и получение нового токена через кабинет после истечения. Поэтому даже работающий сегодня OAuth нельзя представлять как бессрочный доступ без участия пользователя. Для выбранного серверного метода нужно подтвердить служебную авторизацию либо автоматическое обновление токена, TTL и отзыв.

Журнал релизов по-прежнему сообщает о выводе API 1.0 из использования в июле 2026. Исторические методы не проверялись без нового основания.

### Проверенная новая зацепка: протокол v1.2

Поиск обнаружил копию «Программный интерфейс корпоративного клиента v1.2» с `/tanker/api/user/balance/item`. Из полного текста следует обратное направление: корпоративный клиент предоставляет свой URL и ключ, а TANKER запрашивает баланс сотрудника **в системе клиента**. Отдельный метод отчёта содержит операции, не остаток нашего договора у Яндекса. Это не основание вызвать данный путь на домене Яндекса.

Копия расположена на стороннем зеркале, её актуальное официальное размещение не установлено. Поэтому она использована только для исключения ложной поисковой зацепки, не как документация выбранного API; поисковая дата публикации не доказывает дату протокола.

## Что подготовлено по CRM

Read-only анализ текущего checkout установил минимальную область будущей реализации:

- `server/cabinet-connections.ts`: три allowlist автоматических провайдеров, создание клиента, отдельный тип ошибки. Текущие credentials принимают только login/password — OAuth требует явной схемы, а не маскировки под пароль. Сохранённый отдельный encrypted token не включён в connection.
- `web/src/cabinet-model.ts`: Яндекс уже есть в каталоге, имеются поля договора, деталей и времени источника. Формат идентификатора счёта для Яндекса пока ограничен цифрами; окончательный формат следует определить по реальному ответу.
- `web/src/CabinetBalances.tsx`: нужно разрешить automatic только после рабочего метода; текущий экран не выводит contract/details/sourceUpdatedAt. Для Яндекса понадобятся явно раздельные собственные средства и отсрочка, подписи договора и актуальности.
- `server/production.ts`: планировщик уже работает на сервере, tick раз в минуту, обычный интервал кабинета пять минут. Ошибка сохраняет последний успешный снимок; `auth_required` останавливает автоповторы. После restart адаптер обязан восстановить доступ без Mac.
- `tests/api-cabinets.test.ts`, `tests/api-fuel-cabinets.test.ts`: основа будущих проверок точных копеек, неполного ответа, сохранения снимка, ошибок доступа, прав и отсутствия секретов.

Это карта внедрения, **не реализованный адаптер**. Без схемы ответа/авторизации готовить фиктивный клиент и включать «Подключено» было бы недостоверно. Уже существующий scheduler не требуется заменять.

После получения документации/доступа: реальное серверное чтение и сверка полей → реализация из exact текущего production source с узким overlay → проверки/оба образа/backup → выпуск с сохранностью → автоматическое чтение после restart → авторизованный desktop/mobile/tablet UI. Физические устройства и синтетические viewport-проверки указывать раздельно.
